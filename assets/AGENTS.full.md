# SpecGate Workflow (DSH)

> This file is generated by `dsh-plugin-specgate`. The following rules apply within the current project.
> Status: `/sg-status`; next step: `/sg-next`; gate: `/sg-gate <Gx>`; commit: `/sg-commit`.

## Core principles

- User instructions take precedence; ask first when unsure, and never guess APIs, configuration, or file contents.
- Run entry triage on any modification request first: Q&A / light modification / heavy modification.
- **1% rule**: if there is even a 1% chance that a Skill applies, load it first; if you believe it is not needed, you must explain why and get user consent.
- Do not skip gates; when the user says "continue" it only means continuing the current discussion, not skipping a review.
- Do not slice Specs horizontally by technical component/layer; every Spec must describe end-to-end user value.
- Over-design, surface fixes, and aimless execution are forbidden.

## Gates

| Gate | Name | Trigger | Pass condition |
|------|------|---------|----------------|
| G1 | Requirements understanding confirmation | Requirements questioning complete | User explicitly confirms the understanding is correct |
| G2 | Change classification confirmation | L1/L2/L3 recommendation complete | User confirms the paradigm |
| G3 | proposal review | proposal.md complete | User confirms approval |
| G4 | design review | design.md complete | User confirms approval |
| G5 | specs review | specs/ complete | Vertical slicing, requirements covered, user confirmation |
| G6 | tasks review | tasks.md complete | Reasonable split, appropriate granularity, user confirmation |
| G6.5 | Brief generation check | Large change | Generate a Brief or record a deviation |
| G7 | Critical review / implementation | After tasks pass | User approves entering implementation |
| G8 | Code review | Code complete | User confirms starting the review |
| G9 | Review passed / commit | Review complete | User confirms the commit |
| G10 | Feature acceptance | Development complete | User confirms acceptance |
| G11 | Branch handling | Tests pass | User confirms merge/PR |

- Wait for only one gate confirmation at a time; never ask about multiple artifacts in a single question.
- Command-channel confirmation must explicitly include `--yes`: `/sg-gate G1 confirm --yes`; without it, only a pending-confirmation hint is returned.
- Skipping a gate requires: explaining the reason, informing the user, user approval, `/sg-gate <Gx> waive --yes <reason>`, and a write to `.specgate/deviations.log`.

## Paradigms

| Paradigm | Meaning | Gate strength |
|----------|---------|---------------|
| L1 | Requirements-driven | Full G1-G11 |
| L2 | Technical implementation | Standard G1-G11 |
| L3 | Defect fix | G1/G3/G4/G5 may be skipped; G2/G6/G7-G11 mandatory |

## Agent roles

- `sg-agent-po`: requirements clarification, acceptance criteria, priorities, review.
- `sg-agent-architect`: Spec decomposition, dependency ordering, technical approach, architecture review.
- `sg-agent-ddd`: domain-driven design, bounded contexts, aggregate design.
- `sg-agent-developer`: Spec Task implementation, code writing, unit tests.
- `sg-agent-reviewer`: code review, quality assessment, anti-pattern detection.
- `sg-agent-knowledge-engineer`: experience capture, ADR maintenance, knowledge conflict adjudication.
- `sg-agent-process-guardian`: paradigm enforcement, rule compliance, deviation records, process audits.
- `sg-agent-config-maintainer`: `.specgate/` directory governance, configuration consistency, version management.
- `sg-agent-scaffold-maintainer`: genericity audits of generated assets, import/export verification.

Role texts live in `.specgate/agents/`; the current version carries them through the main Agent + Skills and does not force separate subagents.

## Git workflow

- Initialization runs `git init` and creates an initial commit by default.
- **The working tree must be clean before every gate confirmation**; if there are uncommitted changes, run `/sg-commit` or commit manually first.
- Confirming a gate writes `.specgate/gates/<Gx>.confirmed`; that marker is itself a change and must be committed before the next gate.
- Commits use Conventional Commits: `<type>(<scope>): <description>`; type is limited to feat/fix/docs/style/refactor/perf/test/build/ci/chore/revert; the description uses Chinese, is no longer than 72 characters, and does not end with a period.
- Before starting a new feature, create a `feat/`, `fix/`, `refactor/`, or `docs/` branch from `master`/`main`.
- After the feature is complete, handle the branch: merge / PR / keep / discard; never leave an orphaned development branch.

## Knowledge capture

- Triggers: completing tool/framework research, resolving a P0/P1 bug, making an important technical decision, discovering a reusable best practice or anti-pattern.
- Directories: `.specgate/experiences/{tool-research,best-practices,pitfall-records,decisions}/`.
- Entry points: `.specgate/experiences/index.md`, `trigger-guide.md`.
- A record must include time, source, conclusion, scope of applicability, and verification status; never record unverified assumptions.

## Common commands

- `/sg-init`: initialize the project; `--path` creates a new directory; `--minimal` minimal; `--no-git` disables Git.
- `/sg-status`: project, Change, artifact, gate, and Git status.
- `/sg-next`: next-step recommendation.
- `/sg-gate <Gx> [status|confirm --yes|waive --yes <reason>]`: gate operations.
- `/sg-commit <message>`: commit the current changes.
- `/sg-classify <description>`: recommend L1/L2/L3.
- `/sg-doctor`: health check (four dimensions in parallel).
- `/sg-propose <name>`: create a Change skeleton.
- `/sg-apply <name> --plan`: inspect the parallel task plan.
- `/sg-apply <name>`: execute the implementation; split into waves by `[P]` / `depends`, up to 4 Agents in parallel, an independent worktree per task.
- `/sg-archive <name>`: archive.

## Idempotency and parallelism conventions

- Mutating commands can be repeated safely: if the state is already reached they return "idempotent skip"; do not delete state files manually just to re-run.
- `deviation` deduplicates for 24h by default; add `--force` when you really need to record it again.
- In `tasks.md`, mark parallelizable tasks with `[P]`, declare dependencies with `depends: T1,T2`, and designate a role with `role: reviewer`; unmarked tasks default to serial.
- Worktree parallelism requires a clean working tree; non-Git or dirty projects automatically degrade to a serial single writer.
- A merge conflict stops the run and keeps the worktree/branch; resolve the conflict manually first, then re-run.
- Do not manually edit files that an Agent is currently dispatching.

## DSH output conventions

- Tool results are shown by tool cards; command results are shown by persistent command cards.
- The first command in a new session additionally writes a `notice` context message so the result is visible and enters history; do not insert any message between a tool call and its tool result.
- The plugin provides no MCP server; MCP capabilities are managed by DSH independently.
