# SpecGate Workflow (DSH)

> Generated by `dsh-plugin-specgate` 2.x. These rules apply to this project.
> Status: `/sg-status`; next: `/sg-next`; gate: `/sg-gate <Gx>`; commit: `/sg-commit`.

## Core principles

- User instructions take precedence; ask first when unsure.
- Classify every modification request first: question / light / heavy; heavy changes need L1/L2/L3 classification.
- There is exactly one current requirements source: `requirements/REQUIREMENTS.md`.
- Requirement changes are versioned. Never edit the canonical requirements silently; create `/sg-change <id>`, review it, and let G3 apply a new version.
- Historical versions in `requirements/history/vX.Y.Z/` are immutable.
- Design, specs, tasks, tests and reports may exist, but they must reference requirement IDs/versions and must not restate the requirement text.
- **1% rule**: load a relevant Skill when there is even a 1% chance it applies.
- Do not skip gates. "Continue" does not mean approve.

## Requirement and version chain

```text
requirements/
├── REQUIREMENTS.md                 # current approved requirements
├── history/vX.Y.Z/REQUIREMENTS.md  # immutable snapshots
└── changes/<change>/
    ├── change.md                   # intent/scope/impact, no full requirement copy
    ├── change.json                 # added/modified/deprecated/acceptance delta
    ├── design.md
    ├── tasks.md
    ├── tests/cases.md
    ├── tests/matrix.md
    ├── approval.md
    ├── format-report.md
    ├── test-report.md
    └── review-report.md
```

- `/sg-change <id>` creates the change package.
- G3 approves the delta and writes the next version plus snapshot.
- A requirement change after G3 requires a new change/version.

## Gates

| Gate | Meaning |
|---|---|
| G1 | Requirements understanding / baseline confirmation |
| G2 | Change classification (L1/L2/L3) |
| G3 | Requirement delta approval and version snapshot |
| G4 | Design review |
| G5 | Test plan/cases review and freeze |
| G6 | Tasks review |
| G7 | Implementation entry |
| G7.5 | Format/lint pass |
| G8 | Test execution pass |
| G9 | Independent code review + commit |
| G10 | Acceptance |
| G11 | Branch handling |

- One gate at a time; command confirmation requires `--yes`.
- G5 freezes test cases; later expectation changes need re-approval.
- G7.5 checks only changed files; formatting runs before tests.
- G8 requires a passing test report with coverage; G9 requires a review report with no blocking items.

## Test Agent and pass bar

- The `tester` role is independent from the `implementer` role.
- Test cases and automation must be written before implementation.
- Tests run in an independent test worktree; the tester never modifies production code.
- Pass bar: P0/P1 100%, P2 at least 90%, line coverage at least 80%, branch coverage at least 70%; build/typecheck/lint clean; no new regressions.
- Unit and integration tests are required; automatable E2E is required; final manual acceptance is G10.

## Formatter and reviewer Agents

- Formatter step: independent format worktree, changed files only, auto-fix and lint.
- Review subagent: independent read-only review worktree for diff, requirement/test evidence, security and regression risk.
- No formatter/lint command means G7.5 stops; never skip.
- Reviewer reports blocking/non-blocking; blocking prevents G9.
- The main agent is the only merger; formatter is merged by the main agent, reviewer never merges.

## Worktrees and merge

```text
Dev:      specgate/<change>/<task>-dev
Format:   specgate/<change>/format
Test:     specgate/<change>/test
Review:   specgate/<change>/review  (read-only)
```

- Each dev task has its own worktree.
- Each change has one format and one test worktree.
- The main agent is the only merger.
- Test failure returns to the dev agent; the tester re-runs after the fix.
- The tester does not merge, commit production code, or change test expectations to force a pass.

## Commands

- `/sg-init` — initialize a v2 project with the requirements baseline.
- `/sg-change <id>` — create a requirement change package.
- `/sg-test <change> plan|run` — tester plans or executes tests.
- `/sg-status` — project, requirement version, change, gate, test status.
- `/sg-next` — next step.
- `/sg-gate <Gx> [status|confirm --yes|waive --yes <reason>]`.
- `/sg-commit <message>`.
- `/sg-apply <change>` — advance one stage: dev → format → test → review, then stop at the gate.
- `/sg-test <change> plan|run` — tester planning/execution.
- `/sg-archive <change>`.
- `/sg-migrate` — `.ak47/` → `.specgate/`.
- `/sg-requirements-migrate` — legacy `openspec` → `requirements/REQUIREMENTS.md`.

## Git and commits

- Every gate confirmation requires a clean working tree; commit or `/sg-commit` first.
- Conventional Commits: `<type>(<scope>): <description>`.
- Do not leave orphaned dev/test branches after G11.

## Agents

The runtime defines exactly two pipeline roles, `implementer` and `tester`; any other `role:` value is treated as a review-only role. SpecGate ships no `.specgate/agents/` catalog.

## DSH output

- Tool results render as tool cards; command results as persistent command cards.
- A first command in an empty session may add a `notice`; never insert a message between `tool_use` and `tool_result`.
- SpecGate ships no MCP server/tools; MCP is managed by DSH separately.
