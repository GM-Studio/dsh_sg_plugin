# Codex / SpecGate 用户入口与会话内环境准备需求

- 状态：核心实现与双平台命令验收通过；宿主交互与发布验收待完成
- 确认日期：2026-10-23
- 适用仓库：SpecGate Codex 插件
- 目标平台：Windows 与 Linux x64
- Linux 实机验收：VMware Workstation 中的 Ubuntu 虚拟机
- 验收平台修订：用户确认使用现有 Ubuntu 26.04.1 LTS 虚拟机；其他发行版分别记录未验证状态
- 验收运行模式修订（2026-10-23 用户确认）：宿主 Codex 保留认证与会话，调度 Ubuntu 执行 Linux 命令；不迁移认证信息，不要求本轮 Ubuntu CLI 独立登录
- 需求修订：仅提供 Codex 会话内的环境自检与按需安装，不提供外部安装脚本或全量准备入口
- 用户入口：四个任务 Skill 加一个统一导航；旧 `$sg-codex-setup` 保留兼容转接

## 1. 背景

SpecGate 的 Codex、Java、Vue 和 React 工作流依赖 Git、Node.js、npm、
Codex CLI、多个 JDK 与 Maven。当前用户需要逐项发现、安装和配置这些工具，
不同操作系统、权限与网络环境下的行为也不一致。

本需求仅通过进入 Codex 后的 Skill / 命令提供环境准备，先预检和复用，再根据项目
技术栈补齐缺失环境。Windows 与 Linux 采用同一会话内流程。
安装器使用临时国内镜像配置，安装完成后必须通过真实命令
验证工具链、Codex、SpecGate 以及 Java/Vue/React 工作流；生成文件或单元测试不能
替代真实双平台验收。

当前 `$sg-codex` 和 `$sg-codex-setup` 在环境修复、项目初始化与接入上存在职责
重合，且底层 `sg_project_setup` 主要配置 Agent、Skill 和 MCP，不能等同于完整
工具链安装。本需求同时收敛对外入口，区分环境准备、项目准备、需求开发和只读状态。

## 2. 目标

1. 在 Codex 中提供支持 Windows/Linux 的环境准备 Skill / 命令，共享核心规则。
2. 按项目技术栈补齐最小必需环境，验证就绪后才进入后续工作流。
3. 复用满足要求的现有安装，不静默覆盖用户版本或全局配置。
4. 默认适配国内网络，同时允许用户显式切换官方源或自定义镜像。
5. 支持幂等重跑、失败恢复、机器可读报告和安全的临时文件清理。
6. 在真实 Windows 和 VMware Workstation Ubuntu 环境中完成同一提交的验收。
7. 提供四个职责明确的任务入口与统一导航，各入口共享后台能力，避免重复流程。

### 2.1 对用户提供的入口

以下为已确认的入口划分，实现与验收范围以本次验收记录为准：

| 用户能力       | Skill               | 职责与完成条件                                                                 |
| -------------- | ------------------- | ------------------------------------------------------------------------------ |
| 环境准备       | `$sg-codex-env`     | 自检、复用、展示缺项、按技术栈安装和真实验证，报告环境是否就绪                 |
| 项目准备       | `$sg-codex-project` | 新项目初始化或存量项目接入，配置 Agent/Skill/MCP，建立项目基线，完成后等待需求 |
| 需求开发       | `$sg-codex-change`  | 新增、修改、修复的澄清、需求审批、开发、测试、验收和交付                       |
| 项目信息与状态 | `$sg-codex-status`  | 只读汇总当前项目、环境、基线、任务、阻塞原因和下一步                           |
| 统一导航       | `$sg-codex`         | 识别用户意图并转到以上能力，展示帮助，不复制一套执行流程                       |

旧 `$sg-codex-setup` 仅作为兼容别名，按原请求转到环境准备或项目准备。用户无需
先后手动调用多个 Skill；前置能力由任务入口按需衔接，但必须保持原请求边界。
命令菜单若可用，应复用相同流程；本阶段不要求再新增一套独立 slash 命令实现。

## 3. 最小必需范围

安装器支持以下组件，默认只处理当前宿主和项目需要的子集：

| 组件              | 要求                                                                    |
| ----------------- | ----------------------------------------------------------------------- |
| Git               | 可执行真实 clone、status、worktree 等 SpecGate 所需操作                 |
| Node.js           | 默认安装仓库验证门槛允许的固定 LTS 版本；复用版本必须满足当前门槛       |
| npm               | 随 Node.js 提供，能够执行 `npm ci`、测试、构建和打包检查                |
| Codex CLI         | 会话内先复用当前宿主，工作流需要独立 CLI 时才检查并补齐，不重复安装宿主 |
| JDK               | 支持 JDK 8、17、21，默认仅安装项目选择的版本，不改变用户默认 JDK        |
| Maven             | Maven 3.9.x，并可按选定 JDK 执行真实构建                                |
| 系统基础组件      | 安装过程必需的 HTTPS 证书、下载和解压工具                               |
| SpecGate 源码依赖 | 仅源码方式需要时在插件源码仓库按锁文件安装，普通插件用户不安装开发依赖  |
| SpecGate 接入     | 验证插件路径；宿主不支持插件时验证已定义的项目级 MCP + Skill 降级路径   |

Vue、React 及其构建依赖必须通过生成项目的锁文件按项目安装，不得全局安装框架
CLI。JDK 8、17、21 属于支持范围，不是每次都同时安装的清单。例如 Java 17 + Vue
只补齐 JDK 17、Maven、Node/npm 和项目依赖，切换到 Java 8 项目时再补齐 JDK 8。
本阶段不提供脱离项目技术栈的全量工具链准备入口。

## 4. 非目标

本阶段不安装或管理：

- 会话外独立安装脚本、PowerShell/Bash 安装入口或一键全量准备方案；
- Gradle、pnpm、Yarn；
- Docker、Kubernetes、数据库、中间件；
- Chrome、Playwright 或其他浏览器运行时；
- IDE、编辑器或 Codex Desktop 应用；
- macOS、WSL、容器镜像；
- 任意业务项目的数据库、生产配置或凭据；
- Codex 登录自动化。

缺少 Codex 登录时，安装器必须报告需要人工完成的步骤，不得伪造登录或可用状态。

## 5. 平台范围

首期实现目标均为 x64：

- Windows 10；
- Windows 11；
- Windows Server 2022；
- Ubuntu 22.04 LTS；
- Ubuntu 24.04 LTS；
- Ubuntu 26.04 LTS（用户指定的本次验收环境）；
- Debian 12。

发布验收至少包含当前真实 Windows 环境和 VMware Workstation 中真实 Ubuntu
26.04.1 虚拟机。WSL、容器或平台参数模拟不能作为 Linux 验收证据。
未实际执行的其他系统版本只能记录为“实现支持、未验证”，不得标记为通过。

非 x64 平台必须在任何安装变更前明确拒绝，并报告支持范围；不得下载错误架构。

## 6. 功能需求

### FR-001 唯一的会话内环境准备入口

用户进入 Codex 后，通过 `$sg-codex-env` 进行环境准备；`$sg-codex` 根据意图转接，
项目准备和需求开发入口按需使用同一环境门禁。`$sg-codex-setup` 保留为兼容别名。
普通用户无需查找脚本或 MCP 工具名；可见入口必须明确写入使用文档。

入口先识别平台、宿主和项目；存量项目读取真实技术栈，新项目先收集用户选择，
不得自行代选 JDK 或前端框架。

自检和安装操作均由 Codex 会话内的 Skill 协调执行，安装所需的本机命令仍遵守
宿主的网络与目录权限。不得把用户转到会话外执行独立安装脚本，也不提供另一套
Windows PowerShell 或 Linux Bash 安装入口。

当前 SG MCP 依赖 Node.js。缺少或不兼容时，应由已经加载的 Skill 引导 Codex 在
会话内预检并补齐 Node，然后重新连接 MCP；不得依赖尚未启动的 MCP 安装自己。
若 Skill 不可用或宿主权限阻止安装，明确报告阻塞原因和恢复步骤，保持工作流阻塞。

### FR-002 只读检查与安装模式

安装器必须至少提供：

- 只读检查模式，不下载、不写文件、不修改环境；
- 正式安装模式；
- JSON 机器可读报告；
- 按组件选择的安装能力；
- 仅准备当前项目所需组件，不提供独立全量安装模式；
- 显式选择国内源、官方源或自定义镜像的能力。

帮助和参数错误不得触发发现以外的系统变更。

### FR-003 有界发现与复用

安装前必须通过有界、跨平台的发现逻辑检查已有工具。满足要求的工具必须复用；
不满足要求的版本必须报告原因，再安装隔离版本，不能直接卸载或覆盖用户版本。

发现范围必须限于环境变量、PATH、受控安装目录和少量已知系统目录，不能递归扫描
整块磁盘。

### FR-004 最小化安装与权限

安装器先展示所需、可复用、缺失和不兼容组件，以及拟安装版本、来源和目标路径。
只安装当前项目缺失或明确要求重装的组件。默认优先采用不需要管理员权限的用户目录
安装；确实需要提升权限时，必须在执行前显示将运行的操作并等待操作系统或用户授权。

权限不足时必须尝试安全的用户目录方案，或明确失败；不得静默跳过组件。

### FR-005 多 JDK 共存

JDK 8、17、21 必须支持共存，并按项目预设选择；其他 JDK 缺失不得触发安装或阻塞
当前项目。安装器不得仅通过
覆盖全局 `JAVA_HOME` 实现切换，也不得破坏用户已有 JDK。每个 JDK 必须通过真实
`java` 与 `javac` 探测。

### FR-006 Maven 与 Node 环境

Maven 3.9.x 必须能在受支持 JDK 下运行。Node.js 与 npm 必须满足仓库当前验证门槛，
并能安装源码仓库及生成项目前端的锁定依赖。

默认安装版本必须固定并记录，不能在每次运行时无条件追随不受控的 latest 版本。

### FR-007 Codex 与 SpecGate 就绪检查

安装器必须执行 Codex CLI 的真实启动与能力探测，并区分：

- CLI 已安装；
- CLI 可运行；
- 用户已认证或仍需认证；
- 插件能力可用；
- SpecGate 插件路径可用；
- 插件不可用时，项目级 MCP + Skill 降级路径可用。

只有相应真实探测通过时，才能把该层状态标记为 ready。安装器不得修改或复制 Codex
登录凭据，也不得覆盖用户已有非受管配置。

### FR-008 国内镜像

默认使用适合国内网络的下载路径：

- npm 使用 npmmirror；
- Maven 使用阿里云公共仓库；
- Node.js、JDK、Codex 及基础归档使用实施时核验过的可信镜像。

镜像配置只对当前安装、验证进程或 SpecGate 管理的临时配置文件生效，不得永久修改
用户全局 npm 或 Maven 配置。用户必须可以显式改用官方源或自定义镜像。

若某组件不存在可校验的可信国内镜像，安装器必须明确报告并要求显式选择官方源，
不能静默换源。

### FR-009 下载完整性

所有便携归档必须使用 HTTPS、固定版本和可核验的 checksum 或签名。校验信息必须
来自可信元数据，不能用同一未受信任归档生成校验值。校验失败时必须删除下载文件、
停止安装并返回非零退出码。

### FR-010 环境持久化

用户目录工具链需要持久化时，安装器只能写入 SpecGate 明确拥有的环境文件或带起止
标记的受管块。重复执行必须替换同一受管块，不得重复追加 PATH，也不得改写无关内容。

本次进程必须立即使用新环境复测；新终端如何加载环境必须明确报告。

### FR-011 幂等与失败恢复

安装器重复执行时必须复用已验证组件，不重复下载、不创建重复配置。部分失败后再次
执行必须能从真实状态继续，不能依赖虚假的完成标记。

组件发布必须先在暂存位置完成下载、解压和探测，再原子地或等价安全地切换到目标
目录。失败不得破坏已工作的旧版本。

### FR-012 临时文件生命周期

下载包、解压目录、临时 npm/Maven 配置和验证项目必须有明确所有者，并在成功、失败
和受控中断后清理。清理必须使用有界重试；清理失败必须进入报告并可由后续运行安全
恢复。安装器不得删除无法证明由自己创建的目录。

### FR-013 真实验证与报告

每个组件安装后必须重新运行真实命令探测，不得仅根据文件存在或安装命令退出码宣布
成功。最终报告至少包含：

- 操作系统、架构和时间；
- 仓库提交；
- 每个组件的来源、安装方式、版本和实际路径；
- 复用、安装、失败、待人工操作或未执行状态；
- 实际执行的验证命令、退出码和证据位置；
- 镜像选择与校验结果；
- 临时目录清理结果；
- 未验证项和残余风险。

### FR-014 工作流环境门禁

准备流程必须执行“识别项目与技术栈 → 只读预检 → 复用 → 展示缺项计划 → 在已有授权
和宿主权限范围内安装 → 重新探测并真实验证 → 放行工作流”。

项目确认、技术栈选择、只读诊断和必要澄清可在门禁前进行。代码生成、实现和交付
必须在相应环境就绪后进行；正式构建测试前也须检查对应环境。环境准备自身的验证
命令属于门禁步骤，不得因门禁尚未通过被阻塞。

安装失败、权限拒绝、取消、版本不符或必要验证未执行时，必须保持阻塞，报告原因和
重试方式。不能把安装命令或配置生成成功当作环境就绪。结果必须绑定项目、技术栈、
实际工具路径和版本；这些条件改变后重新核验，不能复用另一项目的就绪标记。
条件未变时复用有效结果，避免每步重复下载或重新跑完整发布验收矩阵。

### FR-015 用户入口职责与统一导航

必须提供第 2.1 节的四个任务 Skill 和统一导航。环境准备完成不能自行创建项目或
开始开发；项目准备完成且未提供业务需求时停在就绪；需求开发可先澄清用户已提供的
需求，执行前必须满足环境、项目基线及原有 H1/H3 审批要求。导航不生成示例需求。

用户查询帮助或状态时，导航只能给出信息和建议，不自动启动安装、初始化、恢复或
开发。用户只请求环境准备时，不得把项目基线尚未建立当作环境安装失败。

### FR-016 项目准备与环境准备衔接

`$sg-codex-project` 负责新建与接入。新项目先收集用户选择的目录和技术栈，在必要
环境就绪后生成源码、安装项目配置并进行基线验证；存量项目读取真实配置并先预览
接入影响，保留用户文件，不再次初始化。

项目准备调用环境准备能力时，复用同一技术栈选择、缺项计划和安装结果，不反复填写
表单或执行重复安装。已生成但未验证的项目继续验证，已就绪的项目返回现状。
环境就绪与项目就绪必须分别报告；生成成功不能代替绿色基线。

### FR-017 只读项目信息与状态

`$sg-codex-status` 必须只读汇总：

- 当前业务项目路径和身份、技术栈；
- 环境检查结论、实际工具版本与路径、缺失项及证据时间；
- 初始化或接入情况、ProjectProfile、ProjectBaseline 状态；
- 当前 Change / WorkItem、执行阶段、最近验证和交付结果；
- 待澄清或审批事项、阻塞原因、用户可采取的下一步。

没有绑定项目、MCP 未连接或部分证据不可用时，应明确显示未知或不可用，仍可返回
能读取的信息。状态查询不得安装、修复、创建配置、绑定项目、恢复任务或自动审批；
不得为了获取状态触发会写文件的探测。历史通过结果必须标明时间与适用提交，不能
冒充当前环境或当前提交已验证。

### FR-018 兼容、命令与 Skill 一致性

旧 `$sg-codex-setup` 必须保留，用于承接历史的环境修复或项目准备请求。入口解释
一次当前职责，再转到相应新入口，不重复执行准备流程；意图不明时仅做必要澄清。
该别名不得接受业务开发或隐式批准安装。

若宿主展示命令菜单，命令和对应 Skill 必须共享相同调度、权限、参数和状态处理，
不得形成两套工作流。内部 MCP 工具仍是执行与状态来源，无需作为普通用户命令记忆。
更新 Skill、项目内副本、入口元数据、onboardingSkill 和使用文档时必须保持一致。
底层 `sg_project_setup` 继续表示项目 Agent/Skill/MCP 配置，不应被描述为完整环境安装。

### FR-019 任务控制、验收与诊断归属

继续、暂停、取消归入 `$sg-codex-change`，作用于已识别的当前任务，不另设任务控制
Skill。多个任务存在时必须明确目标；继续从已记录检查点恢复，不新建重复 Change，
不跳过审批或环境门禁；取消保留已有代码、分支和证据。

需求开发中的验收和交付继续沿用 H3 与既有交付流程，推送仍需用户明确授权。
诊断与修复归入 `$sg-codex-env`；帮助归入 `$sg-codex`；状态入口只展示上述动作的
可用性，不执行动作。不新增独立的控制、交付、诊断或帮助 Skill。

## 7. 非功能需求

### NFR-001 安全

- 日志和 JSON 报告不得包含令牌、密码、代理凭据或 Codex 登录内容。
- 不得关闭 TLS 校验、系统防护或 PowerShell 安全策略。
- 不得执行来源不明的远程脚本管道。
- 路径、URL 和命令参数必须按参数数组或安全引用传递，避免命令注入。

### NFR-002 可靠性

- 所有网络、发现、安装和验证步骤必须有超时。
- 网络失败、权限不足、版本不符、校验失败和验证失败必须可区分。
- 任一必需组件失败时整体结果必须失败，不能被其他成功项掩盖。

### NFR-003 可维护性

- Windows 与 Linux 入口共享核心规则，避免两套版本门槛漂移。
- 组件版本、镜像和 checksum 元数据集中管理并可测试。
- 工具发现必须复用 `src/codex/core/` 中已有的跨平台能力。
- 不引入版本命名的兼容目录或旧宿主入口。

### NFR-004 性能与资源

- 已就绪环境的检查和第二次执行不能进行无意义下载。
- 发现过程不得无界遍历文件系统。
- 安装产生的临时文件必须在当前运行结束后清理，不能持续占用系统临时目录。

### NFR-005 可审计性

通过状态必须能追溯到真实命令证据。单元测试、模拟平台、静态分析或文件生成只能作为
实现验证，不能替代 Windows/Linux 实机验收。

### NFR-006 入口一致性

各入口必须复用现有 MCP 状态与执行能力，不能通过拆分 Skill 新建第二份项目或任务
状态源。环境、项目和任务的状态分别可见，所有用户可见说明与失败提示使用中文。

## 8. 验收标准

### AC-001 Windows 首次安装

在真实受支持 Windows 环境中进入 Codex，通过会话内入口从缺失或隔离环境开始，
按选定技术栈预检、复用、补齐并真实验证，随后放行后续工作流。

### AC-002 Ubuntu 首次安装

在用户指定的 VMware Workstation Ubuntu 26.04.1 x64 虚拟机中进入 Codex，
完成同样的会话内预检、复用、按需安装、验证和放行流程，并保留真实证据。

### AC-003 幂等重跑

Windows 与 Ubuntu 首次成功后立即再次执行同一命令。第二次运行不得重复下载或追加
配置，所有组件报告为复用或已就绪。

### AC-004 Codex 与 SpecGate

在两平台分别执行真实 Codex 启动、能力探测、SpecGate MCP/插件 smoke。若认证需要
人工完成，证据必须明确区分认证前与认证后结果，不能把待认证标为通过。

### AC-005 Java 矩阵

在两平台分别使用 JDK 8、17、21 执行对应受支持项目的 Maven 编译和测试。每个预设
必须记录实际 JDK 与 Maven 路径、版本、命令和退出码。

### AC-006 Vue/React 矩阵

在两平台分别生成 Vue 和 React 项目，按锁文件安装依赖，并执行测试、lint、格式检查
和生产构建。所有受支持的 JDK × 前端组合必须使用同一仓库提交形成证据。

### AC-007 镜像与切换

在不修改用户全局 npm/Maven 配置的前提下，证明国内镜像实际被当前安装/构建使用；
再验证显式官方源或自定义源参数不会与默认配置混淆。

### AC-008 失败与清理

至少验证下载失败、checksum 不匹配、权限不足和验证失败。每种失败必须返回非零退出码、
报告明确原因、不破坏已有工具链，并清理归属于本次运行的临时目录。

### AC-009 仓库质量门禁

实现完成后执行相关聚焦测试，以及 `npm test`、`npm run lint`、
`npm run format:check`、`npm run pack:check` 和真实插件 smoke。任一未执行项必须明确
记录为未执行。

### AC-010 按需安装与工作流阻塞

两平台分别选择 Java 17 + Vue，证明未选择的 JDK 8、21 缺失时不会被安装或阻塞流程。
切换到 Java 8 项目后只补齐所需缺项，复用已有 Node/npm、Maven。安装失败、取消或
必要验证未执行时，后续生成、实现和交付必须被阻塞；重新验证成功后才可继续。

### AC-011 会话内启动前置依赖恢复

Node 缺失或版本不符时，在 Codex 会话内由已加载的 Skill 协调预检、补齐和真实验证，
然后重连 MCP；只读检查不得触发 Node 安装。无法恢复时必须阻塞并报告原因。
在两平台均验证用户无需切换到会话外运行安装脚本，也不存在独立全量安装入口。
普通插件用户不得被要求安装插件源码仓库的开发依赖。

### AC-012 入口职责与只读状态

逐一验证五个目标入口的路由和停止条件：环境准备不自动初始化；项目准备不自行
开始开发；需求开发覆盖新增、修改与修复；导航正确转接。状态查询在未绑定项目、
环境缺失、项目未就绪、任务等待审批和执行失败时均能报告事实，且查询前后文件、
配置、任务状态不变。查询状态不得触发环境安装或任务恢复。

### AC-013 衔接与旧入口兼容

验证新建、接入、已生成未验证及已就绪项目的正确分流，不重复填写技术栈、不重复
初始化或安装。旧 `$sg-codex-setup` 的环境请求与项目请求分别转到正确入口，且
只执行一次；不明确请求只澄清。Skill、项目副本、入口元数据与文档一致。

### AC-014 任务控制与交付边界

验证对明确任务的暂停、继续和取消，证明恢复使用原检查点、取消保留证据、审批未
完成时不能继续越过门禁。状态入口只报告控制选项；验收交付仍需真实审批，未授权
推送不得执行。命令菜单若存在，验证其与对应 Skill 使用相同执行路径。

## 9. 验收证据规则

### 本轮运行拓扑修订

用户确认采用“宿主 Codex 调度 Ubuntu 执行命令”，沿用 VMware Guest Tools。
Windows 负责 Codex 认证和会话，Linux 负责真实工具链、SG/MCP、构建、测试与应用运行。
不新增网络监听、登录代理或认证缓存迁移；这不是虚拟机 CLI 已复用宿主登录缓存。
Linux 命令证据必须记录实际 `platform=linux` 和虚拟机路径，不能用 Windows 运行结果替代。

本轮不再等待 Ubuntu 独立登录；AC-002、AC-004 中要求 Ubuntu 本地 Codex 会话/认证的部分
明确暂不执行，不标记通过。AC-011、AC-012 至 AC-014 的宿主交互、原生审批与子代理验收
仍须独立证据，其他原有验收条件保持不变。

Windows 与 Ubuntu 证据必须来自同一 Git 提交，并记录：

- 实际操作系统版本、架构和虚拟化信息；
- 完整命令、退出码、开始和结束时间；
- 工具版本与解析后的实际路径；
- 国内镜像与 checksum 结果；
- Java/Vue/React 矩阵结果；
- 第二次运行结果；
- 临时目录清理检查；
- 未执行检查及原因。

只有真实运行通过的项目可以标记为 `passed`。Windows 或 Linux 任一平台缺失时，
整体状态必须保持 `pending` 或 `failed`。

## 10. 实施门禁

本文件确认的是需求范围，不代表现有实现已符合要求，也不代表已经授权执行安装。
实施前必须审计并保留工作区已有未提交内容；实施完成后，必须先提交文档和代码审阅，
再在获得运行授权的真实 Windows 与 VMware Ubuntu 环境中执行可能产生系统变更的验收。
