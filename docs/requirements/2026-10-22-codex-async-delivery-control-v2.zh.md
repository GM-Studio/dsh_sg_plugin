# Codex 异步交付、Web 管理台与飞书决策控制需求

- 状态：已批准实施；交付仍需用户最终确认
- 日期：2026-10-22
- 版本：0.2
- 适用宿主：Codex
- 首版场景：一人团队管理多个 Java/Vue 项目的异步交付
- 前置需求：
  - `docs/requirements/2026-10-22-codex-delivery-mvp-requirements-analysis.zh.md`
  - `docs/requirements/2026-10-22-codex-async-delivery-control.zh.md`
- 产品补充：
  - Web 管理端需要提供详细的运行监控和受控管理能力。
  - 消息触达和远程决策首版使用飞书。
  - 系统只在关键节点和关键状态请求人工处理，其余工作由 AI 自主推进。
  - 人工处理异步进行，系统不得通过页面轮询、聊天等待或长时间占用执行资源来
    换取人工输入。

## 审批与变更边界

本文档只定义产品行为、范围、约束和验收口径，不授权进入设计、任务拆分或代码
实现。

在用户明确审批本文档之前：

- 不修改 `src/`、`test/`、技能、插件清单或项目模板。
- 不创建实现分支，不提交，不推送。
- 不把本文档中的推荐方案视为已经批准的技术设计。
- 现有交付保证需求继续有效；本文档与其冲突时，以更严格的证据、审批和
  安全要求为准。

本文档经用户审批后，拟替代
`docs/requirements/2026-10-22-codex-async-delivery-control.zh.md` 中关于异步
执行、Web 控制台、消息触达和远程决策的产品行为，但不替代现有项目基线、
ChangeContract、Evidence、VerificationAssessment、H1/H3、DeliveryRecord 和
增量再交付需求。

## 1. 反向复述与澄清

### 1.1 对用户意图的复述

我的理解是：

1. Web 管理端不是简单状态页，而是用户的全局运营面板。用户应当能够看见项目、
   WorkItem、执行 Run、AI 角色、当前阶段、关键命令、心跳、证据、风险、待办、
   通知状态、Decision 和交付记录的完整业务脉络。
2. Web 管理端还应当支持受控管理，包括暂停、恢复、取消、重试、要求修改、
   查看证据、重新发送通知和处理异常；但不得变成远程 shell、Web IDE 或任意
   命令控制台。
3. 飞书是首版主要注意力入口。正常执行不通知；只有到达 H1、H3、必须补充信息、
   无法自动恢复的阻塞、执行中断、超预算和最终结果等关键节点，才主动通知。
4. 人工处理不应持有当前执行线程。任务到达人工门禁时保存稳定检查点并转入
   `WAITING_FOR_USER`；人工完成后系统自动恢复，而不是让 Agent、MCP 调用或
   Web 请求一直等待。
5. AI 负责需求分析、计划、测试设计、实现、验证、修复、Review 和交付准备。
   人工主要负责业务范围判断、高风险确认和最终验收，不应手工串联内部 Agent
   或阶段。
6. 用户可以在飞书完成大部分轻量判断，也可以从通知进入 Web 查看完整上下文。
   Web 和飞书必须展示同一业务事实。
7. 系统的目标是保护注意力，不是减少所有通知。真正需要人的节点必须可靠通知，
   不需要人的节点默认安静。

### 1.2 必须防止的错误理解

- “剩余都交给 AI”不等于 AI 可以替用户批准 H1、H3、推送、取消或客户验收。
- “飞书决策”不等于信任消息文字、昵称或卡片中的用户字段。所有动作必须回到
  服务端授权和权威状态。
- “Web 详细监控”不等于实时展示所有思维过程、工具原始输出或完整源码 diff。
  监控的是可解释、可审计、对运营有价值的执行事实。
- “异步”不等于把同步等待从 Codex 页面搬到 Web 页面。人工未处理时，系统必须
  释放执行资源并保持显式等待状态。
- “减少人工介入”不等于隐藏异常。无法安全自动恢复时必须主动打断。

## 2. 产品定位

### 2.1 一句话定位

> AI 持续交付，关键决策异步找到人，Web 管理全局，人工完成后自动续跑。

### 2.2 产品职责

SpecGate 负责：

- 持久化 WorkItem、ExecutionRun、AttentionRequest、Decision 和 Outcome。
- 驱动 AI 在证据和风险约束下自主推进交付。
- 在必要边界停止、通知、等待和恢复。
- 提供 Web 监控、诊断和受控管理能力。
- 通过飞书传递注意力请求并接收经服务端验证的 Decision。
- 把技术结果转换为可解释的业务结果和交付状态。
- 保留完整审计、恢复和失效关系。

Codex 负责：

- 理解代码和业务目标。
- 制定计划、设计测试、修改代码和运行命令。
- 使用宿主允许的项目 Agent 完成实现、验证和 Review。
- 通过持久化 session 在 Decision 后继续工作。

飞书负责：

- 主动触达。
- 展示最小可行动摘要。
- 提供安全入口和受支持的轻量动作。
- 反馈通知是否送达以及是否已处理。

Web 管理端负责：

- 展示全局和详细上下文。
- 提供复杂证据查看、故障诊断和受控操作。
- 展示通知、Decision 和交付的完整链路。

以上界面均不是第二业务真相。权威事实由 SpecGate 的持久状态、不可变证据和
审计链决定。

### 2.3 产品不是

- 不是 Web IDE。
- 不是远程桌面或远程 shell。
- 不是只把 Codex 日志搬到浏览器的监控墙。
- 不是通用 Agent 集群管理平台。
- 不是完整企业项目组合管理平台。
- 不是多租户 SaaS。
- 不是用“同意”消息替代 H1/H3 和证据门禁的自动化工具。
- 不是必须持续刷新的同步工作台。

## 3. 第一性原理与不可破坏的不变量

1. 执行时间与人的在线时间可以分离，因此执行监督器必须独立于 Web 页面、
   飞书连接和原 Codex 会话。
2. 注意力必须稀缺。没有明确人工动作的事件默认不主动推送。
3. 人工判断只应发生在结果会变化的边界，而不是每个内部阶段。
4. 到达人工门禁时必须释放执行资源，不能通过长时间打开的调用等待用户。
5. 人工作出决定后必须自动续跑，不能要求用户手工启动下一阶段。
6. 任何 Decision 都必须绑定确定 WorkItem、状态版本、目标 artifact 和操作者。
7. 飞书、Web 和 Codex 只能消费同一权威状态，不能各自维护可见状态。
8. 完成、验证、发布、客户接受和部署必须是不同事实。
9. 通过和可交付必须来自真实证据，模型摘要不能成为事实来源。
10. 通知允许至少一次投递，但业务副作用必须恰好一次。
11. 安全失败必须 fail closed，不能用降低审批强度换取流程连续性。
12. 无人值守执行必须有时间、token、重试和磁盘预算。
13. 宿主离线、执行中断和通知失败必须显式可见，不得伪装为继续运行。
14. Web 可以详细，飞书必须简洁。详细管理不能重新制造持续盯守。

## 4. 角色与权限

### 4.1 Owner

项目负责人。可以：

- 创建、暂停、恢复、取消和重试 WorkItem。
- 提交修改要求。
- 处理 H1 和 H3。
- 查看完整内部证据。
- 发起交付和确认客户交付动作。
- 管理项目和通知规则。

### 4.2 Approver

特定门禁的责任人。首版允许 Owner 兼任 Approver，但审批必须由服务端确认其
身份、权限、认证强度、目标和版本。

### 4.3 Customer or Stakeholder

只查看客户可见结果并完成客户验收的人。不得默认看到：

- 本机路径和内部工作树。
- 原始日志和内部 Agent 推理。
- 未脱敏风险、凭据或客户数据。
- 内部 Review 内容。

### 4.4 Observer

只读用户。首版可以不开放管理 Observer 的 UI，但数据模型和 Web 投影不得默认
所有查看者都有管理权限。

### 4.5 AI Worker

执行分析和交付工作的 Codex 运行实例。AI Worker：

- 可以提出审批对象和 Decision 建议。
- 可以在授权范围内自主修复和重试。
- 不得产生可信用户身份。
- 不得自行消费 H1、H3、推送、取消或客户验收 Decision。
- 不得绕过不可执行、未验证或高风险状态。

## 5. 核心业务对象

### 5.1 WorkItem

WorkItem 是用户真正关心的一次异步交付工作。

必须包含：

- `workItemId`。
- 项目和可选 Change 引用。
- 业务目标和当前版本。
- 用户可见主状态。
- 当前执行 Run。
- 当前 AttentionRequest。
- 最新 Outcome。
- 最近交付和父交付。
- 创建、更新、最近心跳和完成时间。
- 人工介入次数和已消耗运行预算。

WorkItem 不是 Codex 对话、Agent thread、worktree 或单个命令。

### 5.2 ExecutionRun

ExecutionRun 是一次实际执行尝试。

必须包含：

- 使用的 Codex session、thread 或等价执行上下文。
- 宿主、项目和工作树标识。
- 开始、心跳和结束时间。
- `RUNNING`、`WAITING`、`SUCCEEDED`、`FAILED`、`INTERRUPTED` 或
  `CANCELLED` 状态。
- 当前内部阶段和当前关键命令摘要。
- 重试次数、超时、预算和中断原因。
- 产生的 commit、证据和恢复检查点。

### 5.3 AttentionRequest

AttentionRequest 是请求用户注意力的唯一业务对象。

必须包含：

- 为什么需要用户。
- 用户需要决定什么。
- 可用动作及每个动作的业务后果。
- 相关 AC、Outcome、风险和证据摘要。
- Decision 绑定所需的版本和 artifact hash。
- 创建、失效和提醒时间。
- 用户不处理时的系统行为。
- 推荐动作，但推荐不得代替用户决定。

同一业务问题使用稳定 `attentionKey`。相关对象变化时产生新 revision，旧 revision
必须进入 `SUPERSEDED` 或 `EXPIRED`。

### 5.4 Decision

Decision 是授权用户对 AttentionRequest 或明确 artifact 完成的业务决定。

首版动作：

- `approve`。
- `request_changes`。
- `answer`。
- `pause`。
- `resume`。
- `retry`。
- `cancel`。
- `accept_delivery`。

Decision 必须绑定：

- 操作者业务身份和认证强度。
- 来源渠道。
- WorkItem、ExecutionRun、AttentionRequest revision。
- WorkItem 状态版本。
- 目标和 artifact hash。
- 幂等键、签发时间、消费时间和审计记录。

### 5.5 Outcome

Outcome 是从服务端事实生成的业务结果，不是模型自由文本。

必须包含：

- 做成了什么。
- 哪些 AC 通过、失败或未验证。
- 改动范围。
- 已知问题和剩余风险。
- 当前能否交付。
- 下一步责任人。
- 证据、commit、环境和 assessment 引用。

模型可以渲染文字，但每个关键结论必须引用结构化事实。模型摘要与事实冲突时，
以事实为准并标记冲突。

### 5.6 WebProjection

WebProjection 是权威状态的可重建展示投影。它必须能够重建以下视图：

- 项目组合。
- WorkItem 详情。
- ExecutionRun 和 AI 角色状态。
- AttentionRequest 和 Decision 历史。
- Evidence 和 VerificationAssessment。
- DeliveryRecord 和交付包。
- 通知投递与渠道健康。

投影可以缓存，但不得成为不可恢复的唯一状态。

## 6. 状态模型

### 6.1 不采用单体八状态

业务里程碑、执行状态、宿主健康和注意力状态必须正交保存。不能通过一个状态枚举
同时表达所有维度，否则会出现“证据已就绪但执行失败”“已交付但未验收”等无法表达
或互相矛盾的组合。

### 6.2 业务里程碑

| 状态                 | 含义                                |
| -------------------- | ----------------------------------- |
| `PROJECT_READY`      | 项目 Profile 和 Baseline 可用       |
| `CONTRACT_CONFIRMED` | H1 已通过，ChangeContract 已冻结    |
| `EVIDENCE_READY`     | 当前提交的验证结果和证据足够进入 H3 |
| `RELEASE_APPROVED`   | H3 已通过，允许生成正式交付         |
| `DELIVERY_ACCEPTED`  | 客户验收或正式交付接受已完成        |

### 6.3 执行状态

| 状态               | 含义                         | 是否占用 AI 执行资源 |
| ------------------ | ---------------------------- | -------------------- |
| `QUEUED`           | 已持久化，等待租约或前置条件 | 否                   |
| `RUNNING`          | AI 或验证命令正在执行        | 是                   |
| `WAITING_FOR_USER` | 到达人工门禁，已释放执行资源 | 否                   |
| `PAUSED`           | 用户或系统主动暂停           | 否                   |
| `BLOCKED`          | 无法继续但尚未确定恢复动作   | 否                   |
| `FAILED`           | 执行失败且需要人工选择       | 否                   |
| `COMPLETED`        | 当前 WorkItem 成功结束       | 否                   |
| `CANCELLED`        | 用户取消                     | 否                   |

`WAITING_FOR_USER`、`BLOCKED`、`PAUSED` 不得继续持有 Codex session 的同步工具
调用，也不得持续占用项目执行租约。

### 6.4 宿主健康

- `ONLINE`：supervisor 和 WorkItem 执行上下文可用。
- `OFFLINE`：宿主已失去心跳，不能执行危险动作。
- `INTERRUPTED`：宿主恢复后发现上次 Run 异常终止，需要重新校验。

视觉上不得在 `OFFLINE` 时显示 `RUNNING`。

### 6.5 注意力状态

- `NONE`。
- `OPEN`。
- `DELIVERED`。
- `REMINDED`。
- `DECIDED`。
- `EXPIRED`。
- `SUPERSEDED`。

### 6.6 用户可见主状态

Web 和飞书显示一个由上述维度投影出的主状态：

- 排队中。
- AI 执行中。
- 需要你决定。
- 已暂停。
- 已阻塞。
- 执行失败。
- 待验收。
- 已完成。
- 已取消。
- 宿主离线。

内部 `TEST_DESIGN`、`INTEGRATING`、`REVIEWING` 等阶段可作为二级信息展示，不能
成为普通用户必须理解的主状态。

## 7. 人工介入与 AI 自主边界

### 7.1 AI 可以自主完成

在已确认契约、现有权限和预算内，AI 可以自主完成：

- 影响分析、方案分析和风险建议。
- 任务规划和测试设计。
- 创建和清理隔离工作树。
- 前端、后端、测试、格式化和 Review 角色的执行与重试。
- 运行构建、测试、HTTP、浏览器和运行时验证。
- 根据结构化缺陷执行有限次数修复。
- 生成证据、Outcome 草稿和交付包草稿。
- 在无需新业务判断的低风险失败中自动重试。

这些内部动作不应生成飞书进度通知，也不需要用户手工串联。

### 7.2 必须由人处理

下列边界必须进入人工处理：

- 需求范围、非目标或验收标准需要确认，即 H1。
- 存在会实质改变结果的歧义，AI 不能自行假设。
- 发生无法在预算内自动恢复的失败、冲突或环境缺失。
- 需要高风险例外或改变已冻结范围。
- H3 发布审批。
- 远程推送。
- 取消、终止或可能造成外部副作用的破坏性动作。
- 客户交付验收。
- 运行预算需要提高。

### 7.3 自动与人工决策矩阵

| 节点               | AI             | 人工 | 默认通知           |
| ------------------ | -------------- | ---- | ------------------ |
| WorkItem 排队      | 持久化并开始   | 否   | 否                 |
| 需求分析和方案建议 | 自主完成       | 否   | 否                 |
| H1 契约确认        | 准备审批包     | 是   | 是                 |
| 测试设计和实现     | 自主完成       | 否   | 否                 |
| 自动验证通过       | 记录证据       | 否   | 否                 |
| 可自动修复失败     | 有限重试       | 否   | 否，超过阈值才通知 |
| 不可恢复失败       | 整理影响和建议 | 是   | 是                 |
| H3 发布审批        | 准备交付包     | 是   | 是                 |
| 推送               | 等待显式决定   | 是   | 是                 |
| 客户验收           | 准备客户视图   | 是   | 是                 |
| 完成且无需后续动作 | 归档 Outcome   | 否   | 一次摘要           |

## 8. Web 管理端需求

### 8.1 定位

Web 是完整上下文、监控、诊断和受控管理中心，不是日常盯守页面。

Web 需要详细，但信息必须分层：

- 第一层：我现在要做什么，以及哪些 WorkItem 有异常。
- 第二层：WorkItem 结果、证据、风险和下一步。
- 第三层：ExecutionRun、AI 角色、命令、日志、worktree 和审计。

### 8.2 注意力首页

首页第一屏必须显示：

- 等待当前用户处理的 AttentionRequest。
- 按风险、阻塞时长和截止时间排序的待办。
- 离线、中断和通知失败等异常。
- 最近一次重要结果。

普通运行日志、Agent 自评和阶段启动不得占据首页主要位置。

### 8.3 全局项目监控

必须提供跨项目视图，至少展示：

- 项目就绪状态和 Baseline 状态。
- 当前活动 Change。
- WorkItem 队列和每个项目允许的单活动 Change 占用情况。
- 执行中、等待人工、阻塞、失败、暂停和完成的 WorkItem。
- 宿主在线状态和最近心跳。
- 最近通知失败和未送达 Decision。
- 最近交付和待验收交付。

首版不要求同项目并行多个 Change，但队列和跨项目监控必须存在。

### 8.4 WorkItem 详情

必须展示：

- 目标和当前版本。
- 用户可见主状态和业务里程碑。
- 当前责任人：AI、用户、客户或系统。
- 当前 AttentionRequest 和下一步。
- 最新 Outcome。
- 人工介入次数、已运行时长和预算使用。
- 历史 ExecutionRun。
- 最近交付和父交付。
- 暂停、恢复、取消、重试和要求修改等允许动作。

### 8.5 ExecutionRun 与 AI 监控

管理员必须能够查看：

- 当前 Codex session/thread 标识，但普通用户视图默认折叠。
- 当前内部阶段、开始时间、最近心跳和已运行时长。
- 当前 AI 角色和角色状态。
- 当前关键命令的业务描述、退出码、耗时和脱敏后的尾部输出。
- 工作树、分支、目标 commit 和集成关系。
- 重试次数、失败分类和剩余预算。
- Run 在等待人工前的稳定检查点。
- 中断、恢复和失联原因。

不要求展示模型内部思维过程。原始日志可以按权限查看或下载，但不得成为首页主
信息，也不得包含明文凭据。

### 8.6 证据和 Report

必须展示：

- AC 与当前 Outcome 的映射。
- Evidence 的类型、命令、commit、环境、状态和产物。
- skipped、not-run、timeout、cancelled、flaky 和 retry 记录。
- VerificationAssessment 的独立性、风险和最终判断。
- H1/H3 artifact hash 和审批记录。
- DeliveryRecord、内部证据包和客户包。

关键结论必须可以下钻到对应证据，不得只展示模型摘要。

### 8.7 Decision 和跨端一致性

必须展示：

- AttentionRequest 的 revision 和当前状态。
- 通知发送、失败、提醒和处理状态。
- Decision 的来源渠道、认证强度、操作者、时间和结果。
- 旧 revision、过期动作和重复回调记录。
- 一个渠道完成后其他渠道的已处理摘要。

从 Web 做 Decision 与从飞书做 Decision 必须经过同一服务端校验和业务路径。

### 8.8 通知和集成健康

必须展示：

- 飞书应用和机器人连接状态。
- 用户身份映射状态。
- 最近发送成功率、失败原因和重试队列。
- 安全链接和认证配置状态。
- 发送测试通知的能力。
- 某个渠道故障是否阻塞执行；正常实现必须显示“不阻塞”。

### 8.9 受控管理动作

Web 首版必须支持：

- 暂停和恢复。
- 取消。
- 重试当前失败。
- 要求修改。
- 重新发送当前通知。
- 查看或复制安全链接。
- 处理离线、中断和需要核对的 Run。
- 查看完整审计。

Web 不得提供：

- 任意 shell。
- 任意文件写入。
- 任意 MCP 方法调用。
- 任意修改固定 commit 或证据。
- 绕过 H1/H3 的状态编辑。

高风险动作必须经过与飞书相同的服务端授权和版本校验。

## 9. 飞书消息与决策控制

### 9.1 渠道定位

飞书是一人团队首版的主要注意力入口，不是业务状态数据库。

飞书消息默认只承担：

- 告诉用户现在为什么需要他。
- 给出业务摘要、风险和动作后果。
- 提供认证决策入口。
- 在动作完成后更新原消息。

### 9.2 通知触发

默认通知：

- H1 待确认。
- 必须补充信息。
- H3 待审批。
- 不可恢复的阻塞。
- 执行失败、宿主机离线或执行中断。
- 运行预算耗尽或需要提高。
- 待客户验收。
- 最终完成或取消摘要。

默认不通知：

- 已接收并开始执行。
- 普通阶段切换。
- 单个 Agent 启动或完成。
- 普通测试通过。
- 普通日志更新。
- AI 自评。
- 可自动处理且未超过阈值的单次失败。

### 9.3 通知内容

首屏必须回答：

1. 哪个项目和 WorkItem。
2. 当前发生了什么。
3. 为什么需要用户。
4. 有哪些可选动作。
5. 每个动作会导致什么。
6. 风险和已知问题是什么。
7. 动作何时失效。
8. 不处理时系统会怎样。

推荐格式：

```text
CRM 导出修复：需要你的审批

验证已通过 4/4 个验收标准。
改动：后端导出逻辑、前端文件名处理。
风险：低。
下一步：确认是否允许进入发布交付。

[查看完整结果] [安全检查并批准] [要求修改]
```

### 9.4 飞书动作安全

- 飞书消息文字、昵称、群成员字段和卡片 submit 内容不得直接作为可信身份。
- 所有动作必须调用服务端 Decision API。
- 服务端必须通过受验证的飞书应用事件或映射身份确认操作者。
- H1、H3、推送、取消和客户验收必须使用与普通查看不同的升级认证。
- 安全链接必须短期、单次或可撤销，并绑定具体 Decision 上下文。
- 过期、已消费或 artifact 已变化的链接必须拒绝并显示最新状态。
- 群机器人只可通知时，不得显示为可审批入口。

### 9.5 合并、提醒与静音

- 同一 WorkItem、同一 `attentionKey` 的重复事件必须合并。
- 普通非关键事件可以在默认 5 分钟窗口内合并。
- H1/H3、阻塞、离线和高风险事件仍只发送一个带 revision 的通知，不重复制造
  多个待办。
- 未处理的 H1/H3 可以按策略提醒，但提醒必须引用同一 revision，不能生成新 Decision。
- 高优先级阻塞、离线和高风险审批可以绕过项目静音。
- 静音只影响触达，不得改变业务状态或自动批准。

### 9.6 不处理时的行为

- 系统默认保持 `WAITING_FOR_USER`，不自动批准。
- 不得因为等待用户而占用 AI 执行租约。
- Notification revision 到期后标记 `EXPIRED`，但 WorkItem 保留明确阻塞原因。
- 用户重新打开页面或主动查询时，可以创建新的 AttentionRequest revision。
- 用户取消或关闭 WorkItem 必须通过显式 Decision。

## 10. 异步执行监督

### 10.1 独立 Supervisor

系统必须有一个独立于 MCP stdio 会话、Web 请求和飞书连接的执行监督器。

Supervisor 负责：

- 领取 WorkItem 执行租约。
- 启动或恢复 Codex execution。
- 维护 heartbeat 和预算。
- 将 AI 输出转换为结构化阶段和证据。
- 在人工门禁前保存稳定检查点。
- 释放执行资源并等待 Decision。
- Decision 后创建或恢复 ExecutionRun。
- 检测崩溃、失联和超时。

关闭 Web 页面、飞书客户端、MCP 客户端或原 Codex 会话不得杀死已持久化
WorkItem。

### 10.2 决策边界不得长时间同步等待

到达 H1、H3、补充信息或预算升级等人工门禁时：

```text
RUNNING
  -> persist checkpoint
  -> persist AttentionRequest
  -> WAITING_FOR_USER
  -> release execution lease
  -> notify Feishu/Web
```

人工完成后：

```text
Decision accepted
  -> validate version/artifact/identity
  -> QUEUED
  -> new or resumed ExecutionRun
  -> RUNNING
```

不得使用持续数小时的 MCP RPC、HTTP 连接、WebSocket 连接或浏览器轮询等待人的
决定。

### 10.3 心跳和离线

默认建议：

- 每 15 秒写入一次 supervisor heartbeat。
- 45 秒无心跳标记为疑似失联。
- 90 秒无心跳进入 `OFFLINE` 或 `INTERRUPTED`。
- 上述阈值可配置，但产品必须显示当前实际配置。

恢复后必须重新校验：

- WorkItem 版本。
- 执行租约。
- 固定 commit 和工作树。
- 未消费 Decision。
- H1/H3 artifact 是否仍有效。
- 证据和环境指纹。

无法安全恢复时进入 `INTERRUPTED` 或 `BLOCKED`，不得伪造“从中断处完成”。

### 10.4 运行预算

每个 WorkItem 必须有可配置预算：

- 最大墙钟时间。
- 最大 token 或等价模型使用量。
- 最大工具调用或命令执行时间。
- 最大自动修复轮次。
- 最大通知和提醒次数。
- 最大磁盘或证据包大小。

达到软阈值时可在 Web 提示但不打断；达到硬阈值时进入 `WAITING_FOR_USER` 或
`PAUSED`。提高预算属于人工 Decision。

### 10.5 重试与副作用

- 重试必须有分类和上限。
- 创建 commit、创建 DeliveryRecord、发送通知、推送和消费 Decision 必须幂等。
- 进程崩溃后不得重复创建 Change、重复执行已完成验证或重复推送。
- 不确定外部副作用是否完成时，必须进入核对状态，不能自动认为失败或成功。

### 10.6 多项目执行

- 首版保持同一项目同一时间一个活动 Change。
- 不同项目可以有独立 WorkItem，但默认不使用复杂 DAG 或文件锁系统。
- 项目内的新 WorkItem 进入队列，不得静默并行影响同一工作区。
- Supervisor 必须记录项目租约、排队原因和开始顺序。

## 11. Outcome、交付和证据语义

### 11.1 Outcome 生成

Outcome 由结构化事实生成：

- ChangeContract。
- AC。
- ExecutionRun。
- Evidence。
- VerificationAssessment。
- Review 结果。
- 风险和未验证区域。
- DeliveryRecord。

模型可以生成面向用户的摘要，但不得新增无证据的完成、通过、可交付或已接受结论。

### 11.2 交付状态分离

以下状态必须分开：

- 技术验证完成。
- H3 发布审批完成。
- DeliveryRecord 和交付包已生成。
- 本地交付可用。
- 客户端已收到交付。
- 客户已接受交付。
- 远程推送完成。
- 生产部署状态。

H3 通过不得直接显示为“客户已接受”。

### 11.3 DeliveryRecord 完整性

正式 DeliveryRecord 必须引用：

- `verificationId` 和 VerificationAssessment hash。
- H3 approval hash 和 artifact hash。
- ChangeContract hash。
- 固定 commit、环境和 review evidence。
- AC 结果。
- 已知问题、未验证区域和开放风险。
- 内部包和客户包 hash。

DeliveryRecord 不得把所有已知问题固定为空。

### 11.4 客户视图

客户视图只展示：

- 已交付的业务范围。
- 已通过或未验证的业务 AC。
- 用户可理解的风险和已知问题。
- 升级、回滚和联系方式。

客户视图必须与同一 DeliveryRecord 和 commit 一致，默认隐藏内部路径、日志、
凭据、内部 Agent 内容和未脱敏敏感数据。

## 12. 功能需求

### 12.1 WorkItem 与执行

#### FR-001 持久化 WorkItem

系统 MUST 在页面、渠道和原 Codex 会话关闭后保留 WorkItem、当前版本、状态和
恢复所需引用。

#### FR-002 独立执行监督

系统 MUST 使用独立于 MCP stdio、Web 页面和飞书连接的 supervisor 推进 WorkItem。

#### FR-003 决策边界释放资源

系统 MUST 在进入 `WAITING_FOR_USER` 前保存检查点并释放执行租约，不得长时间
持有同步调用等待人工输入。

#### FR-004 单项目约束

系统 MUST 阻止同一项目同时存在相互影响的活动 Change；其他 WorkItem MUST 明确
排队。

#### FR-005 心跳和离线

系统 MUST 维护 ExecutionRun heartbeat，并在失联时进入显式的 `OFFLINE` 或
`INTERRUPTED` 状态。

#### FR-006 恢复

系统 MUST 在宿主重启后重新校验状态版本、租约、commit、审批、环境和工作树，
并安全恢复或终止 WorkItem。

#### FR-007 预算

系统 MUST 为无人值守执行设置时间、token、工具调用、修复轮次和磁盘预算。

#### FR-008 AI 自主边界

系统 MUST 让 AI 自主完成已授权范围内的工作，并 MUST 在 H1/H3、高风险例外、
推送、取消和客户验收等边界请求人工输入。

### 12.2 Web 管理端

#### FR-009 注意力首页

Web 首页 MUST 优先展示“等待当前用户处理”的事项和异常，而不是普通日志。

#### FR-010 跨项目监控

Web MUST 提供跨项目、工作项、执行 Run、队列、心跳、通知和交付的聚合视图。

#### FR-011 WorkItem 详情

Web MUST 展示 WorkItem 的目标、用户状态、业务里程碑、Outcome、风险、当前责任人、
下一步、预算和历史。

#### FR-012 执行监控

Web MUST 展示当前 ExecutionRun、AI 角色、内部阶段、关键命令、重试、工作树、
commit、心跳和恢复检查点。

#### FR-013 证据下钻

Web MUST 允许授权用户从 Outcome 下钻到 AC、Evidence、VerificationAssessment、
commit、H1/H3 和 DeliveryRecord。

#### FR-014 Decision 审计

Web MUST 展示 AttentionRequest、通知投递、Decision、失效、过期和重复请求。

#### FR-015 受控管理

Web MUST 支持暂停、恢复、取消、重试、要求修改、重发通知和查看安全链接，并
MUST NOT 提供任意 shell、文件写入或状态绕过。

#### FR-016 集成健康

Web MUST 展示飞书连接、身份映射、通知失败、重试队列和渠道是否阻塞执行。

### 12.3 飞书与注意力

#### FR-017 飞书首版

飞书 MUST 作为首版主要消息触达和轻量 Decision 入口。

#### FR-018 必要触达

系统 MUST 在 H1、H3、必要补充信息、不可恢复失败、离线、预算耗尽、待客户验收和
最终摘要时主动通知。

#### FR-019 默认安静

系统 MUST NOT 主动发送普通阶段、单角色启动、普通测试通过或常规进度通知。

#### FR-020 可行动通知

AttentionRequest MUST 包含原因、所需决定、动作后果、结果、证据入口、风险、
有效期和不处理的后果。

#### FR-021 合并与提醒

系统 MUST 按 `attentionKey` 合并重复事件，并 MUST 让提醒继续引用同一未处理
revision。

#### FR-022 原通知更新

Decision 在其他端完成、目标变化或请求过期后，系统 SHOULD 更新原飞书消息或发送
一次简短失效说明。

### 12.4 Decision 与安全

#### FR-023 结构化动作

系统 MUST 只接受预定义 Decision，不接受飞书自由文本作为 shell、文件或任意工具
调用。

#### FR-024 版本绑定

所有改变状态的 Decision MUST 使用服务端解析的当前版本，并以 CAS 拒绝旧动作。

#### FR-025 身份可信

系统 MUST 从已验证渠道事件或认证会话获得操作者身份，不得信任消息昵称、正文中的
`actor` 或客户端声称的角色。

#### FR-026 高风险认证

H1、H3、推送、取消和客户验收 MUST 使用高于普通查看的认证强度和确认语义。

#### FR-027 幂等

重复点击、消息重试、网络超时和平台重放 MUST NOT 产生重复 Decision、重复执行、
重复推送或重复交付。

#### FR-028 自动续跑

有效 Decision 完成后，系统 MUST 自动恢复或创建 ExecutionRun，不得要求用户手工
启动下一内部阶段。

#### FR-029 失效处理

过期、已消费或绑定旧 artifact 的 Decision MUST 被拒绝，并向用户显示最新状态和
重新获取动作的路径。

### 12.5 Outcome 和交付

#### FR-030 Outcome 事实来源

Outcome MUST 从服务端证据和状态生成，模型摘要不得替代事实。

#### FR-031 完成语义

系统 MUST 分开技术验证、H3 审批、交付包生成、客户接受、推送和部署。

#### FR-032 DeliveryRecord 关联

DeliveryRecord MUST 引用 VerificationAssessment、H3、固定 commit、证据、风险和
客户包 hash。

#### FR-033 客户安全

客户视图 MUST 默认隐藏内部路径、原始日志、凭据、内部 Agent 内容和未脱敏风险。

### 12.6 可观察性与恢复

#### FR-034 完整审计

系统 MUST 记录 WorkItem 创建、ExecutionRun、心跳、AttentionRequest、通知、
Decision、失效、失败、恢复和交付。

#### FR-035 运行时诊断

Web MUST 能区分执行存活、等待人工、暂停、阻塞、离线、失败、完成和取消。

#### FR-036 人工介入指标

系统 MUST 记录实际通知数、有效待办数、人工 Decision 次数、处理耗时、恢复操作
次数和预算使用。

## 13. 非功能需求

### NFR-001 注意力预算

- 没有可执行动作时不主动发送飞书通知。
- 同一业务问题不得在多个渠道重复要求回答。
- 普通 Change 的内部人工注意力请求默认不超过 2 个。
- 客户验收作为独立业务事件单独计量，不通过自动批准合并。

### NFR-002 可靠性

- 页面关闭、原 Codex 会话结束和飞书暂时离线不得丢失 WorkItem。
- 通知投递失败不得阻塞执行、证据保存或状态推进。
- 宿主崩溃必须在 90 秒内被识别为疑似或明确离线，具体阈值可配置。
- 所有副作用必须可幂等恢复。

### NFR-003 一致性

- Web、飞书和 Codex 对同一 AttentionRequest 使用同一 revision。
- Decision 在一个渠道完成后，其他渠道显示已处理或失效。
- 消息平台状态不能成为审批、验证或交付的权威记录。

### NFR-004 安全

- 默认不暴露公网管理端口；远程访问应通过受认证的安全入口或出站 Relay。
- 飞书凭据、模型凭据和项目密钥不得进入仓库或普通日志。
- 外部消息和附件按不可信输入处理。
- 无法完成认证或授权校验时 fail closed。

### NFR-005 性能

- 已持久化的关键事件 SHOULD 在 30 秒内完成首次飞书投递尝试。
- Web 查询本地权威状态 SHOULD 在 2 秒内返回第一屏。
- 有效 Decision 提交后 SHOULD 在 10 秒内进入恢复处理或给出明确失败原因。
- 普通执行日志不得同步阻塞通知和状态推进。

### NFR-006 可观察性

- 能区分 heartbeat 超时、进程退出、命令超时和逻辑阻塞。
- 能追踪 AttentionRequest 从创建到通知、Decision 和执行结果的全链路。
- 能识别重复、过期、旧版本和跨项目错误绑定。
- Web 能显示每个异常当前是否需要人以及下一步是什么。

### NFR-007 可恢复性

- 失败的 WorkItem 保留失败证据和恢复风险。
- 恢复后不得复用失效 H1、H3、证据或交付状态。
- 无法证明安全恢复时必须显式停止。

### NFR-008 可用性

- 飞书首屏必须能在窄屏上完成判断。
- Web 首页必须先回答“我需要做什么”，再允许查看技术细节。
- 用户不需要理解 Agent、worktree 或内部阶段代号就能处理普通审批。
- 技术细节可折叠，但不能被删除或不可审计。

### NFR-009 成本

- 每个 WorkItem 记录模型调用、工具调用、运行时长和可获得的费用指标。
- 达到软预算时在 Web 显示，达到硬预算时阻断并通知。
- 自动修复不得无限重试。

### NFR-010 兼容性

- 继续遵守现有 Java/Vue、ProjectProfile、Baseline、Evidence、H1/H3 和
  DeliveryRecord 语义。
- 不新增第二套交付记录或消息平台真相。
- 新增渠道不得复制 Decision、审批和交付逻辑。

### NFR-011 可维护性

- 执行监督、注意力策略、通知投递、身份认证和 Web 投影必须有清晰边界。
- 通知模板与业务判断分离。
- 业务事件类型不得绑定飞书事件名。

### NFR-012 数据保留

- 进行中 WorkItem、未消费 AttentionRequest 和相关审计不得因清理策略丢失。
- 已交付 DeliveryRecord、审批和客户接受记录长期保留。
- 原始日志可按大小和期限清理，但必须保留哈希、摘要和清理记录。

## 14. 核心验收场景

### AC-001 提交后离开

- GIVEN 用户提交一个需要持续执行的 WorkItem
- WHEN WorkItem 已持久化并开始执行
- THEN 用户可以关闭 Web、飞书和原 Codex 会话
- AND ExecutionRun 继续推进
- AND 系统不发送普通进度通知

### AC-002 H1 异步处理

- GIVEN WorkItem 到达 H1
- WHEN 审批包和 AttentionRequest 已持久化
- THEN Run 进入 `WAITING_FOR_USER` 并释放执行租约
- AND 飞书在默认阈值内发送一次通知
- WHEN 用户完成可信 H1 Decision
- THEN 系统自动恢复或新建 ExecutionRun
- AND 不需要用户启动内部下一阶段

### AC-003 AI 自主推进

- GIVEN H1 已通过且没有新阻塞
- WHEN AI 执行计划、测试、实现、验证和修复
- THEN 系统不因普通阶段切换打断用户
- AND 所有内部角色和证据自动串联

### AC-004 H3 与客户接受分离

- GIVEN 证据已通过且进入 H3
- WHEN 用户批准 H3 并生成 DeliveryRecord
- THEN 系统显示“已批准发布”或“待交付”
- AND 在客户接受前不得显示“客户已接受”

### AC-005 旧审批失效

- GIVEN 用户持有旧飞书卡片或安全链接
- WHEN artifact 或 WorkItem 版本已变化
- THEN 服务端拒绝旧 Decision
- AND 用户看到最新 revision 和重新处理入口

### AC-006 重复回调

- GIVEN 飞书重复发送同一动作回调
- WHEN 服务端重复收到请求
- THEN 只产生一次 Decision 和一次业务副作用
- AND 审计中记录重复请求

### AC-007 跨端一致

- GIVEN 同一 AttentionRequest 同时显示在 Web 和飞书
- WHEN 用户在一个端完成 Decision
- THEN 另一渠道显示已处理或失效
- AND 不能再次消费同一 Decision

### AC-008 通知失败隔离

- GIVEN 飞书服务不可用
- WHEN WorkItem 到达 H1/H3 或阻塞状态
- THEN 执行和证据保存不被阻塞
- AND Web 显示通知未送达和重试状态
- AND 通知恢复后可以重新投递

### AC-009 宿主离线

- GIVEN WorkItem 显示 AI 执行中
- WHEN supervisor heartbeat 超时
- THEN 状态变为疑似失联或离线
- AND Web 和飞书展示明确异常
- AND 危险 Decision 不得显示为成功

### AC-010 重启恢复

- GIVEN supervisor 或宿主在 `RUNNING` 状态重启
- WHEN WorkItem 被恢复
- THEN 系统重新校验租约、版本、commit、证据和审批
- AND 不重复已完成副作用
- AND 无法安全恢复时进入显式中断状态

### AC-011 详细 Web 监控

- GIVEN 一个 WorkItem 正在执行
- WHEN 管理员打开 Web 详情
- THEN 可以看到项目、WorkItem、Run、角色、阶段、关键命令、心跳、预算、commit、
  证据、风险和当前责任人
- AND 可以下钻到审计和相关 artifact
- AND 页面刷新或关闭不影响执行

### AC-012 受控管理

- GIVEN 管理员从 Web 暂停一个 WorkItem
- WHEN 系统完成暂停
- THEN 状态、Run 和租约一致更新
- AND 证据和工作树保留
- AND 恢复后从稳定检查点继续
- AND 页面不暴露任意 shell 或文件写入

### AC-013 运行预算

- GIVEN WorkItem 达到任务硬预算
- WHEN AI 仍需要继续执行
- THEN 系统停止继续消耗并进入 `WAITING_FOR_USER` 或 `PAUSED`
- AND 通知用户当前成果、已用预算和可选动作
- AND AI 不得自行提高预算

### AC-014 结果可信

- GIVEN 系统生成完成或可交付摘要
- WHEN 用户查看结论
- THEN 每个关键结论可映射到 Evidence 和固定 commit
- AND 模型摘要与证据冲突时以证据为准并标记冲突

### AC-015 客户视图

- GIVEN 客户访问交付摘要
- WHEN 客户查看结果
- THEN 只显示与 DeliveryRecord 一致的业务范围、AC、风险和回退信息
- AND 不显示内部路径、凭据、原始日志和内部 Agent 内容

### AC-016 多项目注意力

- GIVEN 多个项目存在 WorkItem
- WHEN 用户打开 Web 首页或飞书待办
- THEN 可以看到每个项目当前需要人的事项
- AND 同一项目仍遵守单活动 Change 约束
- AND 排队 WorkItem 不会静默创建冲突工作树

## 15. 指标与试点门槛

### 15.1 核心指标

- 提交后无需桌面值守的 WorkItem 比例。
- 每个普通 Change 的有效人工注意力请求数。
- 通知中真正需要行动的比例。
- 从 AttentionRequest 创建到用户 Decision 的时间。
- 需要打开 Web 才能完成普通决策的飞书通知比例。
- 过期、重复和错误绑定的 Decision 数量。
- 无真实证据的完成、可交付和客户接受数量。
- 宿主离线发现时间和恢复时间。
- 每个 WorkItem 的模型、工具、时长和存储成本。
- 用户从打开通知到完成判断的步骤数。

### 15.2 首轮试点建议门槛

- 普通 Change 内部人工注意力请求不超过 2 个。
- 常规执行阶段不发送飞书进度通知。
- 重复 Decision 和重复副作用为 0。
- 无真实证据的完成、可交付或客户接受为 0。
- 关闭 Web 和原 Codex 会话后 WorkItem 不丢失。
- 已持久化的关键注意力事件在正常网络下 30 秒内首次投递。
- 宿主失联在 90 秒内被识别。
- 至少一条完整流程从飞书 Decision 自动恢复并完成交付。
- 用户不需要手工创建新对话、新 Change 或串联内部 Agent。

### 15.3 停止扩张条件

出现以下任一情况，应停止增加渠道和页面，优先修复核心模型：

- 飞书通知数量增加但用户决策时间没有下降。
- 用户仍需持续打开 Web 查看进度。
- Decision 重复、旧动作误执行或跨项目误绑定。
- 页面或飞书状态长期不一致。
- 通知系统阻塞执行或证据保存。
- AI 在人工门禁上长时间占用执行资源。
- 无法识别宿主机失联或恢复后重复副作用。
- 用户仍需手工串联内部 Agent。

## 16. 交付切片

### S1：异步执行底座

- WorkItem、ExecutionRun、heartbeat、租约和恢复。
- 到达人工门禁后释放执行资源。
- 单项目单活动 Change 和跨项目排队。
- 运行预算和中断状态。

### S2：Web 监控与注意力首页

- 跨项目总览。
- 待办和异常首页。
- WorkItem、Run、角色、阶段和 commit 监控。
- Outcome、Evidence 和 Decision 基础视图。

### S3：飞书关键节点触达

- H1/H3、阻塞、离线、预算和完成通知。
- AttentionRequest revision、合并和安全链接。
- 身份映射、通知重试和渠道健康。

### S4：远程 Decision 与自动续跑

- H1/H3 审批。
- 暂停、恢复、重试、取消和要求修改。
- 版本绑定、幂等、过期和跨端同步。
- Decision 后自动恢复 Codex execution。

### S5：Web 受控管理与交付闭环

- 详细执行管理和异常处理。
- DeliveryRecord、H3 和客户交付视图分离。
- 客户验收、回执和客户可见 Outcome。

### S6：扩展能力

- 第二消息渠道。
- 邮件正式交付和 Feedback Inbox。
- 多设备、多宿主和远端执行环境。
- 团队角色和更复杂审批。

## 17. 明确非目标

- 不提供任意远程 shell。
- 不提供 Web IDE 或远程文件管理器。
- 不展示模型内部思维过程。
- 不把每段日志、每次工具调用和每个阶段变化推送飞书。
- 不允许 AI 自行批准 H1、H3、推送、取消或客户验收。
- 不在首版实现企业级多租户、复杂 RBAC 和项目组合管理。
- 不在首版实现任意项目并行 DAG 或复杂文件锁调度。
- 不以个人微信非官方自动化作为核心通道。
- 不在首版实现生产部署和生产数据库回滚。
- 不让 Web 或飞书成为第二套交付真相。

## 18. 推荐确认项

以下内容采用本文推荐值；用户审批时可以修改：

1. 首版消息和轻量决策入口固定为飞书。
2. H1 和 H3 是普通 Change 的内部人工门禁。
3. H3 通过后生成正式交付，但“客户已接受”必须单独记录。
4. 客户验收不计入普通 Change 的两个内部注意力请求。
5. 普通执行不通知，只在关键门禁、异常、预算和最终摘要时通知。
6. Web 首版同时包含详细监控和受控管理，但不提供任意命令入口。
7. 首版保持同一项目一个活动 Change，不同项目可排队。
8. 人工门禁默认等待 24 小时，期间可按策略提醒；到期后保留阻塞并生成新
   revision，不自动批准。
9. 宿主 heartbeat 默认 15 秒，45 秒疑似失联，90 秒进入离线或中断。
10. H1/H3、推送、取消和客户验收采用 Passkey/WebAuthn 或等效升级认证。

## 19. 最终完成定义

1. 用户提交 WorkItem 后可以关闭 Web、飞书和原 Codex 会话。
2. 独立 supervisor 继续执行，页面和渠道连接不影响 WorkItem。
3. AI 自动完成普通计划、测试、实现、验证、修复和交付准备。
4. 只在关键节点、关键状态和无法自动恢复的异常时请求人工处理。
5. 到达人工门禁时释放执行资源，不以长时间连接等待用户。
6. 飞书在关键节点自动触达，通知包含原因、结果、风险、动作和失效信息。
7. 用户可以通过飞书或 Web 完成经认证的 Decision。
8. Decision 绑定身份、版本和目标 artifact，过期和重复动作无法执行。
9. Decision 完成后系统自动恢复执行，不需要用户串联内部 Agent。
10. Web 可以详细查看项目、WorkItem、Run、角色、阶段、命令、证据、风险和交付。
11. Web 可以提供受控暂停、恢复、取消、重试、修改和通知管理。
12. 宿主离线、执行中断、通知失败和预算异常均显式可见。
13. 完成、验证、H3、交付、客户接受、推送和部署保持分离。
14. Outcome 和客户视图来自真实证据和 DeliveryRecord，不来自模型自述。
15. 普通 Change 的内部人工注意力请求不超过两个。
16. 重复 Decision、重复副作用和无证据完成均为零。
