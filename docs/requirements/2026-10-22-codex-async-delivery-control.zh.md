## 1. 问题定义

### 1.1 核心问题

Codex 能够持续执行分析、实现、测试、修复和交付准备，但当前使用方式仍然
要求用户留在电脑前等待执行结果。这种等待没有直接产生业务价值，也阻碍用户
在同一时间处理其他项目、客户沟通或其他工作。

真正需要解决的问题不是“如何让 Web 页面显示更多日志”，也不是“如何通过
聊天软件操纵开发机”，而是：

> 将 Codex 从需要人持续盯守的同步工具，转化为可托管的异步工作队列；只有
> 当人的判断会影响结果时，才获取人的注意力。

### 1.2 第一性原理

系统必须遵循以下事实：

1. 执行时间与人的在线时间可以分离。
2. 执行状态与人的注意力必须分离。
3. 内部流程复杂度不能转移给用户。
4. 只有需要人决策时，打断才具有价值。
5. 用户需要的是结果和可执行的下一步，不是 Agent 的工作过程。
6. 没有真实证据的“完成”不能视为完成。
7. 用户从任何入口做出的决定，都必须回到同一个权威工作状态。

### 1.3 产品机会

现有代码 Agent 产品通常强化三个方向：

- 更强的代码生成能力。
- 更完整的实时日志和工具调用展示。
- 更丰富的聊天交互。

一人团队真正缺少的是：

- 提交工作后可以安全离开电脑。
- 系统在没有人工操作时继续执行和恢复。
- 需要审批或修改时主动找到责任人。
- 责任人能通过手机快速查看上下文并做出决定。
- 决定之后系统自动继续，不需要人工串联内部 Agent。
- 最终只以经过证据验证的结果进入交付。

## 2. 产品定位

### 2.1 一句话定位

> 提交后就可以离开，只在需要你决定时找你。

### 2.2 产品职责

产品负责：

- 承载长期运行的 WorkItem。
- 维持执行状态、心跳和恢复能力。
- 将内部执行结果归纳为用户可判断的业务结果。
- 在需要人介入时创建 AttentionRequest。
- 通过 Web、手机和消息渠道传递 AttentionRequest。
- 接收授权用户从远方做出的 Decision。
- 将 Decision 绑定到正确的 WorkItem、版本和证据。
- 让执行自动继续，直到完成、阻塞、失败或取消。
- 将最终结果和交付物按角色可见性提供给相关人员。

Codex 继续负责：

- 理解和修改代码。
- 调用工具和运行命令。
- 使用宿主允许的子 Agent 完成实现、验证和 Review。

SpecGate 继续负责：

- 项目基线、ChangeContract 和验收标准。
- 真实证据、风险、审批和交付记录。
- 判断是否真的完成，是否可交付。

消息平台、Web 控制台和移动端只负责交互和触达，不成为新的业务真相。

### 2.3 产品不是

本产品不是：

- 通用聊天机器人。
- Web IDE。
- 远程桌面或远程 shell。
- 通用 Agent 调度平台。
- 完整企业项目组合管理平台。
- 多租户 SaaS 交付平台。
- 仅用于展示 Codex 执行日志的监控面板。
- 用一条“同意”消息代替证据和审批门禁的自动化工具。

## 3. 目标与非目标

### 3.1 用户目标

1. 用户提交任务后可以离开电脑，不需要持续观察执行过程。
2. 系统只在需要审批、修改、补充信息或处理失败时通知用户。
3. 用户收到通知后，不阅读大段日志也能判断当前结果和所需动作。
4. 用户可以通过 Web、手机或消息入口完成同一项决策。
5. 用户可以在不操作开发机的情况下提交修改要求并让执行继续。
6. 系统不会把执行结束、会话关闭或 Agent 自述误报为可交付完成。
7. 用户和旁观者能够区分“正在执行”“等待自己”“已通过验证”“已交付”。
8. 客户或协作方只看到与自身职责相符的进度和交付信息。
9. 低风险状态查询和高风险审批具有不同的身份与操作要求。
10. 所有远程操作在断网、重试、跨渠道和重启后仍保持一致。

### 3.2 产品目标

1. 用少量用户可见状态替代内部复杂状态机。
2. 用 AttentionRequest 统一驱动 Web 待办、消息通知和远程操作。
3. 用 Decision 统一表达审批、修改、暂停、恢复、取消和验收。
4. 用 Outcome 统一表达完成结果、证据、风险和交付状态。
5. 用同一套身份、版本和审计规则约束所有远程操作。
6. 让用户在最多两次主要人工决策内完成普通 Change。
7. 让普通 Change 在无人工介入期间持续推进，直到出现必要门禁。

### 3.3 非目标

- 不允许用户通过任意文本或任意命令直接执行 shell。
- 不提供通用远程终端、文件管理器或 IDE。
- 不要求用户在手机上理解 Agent、worktree、分支和内部阶段。
- 不把每个工具调用、每段思考、每条测试日志实时推送给用户。
- 不以消息发送数量、渠道数量或审批按钮数量作为产品价值。
- 不自动替用户批准 H1、H3、推送或高风险例外。
- 不在首版实现多租户、企业级 RBAC 和复杂组织权限。
- 不在首版实现任意项目并行 DAG、文件锁调度和复杂多工作项并发。
- 不替代现有 SpecGate 证据和交付内核，也不实现第二套交付记录。
- 不以个人微信非官方自动化作为核心生产通道。

## 4. 目标用户与相关角色

### 4.1 主要用户

- 一人完成需求、开发、测试和交付的独立开发者。
- 同时维护多个客户项目，但无法持续守在电脑前的承接方。
- 需要把实现交给 Codex，同时保留业务判断和最终验收权的项目负责人。

### 4.2 相关角色

#### Owner

工作项负责人，可以：

- 创建和终止 WorkItem。
- 提交修改要求。
- 提交 H1/H3 决策。
- 查看内部证据。
- 发起或确认交付。

#### Approver

对特定门禁负责的人。首版允许 Owner 兼任 Approver，但审批身份必须经过服务端
认证并绑定具体审批对象。

#### Customer or Stakeholder

只关心进度、客户可见结果和交付确认的人。默认只能看到客户视图，不得看到：

- 内部实现细节。
- 本机路径。
- 完整日志。
- 未脱敏风险。
- 内部 Agent 评审内容。

#### Observer

可以查看状态但不能执行修改、审批或交付操作的人。首版可以暂不开放 Observer
管理，但状态模型不得假定所有查看者都有操作权限。

## 5. 核心概念

### 5.1 WorkItem

WorkItem 是用户真正关心的一项异步工作，例如“修复客户反馈的导出乱码问题”。

WorkItem 至少包含：

- 工作目标。
- 所属项目和 Change。
- 当前用户可见状态。
- 最新执行结果。
- 当前是否等待人。
- 需要处理的事项。
- 最近一次交付和下一交付。
- 最近一次心跳时间。

WorkItem 不是 Codex 对话、Agent 任务或 Git worktree。这些只是 WorkItem 的
内部执行资源。

### 5.2 ExecutionRun

ExecutionRun 表示一次实际执行尝试，用于系统内部记录：

- 使用的 Codex thread 或等价执行上下文。
- 开始、更新和结束时间。
- 执行是否存活。
- 当前是否等待审批或输入。
- 失败、中断和恢复原因。
- 本轮产生的 commit 和证据。

普通用户不需要直接管理 ExecutionRun。

### 5.3 AttentionRequest

AttentionRequest 是系统请求用户注意力的唯一业务对象。

每个 AttentionRequest 必须回答：

1. 为什么现在需要用户？
2. 用户需要决定什么？
3. 可选动作是什么？
4. 每个动作会带来什么结果？
5. 相关结果、证据和风险是什么？
6. 什么时候失效？
7. 如果用户不处理，系统会怎样？

首版允许的 AttentionRequest 类型：

- 需求确认。
- H1 审批。
- 需要补充信息。
- 执行阻塞需要决策。
- 验证或 Review 失败需要选择修复路径。
- H3 审批。
- 交付验收。
- 工作机离线或执行中断。

### 5.4 Decision

Decision 是授权用户对 AttentionRequest 做出的业务决定。

首版动作集合：

- `approve`：同意当前审批对象。
- `request_changes`：要求修改并说明修改内容。
- `answer`：补充问题答案。
- `pause`：暂停执行。
- `resume`：继续执行。
- `cancel`：取消工作。
- `accept_delivery`：确认客户交付。

Decision 必须绑定：

- 操作者身份。
- WorkItem 和 Change。
- 当前状态版本。
- AttentionRequest 或被审批的 artifact。
- 操作时间。
- 幂等标识。
- 结果和审计记录。

### 5.5 Outcome

Outcome 是用户可以理解的业务结果，至少回答：

- 做完了没有。
- 完成了什么。
- 哪些 AC 已通过、失败或未验证。
- 改动了哪些业务范围。
- 是否存在已知问题或风险。
- 是否可交付。
- 是否需要用户做下一步动作。
- 下一步动作是什么。

Outcome 可以由模型生成摘要，但摘要不得替代服务端验证结果。所有关键结论必须
引用真实证据、commit 和状态版本。

## 6. 用户可见状态

### 6.1 状态分层

SpecGate 内部状态机可以继续保留详细阶段，但用户可见状态必须分层展示。

业务生命周期继续使用主需求的四个状态：

```text
项目就绪
  -> 变更已确认
  -> 证据已就绪
  -> 交付已接受
```

异步执行状态作为独立投影层展示：

| 用户状态               | 含义                   | 默认行为                  |
| ---------------------- | ---------------------- | ------------------------- |
| `QUEUED`               | 已接收，尚未开始       | 不通知，除非长时间未开始  |
| `RUNNING`              | 正在执行               | 不主动打扰，可随时查询    |
| `WAITING_FOR_USER`     | 等待用户决定           | 立即创建 AttentionRequest |
| `BLOCKED`              | 无法继续，需要人工处理 | 立即通知并说明阻塞        |
| `PAUSED`               | 用户或系统主动暂停     | 通知一次，等待恢复        |
| `FAILED`               | 执行失败且无法自动恢复 | 通知一次，提供恢复动作    |
| `READY_FOR_ACCEPTANCE` | 已验证，等待验收       | 通知一次                  |
| `DELIVERED`            | 已完成验收或交付       | 通知一次并归档摘要        |

### 6.2 状态表达要求

- 不得把 `RUNNING` 显示为“即将完成”，除非存在可信完成依据。
- 不得把 Codex 会话结束显示为完整交付完成。
- 不得在宿主离线时显示为 `RUNNING`。
- 不得将 skipped、not-run、timeout 或 failed 显示为通过。
- `READY_FOR_ACCEPTANCE` 与 `DELIVERED` 必须明确区分。
- 用户查询状态时必须显示最近心跳和下一步责任人。
- 首版不要求提供准确 ETA；没有可信依据时应显示已运行时长和当前状态，不得
  编造预计完成时间。

## 7. 核心产品原则

### 7.1 注意力优先

系统首先保护用户注意力，其次才考虑信息丰富度。

没有用户可执行动作的信息默认不主动推送。

### 7.2 结果优先

用户首先看到结果、风险和下一步，而不是 Agent 过程、工具名称和内部阶段。

### 7.3 决策优先

远程入口不是“控制 Codex”，而是提交授权 Decision。

### 7.4 证据优先

完成、通过、可交付和已验收必须来自服务端可验证状态与证据，不能来自模型自述。

### 7.5 单一路径

无论用户从 Web、移动端、飞书、企业微信还是邮件操作，都必须进入同一套
Decision 和权威状态。

### 7.6 默认可离开

任何进入 `RUNNING` 的 WorkItem，都必须具备：

- 持久化状态。
- 心跳或离线检测。
- 失败显式状态。
- 恢复路径。
- 在需要人时主动通知。

### 7.7 渠道可替换

消息渠道是适配器，不是业务模型。新增渠道不得改变 WorkItem、AttentionRequest、
Decision 或 Outcome 的语义。

## 8. 核心用户旅程

### 8.1 提交后离开

```text
用户提交目标
  -> 系统确认 WorkItem 已持久化
  -> 进入 QUEUED
  -> 开始执行，进入 RUNNING
  -> 用户离开电脑
  -> 系统持续执行
  -> 无人工事件时不推送进度
  -> 完成、失败或需要决策时通知
```

验收要求：

- 用户能够确认任务已经真正进入系统，而不是仍停留在一个可能关闭的页面。
- 用户离开后，会话结束或页面关闭不得终止 WorkItem。
- 页面断开不能影响执行。

### 8.2 需要审批

```text
执行到达 H1 或 H3
  -> 创建 AttentionRequest
  -> 生成结果摘要、证据摘要和风险摘要
  -> 通过用户偏好的渠道通知
  -> 用户查看摘要
  -> 用户在认证后审批
  -> Decision 绑定 artifact hash 和状态版本
  -> 执行自动继续
```

验收要求：

- 通知必须说明为什么需要用户。
- 用户可以不阅读原始日志完成普通审批。
- 复杂审批可以进入完整 Web 或移动视图。
- 旧审批对象变化后，原审批必须失效。

### 8.3 远程要求修改

```text
用户收到“待审批”或“已完成”通知
  -> 选择“要求修改”
  -> 输入业务修改要求
  -> 系统绑定当前 WorkItem 和状态版本
  -> 形成版本化修改请求
  -> 使旧审批失效
  -> 重新进行必要需求确认
  -> Codex 继续执行
  -> 再次通知最终结果或新的审批点
```

验收要求：

- 用户不需要自己创建新对话、新 Change 或重新描述全部背景。
- 修改要求必须保存来源、时间和原文。
- 修改要求不清晰时，系统可以发起澄清。
- 修改后不得复用已经失效的 H3、证据或交付状态。

### 8.4 失败后远程修复

```text
验证或 Review 失败
  -> 系统判断能否自动修复
  -> 不能自动修复时创建 AttentionRequest
  -> 通知展示失败项、影响 AC 和可选动作
  -> 用户选择修复、暂停、取消或查看详情
  -> 用户选择修复后自动进入下一轮
```

验收要求：

- 通知不得只显示“失败了”。
- 通知不得要求用户逐行阅读构建日志才能做决定。
- 修复动作不得把失败静默标记为通过。

### 8.5 交付和客户反馈

```text
验证和 Review 通过
  -> H3 待审批
  -> 用户远程审批
  -> 生成 DeliveryRecord
  -> 生成客户可读交付摘要
  -> 通过客户渠道发送
  -> 记录交付和回执
  -> 后续客户反馈关联该 Delivery
```

验收要求：

- 客户交付与内部证据分离。
- 客户反馈进入系统时是未可信业务输入。
- 客户反馈不能直接触发远程命令或审批。
- 下一次 WorkItem 可以关联上一 Delivery。

### 8.6 工作机离线或执行中断

```text
心跳超时
  -> WorkItem 标记为 OFFLINE 或 INTERRUPTED
  -> 通知责任人
  -> 远程状态查询明确显示不可执行
  -> 恢复后重新检查版本和锁
  -> 按策略恢复或要求重新确认
```

验收要求：

- 离线不得显示为 RUNNING。
- 离线期间的危险操作不得假装成功。
- 恢复后不得直接执行已过期或绑定了旧状态的 Decision。

## 9. 功能需求

### 9.1 WorkItem 与异步执行

#### FR-001 持久化 WorkItem

系统 MUST 将 WorkItem 持久化到可跨页面、跨会话和跨进程重启恢复的位置。

#### FR-002 执行状态

系统 MUST 维护并展示异步执行状态、最近心跳和最近更新时间。

#### FR-003 执行隔离

关闭 Web 页面、关闭移动端、断开消息渠道或关闭原 Codex 会话 MUST NOT 终止
已持久化的 WorkItem。

#### FR-004 单项目执行约束

首版 MUST 对每个项目维持现有单活动 Change 约束。系统可以接受多个待处理目标，
但 MUST NOT 在同一项目中静默并行执行多个相互影响的活动 Change。

#### FR-005 真实完成

系统 MUST 区分执行结束、验证完成、验收完成和交付完成。

#### FR-006 心跳和离线

系统 MUST 检测执行宿主是否存活，并 MUST 在心跳异常时进入显式的离线、中断或
失败状态。

#### FR-007 恢复

系统 MUST 支持 WorkItem 在进程重启、页面断开和可恢复故障后继续或安全终止。

### 9.2 AttentionRequest 与通知

#### FR-008 唯一注意力对象

所有需要用户介入的事件 MUST 生成统一 AttentionRequest，而不是由各渠道自行
拼接不同通知。

#### FR-009 可行动性

AttentionRequest MUST 包含原因、所需决定、可选动作、结果摘要、风险和有效期。

#### FR-010 默认安静

在 `RUNNING` 状态下没有用户动作时，系统 SHOULD NOT 主动推送常规进度。

#### FR-011 必要触达

以下事件 MUST 触达用户：

- 需求确认或 H1 待审批。
- 需要补充信息。
- 阻塞且无法自动恢复。
- 验证或 Review 失败且需要选择。
- H3 待审批。
- 可验收交付。
- 执行失败、中断或宿主离线。

#### FR-012 通知汇总

同一 WorkItem 的短时间重复事件 SHOULD 合并，避免用户收到连续重复通知。

#### FR-013 静音与升级

系统 MUST 支持安静时段或项目静音。高风险审批、阻塞和离线事件 MUST 按明确
策略升级提醒。

#### FR-014 通知更新

当决定已从其他渠道完成、审批对象失效或 WorkItem 状态变化时，系统 MUST 尽可能
更新原通知或发送简短失效说明，避免用户重复操作。

#### FR-015 按需查询

用户 MUST 能从任一支持的交互入口查询 WorkItem 的当前状态、所需动作和最新结果。

### 9.3 Web 控制台与移动端

#### FR-016 注意力首页

Web 控制台首页 MUST 优先展示“等待你处理”的事项，而不是仅展示项目或日志列表。

#### FR-017 WorkItem 视图

Web 控制台 MUST 展示 WorkItem 的目标、用户可见状态、最新 Outcome、
AttentionRequest 和可执行动作。

#### FR-018 完整证据视图

Web 控制台 MUST 允许授权用户查看与结论对应的 AC、证据、commit、风险、
审批和交付记录。

#### FR-019 移动决策

移动端 MUST 支持查看 AttentionRequest、审批、要求修改、暂停、恢复和验收等
首版允许的 Decision。

#### FR-020 跨端一致

Web、移动端和消息渠道 MUST 显示同一 WorkItem、同一状态版本和同一
AttentionRequest 业务结果。

#### FR-021 技术细节折叠

日志、worktree、Agent 名称和内部阶段 MAY 在完整视图中提供，但 MUST NOT 成为
普通用户做出判断的前提。

### 9.4 Decision 与远程控制

#### FR-022 授权动作

系统 MUST 只接受预定义的业务 Decision，不提供任意 shell、任意文件写入或任意
工具调用入口。

#### FR-023 版本绑定

所有改变 WorkItem 状态的 Decision MUST 包含或由服务端解析当前状态版本，并使用
版本 CAS 防止旧操作覆盖新状态。

#### FR-024 身份认证

系统 MUST 从可信会话或已验证渠道映射中得到用户身份，MUST NOT 信任用户输入、
消息昵称、发件人或模型自述中的身份。

#### FR-025 修改语义

`request_changes` MUST 形成可追溯的修改请求，并使受影响的审批、证据和交付状态
失效或重新评估。

#### FR-026 连续执行

用户完成必要 Decision 后，系统 MUST 自动继续工作流，不得要求用户手工串联
内部 Agent 或阶段。

#### FR-027 高风险动作

H1、H3、取消、归档、推送和高风险例外 MUST 使用与普通状态查询不同的认证和
确认要求。

#### FR-028 幂等

重复点击、平台重试和重复回调 MUST NOT 导致重复审批、重复创建 Change、
重复执行或重复交付。

#### FR-029 失效处理

过期、已被消费或绑定旧 artifact 的 Decision MUST 被拒绝，并向用户显示最新状态
和重新获取动作的路径。

### 9.5 消息渠道

#### FR-030 统一渠道抽象

系统 MUST 使用统一 MessageEnvelope 和 ChannelAdapter 语义接入消息渠道。
渠道差异 MUST NOT 泄漏到 WorkItem、AttentionRequest 或 Decision 核心模型。

#### FR-031 飞书

系统 SHOULD 支持飞书消息触达和受控交互卡片，作为一人团队的首选候选渠道。

#### FR-032 企业微信

系统 SHOULD 支持企业微信通知；远程动作能力取决于企业应用、客户联系或安全
H5 能力。群机器人只能通知时，不得伪装成可交互审批入口。

#### FR-033 邮箱

系统 MUST 支持邮件作为通用触达和正式交付摘要渠道，并 SHOULD 支持把客户反馈
录入 Feedback Inbox。

#### FR-034 邮件审批安全

邮件回复 MUST NOT 直接构成审批。邮件中的审批动作 MUST 通过认证链接、短期令牌
和服务端确认完成。

#### FR-035 个人微信边界

个人微信非官方自动化 MUST NOT 作为核心远程控制或审批通道。需要微信生态触达时，
优先使用企业微信、公众号或其他官方能力。

#### FR-036 渠道故障隔离

单一消息渠道不可用 MUST NOT 阻塞 Codex 执行、WorkItem 状态推进或证据保存。

#### FR-037 投递可靠性

系统 MUST 记录通知的待发送、发送成功、发送失败、重试和最终状态。

### 9.6 Outcome 与证据

#### FR-038 结果摘要

系统 MUST 为每个用户可见结果生成业务摘要，至少包含完成情况、改动范围、
AC 结果、已知问题、风险和下一步。

#### FR-039 证据引用

Outcome 中的“通过”“失败”“未验证”“可交付” MUST 可追溯到服务端证据和固定
commit。

#### FR-040 无虚假完成

系统 MUST NOT 将模型回复、会话结束或未验证结果标记为已交付。

#### FR-041 客户视图

系统 MUST 提供与内部证据分离的客户可见结果，并默认隐藏内部路径、日志、
凭据和敏感风险。

### 9.7 反馈闭环

#### FR-042 反馈收件

系统 SHOULD 提供统一 Feedback Inbox，接收邮件、聊天转发和手工录入的反馈。

#### FR-043 不可信输入

外部反馈 MUST 被视为不可信业务输入，不得直接作为审批、推送、远程命令或
系统指令执行。

#### FR-044 反馈确认

反馈进入正式 Change 前 MUST 由授权用户确认其业务意图。

#### FR-045 交付关联

当客户反馈针对已有交付时，新 WorkItem SHOULD 关联对应 Delivery 和受影响 AC。

### 9.8 审计、恢复和观察

#### FR-046 操作审计

系统 MUST 记录 AttentionRequest 创建、通知投递、Decision、命令执行、失效、
失败和恢复。

#### FR-047 跨渠道一致性

一个渠道完成 Decision 后，其他渠道 MUST 能识别其已处理状态，不得再次执行。

#### FR-048 WorkItem 保留

失败、取消和中断的 WorkItem MUST 保留足以解释结果和恢复风险的状态及证据。

#### FR-049 无重复副作用

系统 MUST 保证通知重试、网络超时和客户端重放不会产生重复提交、重复推送或
重复交付。

#### FR-050 可观察性

系统 MUST 提供执行心跳、渠道健康、通知投递和待处理动作的可观察状态。

## 11. 通知和摘要内容规范

### 11.1 一级信息

通知首屏必须让用户在数秒内知道：

- 哪个 WorkItem。
- 当前结果。
- 是否需要自己行动。
- 需要做什么。

示例：

```text
CRM 导出修复：需要你的审批

验证已通过 4/4 个验收标准。
改动：后端导出逻辑、前端文件名处理。
风险：低。
下一步：确认是否交付。

[查看摘要] [审批通过] [要求修改]
```

### 11.2 二级信息

展开后可查看：

- 验收标准逐项结果。
- 改动范围。
- 已知问题。
- 未验证内容和剩余风险。
- 证据和 commit 摘要。
- 交付和回滚说明。

### 11.3 禁止内容

通知默认不得包含：

- 明文凭据、令牌或环境变量。
- 完整源码 diff。
- 未脱敏客户数据。
- 绝对本机路径。
- 大段构建或测试日志。
- 只对内部 Agent 有意义的阶段代号。

## 12. 安全与信任需求

### 12.1 身份与授权

- 渠道账号必须绑定到受信业务身份。
- 外部用户 ID 本身不是审批凭据。
- 用户角色和可执行动作必须由服务端校验。
- 消息内容不得包含“actor”“approval=true”等可伪造身份字段。

### 12.2 审批

- H1/H3 必须绑定具体 artifact hash。
- 审批必须具有有效期和单次消费语义。
- 审批对象变化后必须自动失效。
- 审批必须在服务端记录操作者、渠道、时间和结果。
- 邮件回复、聊天文字和模型输出不能成为审批本身。

### 12.3 远程动作

- 远程动作必须是白名单业务 Decision。
- 远程动作必须绑定 WorkItem、版本和目标对象。
- 高风险动作必须重新认证。
- 工作站不得因消息接入而默认暴露公网管理端口。
- 远程通道不得持有 Codex 登录凭据或项目源码副本。

### 12.4 数据最小化

- 消息渠道只接收完成决策所需的最少信息。
- 完整证据保存在受控位置，通过认证链接访问。
- 内部与客户渠道必须使用不同可见性策略。
- 渠道凭据必须保存在操作系统安全存储中，不得进入项目仓库。

## 13. 非功能需求

### NFR-001 注意力预算

- 普通 Change 的主要人工决策不超过两次。
- 无人工动作时不推送常规进度。
- 用户能够在一个通知内判断是否需要打开完整控制台。
- 同一问题不得跨渠道重复要求用户回答。

### NFR-002 可靠性

- 页面关闭、会话结束和渠道故障不得导致 WorkItem 丢失。
- 通知发送失败必须重试或切换备用渠道。
- 执行进程异常必须被识别为中断，而不是继续保持 RUNNING。
- 所有会产生副作用的动作必须幂等。

### NFR-003 一致性

- 所有 Surface 展示同一权威 WorkItem 状态。
- Decision 完成后其他 Surface 必须得到更新或失效提示。
- 旧版本动作不得覆盖新版本状态。
- 消息平台状态不得成为审批或交付的权威记录。

### NFR-004 安全

- 外部消息、邮件和附件均按不可信输入处理。
- 审批和远程动作必须防重放、防伪造、防跨项目绑定。
- 默认最小权限，默认不暴露管理端口。
- 安全失败必须 fail closed，不能自动放宽审批。

### NFR-005 可恢复性

- 执行宿主重启后可以恢复或安全终止可恢复工作。
- 失败和中断保留恢复所需上下文。
- 恢复后重新校验版本、锁、证据和审批有效性。
- 不能伪造“从中断处继续”的完成证据。

### NFR-006 性能

- 交互式状态查询应在用户可感知的正常页面或消息响应时间内返回。
- 必要审批和阻塞通知应在事件持久化后尽快发出，具体阈值由渠道能力决定。
- 普通执行日志不得因通知需求而同步阻塞。
- 长时间运行不得依赖浏览器连接保持。

### NFR-007 可用性

- 移动决策页面必须适合窄屏使用。
- 消息摘要必须使用业务语言。
- 用户可见状态不超过约定集合。
- 内部技术细节默认折叠，但授权用户可以下钻。

### NFR-008 可观测性

- 可以区分执行存活、等待用户、离线、失败和完成。
- 可以追踪通知是否发送、失败或已处理。
- 可以追踪 Decision 从入口到执行结果的完整链路。
- 可以识别旧动作、重复动作和跨渠道冲突。

### NFR-009 兼容性

- 首版沿用现有 ProjectProfile、Baseline、Change、Evidence、H1/H3 和 Delivery
  语义。
- 不引入与现有权威状态并行的第二业务真相。
- 消息渠道新增或替换不得要求改写核心 WorkItem 状态机。

### NFR-010 可维护性

- 渠道适配、通知规则、Decision 校验和执行桥接应具有清晰边界。
- 业务事件必须使用稳定的业务类型，不能绑定具体消息平台事件名称。
- 通知模板与业务判断分离。
- 新增渠道不得复制审批、状态和交付逻辑。

## 14. 验收场景

### AC-001 提交后离开

- GIVEN 用户提交一个需要长期执行的 WorkItem
- WHEN WorkItem 已持久化并进入执行
- THEN 用户可以关闭页面或离开电脑
- AND 系统继续推进执行
- AND 无人工事件时不发送常规进度通知

### AC-002 完成通知

- GIVEN WorkItem 不需要用户介入即可完成
- WHEN 服务端确认结果和证据
- THEN 用户只收到一次完成通知
- AND 通知说明是否可交付、是否存在已知问题和是否需要下一步动作

### AC-003 审批触达

- GIVEN WorkItem 到达 H1 或 H3
- WHEN 系统创建 AttentionRequest
- THEN 用户在首选渠道收到通知
- AND 通知包含审批原因、结果摘要、风险、证据入口和动作

### AC-004 远程审批

- GIVEN 用户收到未过期的 H3 AttentionRequest
- WHEN 用户完成要求的身份认证并批准
- THEN Decision 绑定当前 artifact hash 和状态版本
- AND 审批只能消费一次
- AND WorkItem 自动继续

### AC-005 审批失效

- GIVEN 用户持有旧审批通知
- WHEN 被审批对象或状态版本已经变化
- THEN 系统拒绝旧动作
- AND 用户收到最新状态和重新获取审批入口

### AC-006 远程修改

- GIVEN 用户在远程端选择要求修改
- WHEN 用户提交业务修改说明
- THEN 系统保存原始说明并形成版本化修改请求
- AND 受影响审批、证据和交付状态失效或重新评估
- AND 系统自动继续必要流程

### AC-007 跨渠道一致

- GIVEN 同一 AttentionRequest 同时出现在多个渠道
- WHEN 用户在一个渠道完成 Decision
- THEN 其他渠道不能再执行同一 Decision
- AND 其他渠道显示已处理或失效状态

### AC-008 重复回调

- GIVEN 消息平台重复发送同一动作回调
- WHEN 系统重复收到请求
- THEN 只产生一次 Decision 和一次业务副作用
- AND 审计记录能够说明重复请求被去重

### AC-009 渠道故障

- GIVEN 首选消息渠道不可用
- WHEN WorkItem 达到需要通知的状态
- THEN 执行和证据保存不阻塞
- AND 系统按策略重试或切换备用渠道
- AND 用户可以在 Web 控制台看到未送达状态

### AC-010 宿主离线

- GIVEN WorkItem 显示 RUNNING
- WHEN 执行宿主人心跳超时
- THEN 状态变为 OFFLINE 或 INTERRUPTED
- AND 用户收到明确通知
- AND 远程危险动作不会显示为成功

### AC-011 状态查询

- GIVEN 用户需要了解某个 WorkItem
- WHEN 用户从任一支持入口查询状态
- THEN 系统返回当前状态、最近结果、所需动作和最近心跳
- AND 不要求用户阅读完整日志

### AC-012 客户反馈

- GIVEN 客户通过邮件或聊天提交反馈
- WHEN 系统接收该反馈
- THEN 反馈进入不可信 Feedback Inbox
- AND 在授权用户确认前不创建执行命令
- AND 确认后可以关联上一 Delivery

### AC-013 无虚假完成

- GIVEN Codex 会话已经结束
- WHEN 验证或 H3 尚未完成
- THEN 系统不得显示 DELIVERED
- AND 必须显示实际验证或验收状态

### AC-014 客户视图脱敏

- GIVEN 客户访问交付摘要
- WHEN 客户查看结果
- THEN 不显示内部路径、完整日志、凭据和内部 Review 细节
- AND 客户可见内容与 DeliveryRecord 保持一致

### AC-015 危险动作限制

- GIVEN 用户持有低权限渠道身份
- WHEN 用户尝试审批、推送或执行任意命令
- THEN 系统拒绝或要求升级认证
- AND 不暴露任意 shell 执行入口

### AC-016 身份伪造

- GIVEN 消息内容声称用户已经同意或包含伪造 actor 字段
- WHEN 系统处理该消息
- THEN 不得因此产生审批或高权限 Decision

### AC-017 静音与升级

- GIVEN 用户处于项目静音或安静时段
- WHEN 普通进度事件发生
- THEN 系统不主动推送
- AND 阻塞或高风险审批仍按策略升级

### AC-018 恢复一致性

- GIVEN 执行宿主或控制进程在 RUNNING 状态重启
- WHEN 系统恢复 WorkItem
- THEN 重新校验状态版本、锁、审批和证据
- AND 不重复执行已完成动作
- AND 无法安全恢复时进入显式状态并通知用户

### AC-019 结果摘要可信

- GIVEN 系统生成了完成摘要
- WHEN 用户查看通过、失败或可交付结论
- THEN 每个结论都能关联到服务端状态和证据
- AND 模型摘要与证据冲突时以证据为准并标记冲突

### AC-020 一人团队注意力预算

- GIVEN 一次普通 Change 没有额外阻塞
- WHEN 用户从提交到验收完成
- THEN 主要人工决策不超过两次
- AND 用户不需要手工派发或串联内部 Agent
- AND 系统记录实际打断次数和决策耗时

## 15. 指标与试点判定

### 15.1 核心指标

- 用户提交后到离开电脑的时间。
- 用户实际盯守执行界面的时间。
- 每次 Change 的主动通知数量。
- 需要行动的通知占比。
- 从需要用户到用户完成 Decision 的时间。
- 每次 Change 的人工决策次数。
- 需要打开完整控制台才能决策的通知占比。
- 修改请求导致的返工轮次。
- 重复、过期和错误绑定的远程动作数量。
- 通知投递成功率和渠道故障恢复时间。
- 执行中断发现时间和恢复时间。
- 从验证完成到交付确认的时间。

### 15.2 试点目标

首轮试点暂定：

- 普通 Change 的主要人工决策不超过两次。
- 常规执行过程中不发送逐步进度通知。
- 必需决策能够在消息摘要中被识别，不需要先阅读完整日志。
- 重复动作和重复副作用为 0。
- 无真实证据的“已完成”或“可交付”为 0。
- 页面关闭或会话结束后 WorkItem 不丢失。
- 远程审批和修改能够完整进入既有审计和交付链路。

### 15.3 停止扩张条件

如果消息和远控系统出现以下情况，应停止增加渠道，优先修正核心模型：

- 通知数量增加但用户决策时间没有下降。
- 用户仍需反复查看完整日志。
- 重复审批、旧动作误执行或跨项目误绑定出现。
- 渠道状态与 Web 状态长期不一致。
- 消息系统阻塞执行或证据保存。
- 用户仍需手工串联内部 Agent。
- 安全性依赖用户正确理解技术细节。

## 16. 批判性风险与已知取舍

### 16.1 消息更多不等于注意力更少

将每个内部事件发送到消息渠道会制造新的干扰。产品必须以 AttentionRequest
为中心，不以事件广播为中心。

### 16.2 Web 控制台不是最终目的

Web 控制台是完整上下文和修复界面，不应成为唯一完成工作流的入口。若用户仍需
持续查看控制台，异步执行问题没有真正解决。

### 16.3 自由聊天不是远程控制协议

自然语言适合表达业务修改，不适合作为高权限状态变更协议。审批、推送、取消和
交付必须使用结构化 Decision、版本绑定和身份校验。

### 16.4 AI 摘要不能成为事实来源

摘要可以降低阅读成本，但通过、失败、可交付和已验收必须来自服务端验证和证据。

### 16.5 本地执行宿主仍是单点

首版依赖开发工作站保持在线。产品必须明确显示离线，不得把工作站休眠、断网或
进程退出伪装为继续执行。更高可用的远端执行环境属于后续范围。

### 16.6 多项目不等于多 Change 并行

首版可以降低多项目的等待成本，但仍受每项目单活动 Change 约束。复杂并行会
扩大冲突、证据和交付风险，不作为首版目标。

### 16.7 个人微信风险

依赖非官方个人微信自动化会带来账号、合规和可靠性风险，因此不作为核心通道。

### 16.8 渠道能力差异

不同消息渠道在交互卡片、回调、审批和附件能力上存在差异。产品必须保证核心
Decision 在不支持复杂交互的渠道上可降级为安全链接，而不是伪造同等能力。

## 17. 交付切片

### S1：异步状态底座

- WorkItem 持久化。
- 用户可见状态投影。
- 执行心跳和离线检测。
- AttentionRequest、Decision 和 Outcome 基础模型。
- 保持现有一个活动 Change 约束。

对应价值：用户能够确认任务不会因关闭页面或会话而丢失。

### S2：Web 注意力控制台

- 首页以待办为中心。
- WorkItem 状态和 Outcome。
- 完整证据视图。
- 动作历史和跨端处理状态。

对应价值：用户离开电脑后回来，可以快速恢复上下文。

### S3：消息触达

- 首选渠道的通知。
- 邮件摘要。
- 通知规则、静音、合并和失败重试。
- 安全深链接。

对应价值：只有需要人时打断。

### S4：低风险远程 Decision

- 状态查询。
- 暂停、恢复。
- 要求修改。
- 从失败进入修复。
- 幂等、过期和版本冲突处理。

对应价值：用户不必返回电脑才能让流程继续。

### S5：远程审批与交付闭环

- H1/H3 远程审批。
- 升级认证。
- 客户交付摘要和回执。
- Feedback Inbox 关联上一 Delivery。

对应价值：从需要审批到最终交付不再依赖桌面环境。

### S6：扩展渠道和远程运行环境

- 第二消息渠道。
- 多设备和工作站路由。
- 更完整的团队和客户角色。
- 远端执行环境评估。

对应价值：在核心闭环被真实项目验证后才扩展规模和复杂度。

## 18. 待确认决策

以下内容需要后续确认，不阻塞需求意图，但会影响设计和试点范围：

1. 首个消息渠道选择飞书还是企业微信；应以真实客户沟通来源为准。
2. 移动端首版采用独立 PWA，还是只提供 Web 响应式页面和安全深链接。
3. 首版是否需要云端 Relay，还是先依赖本地可访问性和渠道原生长连接。
4. H1/H3 远程审批采用何种升级认证方式。
5. 普通 Change 是否允许在满足全部证据和低风险条件时自动进入
   `READY_FOR_ACCEPTANCE`，而不是等待另一条执行完成通知。
6. Feedback Inbox 首版支持哪些入站来源和附件类型。
7. 客户回执是否只记录“已查看/已确认”，还是需要正式电子签收。
8. 多项目场景中，待处理 WorkItem 的队列和公平调度策略。

## 19. 最终完成定义

1. 用户提交 WorkItem 后可以关闭页面、关闭原会话并离开电脑。
2. WorkItem 状态和执行资源可以跨进程重启恢复。
3. 系统能够区分执行中、等待用户、阻塞、暂停、失败、待验收和已交付。
4. 没有用户动作时，系统不主动推送常规执行进度。
5. 需要用户时，系统生成包含原因、结果、风险、动作和有效期的
   AttentionRequest。
6. 用户能够从 Web、移动端或消息渠道查看同一 WorkItem 状态和 Outcome。
7. 用户能够远程审批、要求修改、暂停、恢复和取消受控动作。
8. 所有 Decision 都绑定身份、状态版本和目标对象，能够防止旧动作和重复动作。
9. 修改要求可以重新进入需求、实现、验证和交付流程，而不是形成孤立聊天记录。
10. 消息渠道故障不影响执行、证据保存和 WorkItem 状态推进。
11. 工作站离线、执行中断和通知失败均被显式展示。
12. 完成、验证、验收和交付不会被混为一个“已完成”状态。
13. 没有真实证据的通过、可交付或已验收结论无法进入系统。
14. 客户交付与内部证据分离，客户反馈作为不可信输入进入受控流程。
15. 所有外部渠道动作都能在 Web 控制台和审计记录中追溯。
16. 远程入口不能绕过 H1/H3、证据充分性、高风险 Review 和现有交付门禁。
17. 普通 Change 的主要人工决策不超过两次。
18. 试点能够证明用户盯守时间、决策等待时间或返工成本至少一项显著下降。

## 20. 与现有需求的追踪关系

| 本文能力         | 现有需求关系                                            |
| ---------------- | ------------------------------------------------------- |
| 异步 WorkItem    | 扩展 Change 生命周期和执行监督                          |
| AttentionRequest | 落地主需求的注意力保护原则                              |
| Web 注意力首页   | 强化 FR-024 注意力预算                                  |
| 消息触达         | 为 H1/H3、失败和交付提供低打断触达                      |
| 远程 Decision    | 扩展 H1/H3、暂停、继续和退回能力                        |
| Outcome 摘要     | 复用 VerificationAssessment、Evidence 和 DeliveryRecord |
| 客户视图         | 复用客户交付包并强化脱敏                                |
| Feedback Inbox   | 扩展增量再交付的客户反馈入口                            |
| 跨渠道审计       | 强化 NFR-002 可审计和 NFR-004 一致性                    |

任何实现都不得绕开以下现有规则：

- 证据必须绑定固定 commit 和环境。
- Agent 自述不能替代验证结果。
- H1/H3 必须经过可信用户确认。
- 只有明确授权才能 push，且不得 force push。
- DeliveryRecord、内部证据包和客户交付包必须保持可追溯关系。
