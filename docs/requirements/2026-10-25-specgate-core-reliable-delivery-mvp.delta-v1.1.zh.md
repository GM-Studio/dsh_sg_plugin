## 3. 修订既有 RQ 与新增 RQ

### 3.1 对既有 RQ 的追加验收标准

以下条款**追加**到 v1.0 对应 RQ，原 AC 编号与内容不变。

#### RQ-008 追加：计划文件白名单契约与依赖批准门

- **AC-008-06**：Given 冻结计划，When 校验 plan contract，Then 每个 task 必须包含 `allowedFiles`（非空 glob 列表）与 `forbiddenFiles`；缺失任一即拒绝冻结。角色边界不得由实现代码硬编码前缀推导。
  - 现状：字段不存在（`plan.js:173-199,791-799`）；边界硬编码（`development.js:297-307`）。
- **AC-008-07**：Given 实现 diff 新增或升级了依赖（`pom.xml`、`build.gradle`、`package.json`、`package-lock.json` 等依赖清单），When 校验提交，Then 若该变更有对应 AC 映射则放行，否则阻断并输出请求批准的清单。
  - 现状：未实现；仅作 review 模式升级信号，不阻断（`review.js:223-232,264`）。

#### RQ-012 追加：findings 传递与轮次上界

- **AC-012-05**：Given 质量门或 Review 产生 findings，When 启动修复，Then Implementer 的输入载荷必须**实际包含** finding 列表（可机器断言：输入对象中存在 findings 字段且条数 > 0），不得只写入状态库。
  - 现状：只落库（`development.js:1187-1188`）；角色 challenge 与 native prompt 均不含（`development.js:700-729`）。
- **AC-012-06**：Given 同一 Change 连续自动修复，When 第 N 次失败，Then N ≤ 2 时允许再修复，N = 3 时进入 `BLOCKED`。判定必须由单一计数器表达，不得存在第二个独立循环上界。
  - 现状：`retryAllowed` 为 `failures <= 2`（`checkpoints.js:1,21`），叠加 `retry < 4` 内循环（`development.js:883`）。

#### RQ-014 追加：格式化后回归必须真实发生

- **AC-014-05**：Given Formatter 产生了新 commit，When 进入 Review 之前，Then 必须对**该新 commit**重新执行完整质量门（build、test、lint、format check、运行证据），并把新证据绑定到新 commit；未重跑或证据 commit 不匹配时禁止迁移到 `REVIEWING`。
  - 现状：`format.js:398` 直接迁移，无质量门调用；Review 复用旧 quality hash（`review.js:391-399`）。
  - 本条是 v1.0 AC-014-02 的**强制化**：v1.0 已写要求，但实现缺失，故追加可机械断言的判定点与禁止条件。

#### RQ-015 追加：Review 执行者装配与报告来源可信

- **AC-015-06**：Given 状态查询或 Review 执行，When 服务端未装配 Review 角色提供者且未启用 native 报告路径，Then `sg_state`/`sg_status` 必须报 `unavailable`，`review.run` 必须返回 `REVIEW_PROVIDER_UNAVAILABLE`；不得在任一路径下把 Review 标记为可用而实际不可执行。
  - 现状：`reviewRoleProvider` 在默认入口从未装配（`workflow-tools.js:580`；`server.js:92,111`）；仅有 `nativeAgents` 兜底（`review.js:518-519`；`workflow-tools.js:691-699`）。`mcp.json` 默认 `SPECGATE_NATIVE_AGENTS=1`，因此当前实际依赖 native-report 路径。
- **AC-015-07**：Given 调用方在工具参数中提交 `report` 对象，When 该报告未经服务端角色路径产生，Then 必须拒绝，除非服务端显式声明处于 native-report 模式；且报告的 `evidence` 校验不得退化为「是 diff 文本的子串」这一弱条件。
  - 现状：`args.report` 被优先使用（`review.js:517,540-541`）。

#### RQ-017 追加：客户摘要不得过滤已知问题

- **AC-017-06**：Given DeliveryRecord 记录了 knownIssues、open risks 或未验证区域，When 生成客户可见摘要，Then 摘要中的 knownIssues 必须与 DeliveryRecord 逐项一致；不得出现摘要为空而记录非空的情况，且不得由代码写死空数组。
  - 现状：`release.js:520` 写死 `knownIssues: []`，与 `release.js:456-461,480` 不一致。

#### RQ-018 追加：证据与 commit 的严格绑定

- **AC-018-06**：Given 质量门证据与当前被评审 commit，When 执行 Review 或 H3，Then 证据记录的 commit 必须等于当前固定 commit；若二者不同，即使证据内容 hash 发生变化、或新旧内容被合成为新指纹，也必须拒绝并重新执行质量门。
  - 现状：Review 用新 `integrationCommit` 生成 diff，却复用格式化前的 quality hash，并把二者混为一个新指纹（`review.js:391-399,402-405,527`）。该行为使「hash 变化」看起来像新鲜证据，实际是跨 commit 拼接。

#### RQ-021 追加：公开面与发行包可机械断言

- **AC-021-05**：Given 默认 MCP 启动，When 断言公开工具名清单，Then 清单必须与一份受测的期望清单完全一致，且不含 `sg_work_item_*`、Worker、Decision、TOTP 或远程部署入口；差异即测试失败。
  - 现状：`CONTROL_TOOLS` 无条件并入（`workflow-tools.js:608`），含 3 个 `sg_work_item_*`。
- **AC-021-06**：Given 核心发行包，When 检查 `package.json` 的 `dependencies` 与 `bundledDependencies`，Then 不得包含仅服务于可选模块的依赖（当前指 `mysql2`）；该依赖若需保留，必须改为可选依赖且由可选入口动态加载。
  - 现状：`package.json:81-86` `dependencies.mysql2` + `bundledDependencies: ["mysql2"]`。
- **AC-021-07**：Given 核心 MCP 启动，When 检查模块加载图，Then 不得静态加载控制面、Web、通知或 MySQL 模块；只能按需动态加载。

#### RQ-022 追加：质量门命令来源

- **AC-022-04**：Given 执行质量门，When 构造 build/test/lint/format 命令，Then 命令必须来自项目自声明 profile 或仓库内确定性 provider，且可追溯到一个已提交的命令定义；禁止模型在工具参数中临时拼接 shell 命令。测试必须能断言「模型传入任意命令字符串会被拒绝」。
  - 现状：命令来自 testRunner provider（`quality.js:834-841`），verification 走 profile（`:972-1005`）。provider 满足「非模型拼凑」的实质意图，但缺可追溯性与负向断言。

### 3.2 新增 RQ

#### RQ-025 单一权威状态源

系统必须只存在一条可写状态路径。第二套状态文件不得可写。

- **AC-025-01**：Given 任意工具调用，When 写入状态，Then 只允许写入事件链内核对应的单一文件；其他状态文件必须是只读兼容视图。
- **AC-025-02**：Given 第二套状态实现，When 尝试写入，Then 必须拒绝，或由主内核在同一事务内完成并保持 hash 一致；不允许出现无 CAS、无锁、无事件记录的写入路径。
- **AC-025-03**：Given 同一 Change，When 同时读取两处状态，Then 不得出现互相矛盾且无法仲裁的结果。
- 现状证据：`core/state.js:6-29,181-204`（12 值 phase、无 CAS、无锁、无事件链）与 `state-machine.js:5-48` 并存，写不同文件（`core/state.js:27-29` vs `storage.js:25`）。

#### RQ-026 人工门审批期间的写入可用性

人工审批期间状态库必须保持可读，且不得因等待用户输入而长时间占用写锁。

- **AC-026-01**：Given 系统正在等待 H1 或 H3 的原生审批响应，When 另一请求读取状态，Then 必须在正常时限内返回，不得因审批未返回而失败。
- **AC-026-02**：Given 审批等待中，When 另一写入请求到达，Then 必须得到明确、可区分的结果（例如 `APPROVAL_IN_PROGRESS`），不得表现为通用的存储忙或超时。
- **AC-026-03**：Given 审批超时或取消，When 恢复，Then 状态库必须回到审批前的可用状态，且不残留锁。
- 现状证据：`state-machine.js:100-101,261` 在写锁内 await 审批；审批表单超时可达 5 分钟（`approvals.js:263`），期间其他写入在数秒后 `STORE_BUSY`（`storage.js:197,220-224`）。

#### RQ-027 事务性审计回滚的一致性

审计事件与状态快照必须保持一致；回滚不得留下会导致事件链自判损坏的残留。

- **AC-027-01**：Given 事务性审计在写入事件后失败，When 回滚，Then 事件链必须仍然可校验通过，或在当日志中留下可识别的隔离标记；不得使后续读取判定 `AUDIT_CORRUPT`。
- **AC-027-02**：Given 回滚发生，When 追加后续事件，Then 不得出现同一 `sequence` 的两条记录。
- **AC-027-03**：Given 快照写入失败，When 继续运行，Then 必须显式暴露该状态而不是静默降级。
- 现状证据：`state-machine.js:127-133` 回滚只做 `version--`；事件已 fsync 落盘（`storage.js:234-244`）；随后以同一 `headHash` 追加同 `sequence` 会被 `events.js:51` 判为 `AUDIT_CORRUPT`。

#### RQ-028 事件链外部单调锚点

系统必须能检出「事件链与快照被同时回退到较早状态」这一类篡改。

- **AC-028-01**：Given 项目 Git 树之外的单调锚点记录，When 状态回退到较早版本，Then 系统必须检出并拒绝继续，而不是静默接受。
- **AC-028-02**：Given 锚点不存在或不可读，When 读取状态，Then 必须按 fail-closed 处理并明确报告，不得默认视为可信。
- **AC-028-03**：Given 锚点落盘，When 正常推进状态，Then 锚点必须单调推进，且推进本身有真实写证据（文件内容或 commit）。
- **范围界定（假设 A1）**：本条只要求「检出本地回退」，**不**要求防御拥有本机完全控制权、可重建整条链与锚点的攻击者。后一目标超出 MVP 单机范围。
- 现状证据：`events.js:3-4` 作者自述无外部信任锚；快照与事件同时回退无检测手段。

#### RQ-029 冻结测试在冻结期不可替换

测试冻结一经形成，在实现与验证阶段必须不可替换。

- **AC-029-01**：Given 测试已冻结并已通过红色基线，When 进入 `IMPLEMENTING` 或之后任一阶段，Then 不得整体替换冻结测试资产。
- **AC-029-02**：Given 确有必要替换，When 执行替换，Then 必须回到红色基线之前的稳定检查点、重新冻结并重跑红色基线，且留下显式的审批记录；替换后不得直接继续实现。
- **AC-029-03**：Given 替换发生，When 校验证据链，Then 旧冻结资产的 hash、替换原因、审批来源与新 hash 必须同时存在。
- 现状证据：`plan.js:1014-1026` 允许在 `TESTING` 阶段以单个 reason 字符串替换；`plan-tools.js:159-160` 已导出该入口。

#### RQ-030 状态机对外承诺与内部实现分离

需求层只承诺对外业务状态；内部状态词表是实现细节，必须可映射且映射受测。

- **AC-030-01**：Given 用户或外部集成读取状态，When 展示阶段，Then 只能看到 §4.1 定义的对外业务状态与侧状态。
- **AC-030-02**：Given 内部状态取值，When 转换到对外状态，Then 必须存在一张受测的完整映射表，覆盖全部内部取值，不允许有未映射或映射到多个对外状态的歧义项。
- **AC-030-03**：Given 新增或删除内部状态，When 合并，Then 必须同步更新映射表与其测试，否则视为破坏性变更。
- 现状证据：`state-machine.js:5-30` 共 16 主 + 6 侧；v1.0 §5.2 只有 10 主 + 3 侧；映射见 §4。

## 6. 非功能需求增补

以下条款追加到 v1.0 §11，原文不变。

### 6.1 可靠性

- **NFR-R-01**：任意时刻只允许一个可写状态源（对应 RQ-025）。存在第二条写路径即视为不满足。
- **NFR-R-02**：等待人工输入（H1/H3）不得阻塞无关的状态读取，且不得导致无关写入表现为通用存储故障（对应 RQ-026）。
- **NFR-R-03**：事务性审计失败必须保持事件链可校验；不得出现「回滚后立即自判损坏」的组合（对应 RQ-027）。
- **NFR-R-04**：状态回退到较早版本必须可检出（对应 RQ-028，限该条界定范围）。
- **NFR-R-05**：质量门证据必须绑定到被评审的那一个 commit；跨 commit 复用旧 PASS 一律视为未验证（强化 AC-018-04/05）。

### 6.2 可维护性与可验证性

- **NFR-M-01**：公开工具名清单必须由测试断言完整清单，而不只是断言「某些名字不出现」。
- **NFR-M-02**：核心启动的静态 import 图必须由测试断言：控制面、Web、通知、MySQL 模块不得出现在静态加载图内。
- **NFR-M-03**：发行包内容必须由测试断言：`dependencies` 与 `bundledDependencies` 不含仅服务可选模块的条目。
- **NFR-M-04**：每个新增的内核级不变量（RQ-025…RQ-029）必须至少有一个负向测试，证明违规被拒绝。
- **NFR-M-05**：状态映射表（§4）必须由测试断言完整覆盖，新增内部状态而不更新映射即为失败。

### 6.3 性能与成本

- **NFR-P-01**：锚点写入（RQ-028）在单个状态迁移上的额外开销必须是常数级文件追加，不得触发全量重算。
- **NFR-P-02**：格式化后强制重跑全量质量门（AC-014-05）会增加一次完整门耗时；该成本被明确接受，因为它是 RQ-014 的实质内容，不得以「流程变慢」为由跳过。

### 6.4 安全

- **NFR-S-01**：Review 报告不得由调用方注入的普通对象充当（对应 AC-015-07）；服务端必须能区分「角色路径产出的报告」与「调用方提交的报告」。
- **NFR-S-02**：测试替换（RQ-029）必须要求显式审批记录，不能仅凭一段原因文本。

## 8. 验收场景增补

以下场景追加到 v1.0 §13，与 AC-MVP-01…AC-MVP-10 并存。

### 8.1 AC-MVP-11 格式化后回归真实发生

Given 一个已通过质量门的实现 commit 和一次产生新 commit 的格式化，
When 请求进入 Review，
Then 系统对该新 commit 重新执行 build、test、lint、format check 与运行证据，且新证据绑定新 commit；若未重跑，则拒绝进入 Review。

### 8.2 AC-MVP-12 单一状态源

Given 一个活动 Change，
When 审计状态写入路径，
Then 只存在一条可写路径且每条写入都有对应事件记录；第二套状态文件为只读，任何写入尝试被拒绝。

### 8.3 AC-MVP-13 审批不阻塞状态库

Given 系统正在等待 H1 原生审批，
When 另一个请求读取状态或尝试写入，
Then 读取正常返回，写入得到可区分的明确结果，且审批超时后状态库无残留锁。

### 8.4 AC-MVP-14 回退可检出

Given 事件链与快照被同时回退到较早版本，
When 读取状态，
Then 系统检出并拒绝继续，输出明确的失败码，而不是静默接受较早状态。

### 8.5 AC-MVP-15 冻结测试不可偷换

Given 测试已冻结并已通过红色基线，
When 在实现或验证阶段尝试整体替换冻结测试，
Then 系统拒绝直接替换；若走显式流程，则必须回到红色基线之前的检查点并重跑红色基线。

### 8.6 AC-MVP-16 公开面与发行包可断言

Given 核心 MCP 启动与一张发行包，
When 断言公开工具清单、静态加载图与包依赖清单，
Then 三者均不含可选模块入口与仅服务可选模块的依赖，且断言以完整清单比对方式通过。
