## 1. 文档状态与授权边界

用户要求先只读扫描、通过交互对话框澄清功能及非功能需求，经确认后新建需求文档，未批准前严禁变动。完成三轮澄清后，用户明确选择：**“确认候选内容，仅批准新建需求文档”**。

本次授权仅覆盖新建本文件。它不授权修改源码、测试、配置、既有需求或计划、SG 权威状态，也不授权开发实施、安装工具、创建业务 Change、提交、推送、发布或部署。本文件不代替运行时 H1/H3 回执，不宣称需求已通过 SG 状态机冻结。

第 2 节是用户逐项确认的决策；后续条款将这些决策展开为可审阅的需求与验收标准。尚未逐项讨论的参数和策略集中列于第 10 节，不因文档写入批准而视为已确认。本文不覆盖或修改既有冻结需求、批准计划及仓库规则；后续实施前需要显式处理与本方向冲突的旧约束。

## 4. 目标与首期范围

目标是让存量仓库先被理解，再在用户确认的需求基线、计划、权限和资源预算下推进工作流。

首期包括：

- 单仓库内不同语言、技术栈、模块组织方式的只读识别与候选需求基线，不强制同时具有前端和后端。
- 优先发现仓库原有构建、静态检查、格式检查、测试及运行验证命令，按需要补充能力。
- Windows/Linux x64 上的按需环境复用、安装方案审批和安装后真实复验。
- 四类核心变更的需求澄清、计划、开发、验证、Review 和交付流程。
- 一个已批准计划范围内的动态多 agent 调度，以及按影响范围组织验证。

首期不要求将依赖/框架升级、安全专项、性能专项、数据迁移、独立补测试任务、独立文档/配置/CI 任务、交付后再交付、紧急热修复/回滚、同仓库多个 Change 并行、多仓库联动分别建设为专门工作流。四类核心变更附带的相关工作仍需在已批准范围内处理，不得以此绕过审批。

“任意技术栈可扫描”不代表“任意技术栈已具备完整自动执行能力”。缺少适配、运行依赖、外部服务或认证时，必须说明能力缺口，不伪造通过。

Codex 仍是本分支唯一宿主；跨操作系统不等于新增其他 AI 宿主支持。

## 5. 功能需求

### FR-01 技术栈无关的只读发现

扫描应依据仓库真实内容识别语言、框架、构建系统、包管理器、锁文件、模块边界、入口、测试、CI 配置及已有文档，不要求用户先选择固定技术栈，不要求业务工具链先全部安装完成。

不能仅凭目录名称判断模块或角色；同一仓库可具有多种语言与多个模块。未知技术栈应输出可确认的观察和缺口，不直接拒绝整个分析阶段。识别阶段不自动运行仓库脚本、安装依赖、生成业务模板或改写代码。

验收标准：

- AC-01：没有 Maven、Vue 或 React 的仓库可获得扫描结果，不因缺少这些组件直接被拒绝。
- AC-02：纯后端、纯前端、CLI、库及同仓库多模块样例能够表达各自实际结构，不补造不存在的前后端模块。
- AC-03：缺少业务工具链时仍能完成能力范围内的只读分析，并明确列出无法识别、无法验证及未扫描部分。

### FR-02 从存量证据建立候选需求基线

扫描应形成技术画像、模块/功能清单、可观察行为、接口及数据结构线索、测试覆盖线索、已知问题、冲突和待澄清问题。候选需求需要能追溯到文件、符号、已有文档、测试或真实运行证据，并记录分析对应的仓库版本或内容快照标识。

必须区分：静态观察到的实现行为、推断的业务意图、真实执行验证的行为、用户确认的目标要求。测试文件存在不等于测试已运行，代码现状也不自动等于正确需求。相互冲突的证据不能静默合并。

验收标准：

- AC-04：候选需求能查看来源及证据类别，模型推断不显示为用户确认。
- AC-05：仅静态读取测试时，该行为不被标为运行验证通过；没有文档或测试时明确标记缺口。
- AC-06：用户可确认、纠正或拒绝推断；基线修订保留历史，不覆盖原始证据。
- AC-07：需求基线与构建/测试执行基线分别表达，不以生成需求文档冒充建立了真实执行基线。

### FR-03 按任务发现并复用兼容环境

所需能力应从项目事实和拟执行任务推导，覆盖构建、静态分析、格式化、测试及代码走查实际需要的工具。优先发现环境变量、PATH、常见安装位置、用户缓存及项目已有工具，检查版本、架构、项目约束与实际可运行性。

发现必须有界，不能为“扫描本机所有依赖”无条件遍历整盘。仓库已有命令、包装器、版本约束与锁文件应作为环境计划的依据；具体工具优先级在设计阶段确定。

验收标准：

- AC-08：兼容工具已存在时复用其真实路径与版本，不重复下载安装。
- AC-09：工具存在但不兼容时列为不兼容，不因文件存在便判环境通过。
- AC-10：只读检查不下载、不安装、不修改系统或项目环境配置。
- AC-11：只准备当前任务需要的能力，不安装全部已知技术栈工具。

### FR-04 受批安装、隔离配置与真实复验

缺项时生成具体安装方案，展示任务用途、组件、版本、来源、校验方式、位置、配置变动与权限要求。按 D07 批量批准后执行，优先用户目录或项目隔离环境；系统级安装、提权或来源变化重新申请审批。

安装批准不能替代宿主实际权限。安装成功后重新探测，并对后续任务的真实可用性分别验证。失败、权限拒绝、取消、校验异常或无法联网时保留已完成结果和阻塞原因，不自动放宽来源或权限。

验收标准：

- AC-12：未取得对应方案授权前不发生下载安装或环境配置写入。
- AC-13：执行与批准的版本、来源、位置或权限不一致时，不沿用旧授权继续。
- AC-14：安装命令成功但复验失败时，环境状态仍不能通过。
- AC-15：环境通过与项目构建、测试、Review 通过分别报告。

### FR-05 跨平台能力与引导边界

首期真实验收 Windows/Linux x64。工具发现、命令执行、路径处理和安装方式应隔离操作系统差异，架构预留 macOS/ARM64，不写成通用流程中的固定平台命令。

必须区分 SG 自身的启动依赖与业务工具链。当前 MCP 由 Node 启动，不能要求尚未启动的 MCP 自行修复全部前置条件；缺少启动依赖时需要明确的宿主引导或阻塞反馈，具体方案见第 10 节。

验收标准：

- AC-16：Windows/Linux x64 各有真实发现、复用、缺项准备和复验记录；不得互相代替验收。
- AC-17：macOS/ARM64 在未完成真实支持与验收前明确标为预留或未验证。
- AC-18：MCP 无法启动、宿主权限不足或认证缺失时给出可区分的原因，不声称环境已就绪。

### FR-06 四类变更采用对应的验证策略

| 场景     | 需求重点                                   | 验证要求                                                                 |
| -------- | ------------------------------------------ | ------------------------------------------------------------------------ |
| 新增功能 | 新增能力、边界、失败路径、与既有功能的关系 | 验证目标能力原本缺失，实施后满足 AC；已有回归用例保绿。                  |
| 修改功能 | 当前行为、目标行为、兼容性和受影响范围     | 对目标行为变化形成前后证据，维护无关回归；不要求所有既有用例先失败。     |
| 修复 bug | 实际行为、预期行为、复现条件和影响         | 真实复现目标故障，修复后同一目标断言通过；基础设施错误不能冒充业务故障。 |
| 重构     | 允许调整的内部结构、不变的对外行为和约束   | 建立重构前后的行为保持证据；不为满足全红而人为破坏已正确行为。           |

文档、配置及其他附带工作采用与其性质相符的检查。每项验证标明目的、执行方式、适用范围和结果。测试修改需要明确的角色与授权边界，不允许实现方通过放弱断言或偷换冻结测试取得通过。

验收标准：

- AC-19：重构需求可以合法进入工作流，不必伪装成新增功能或故意制造全红。
- AC-20：新增或修复的目标用例失败、既有回归用例通过时，不因回归没有失败而拒绝有效基线。
- AC-21：超时、缺依赖、进程异常或未运行不能冒充已观察到的业务缺陷。
- AC-22：纯模块变更不被强制附加无关的前端、后端、HTTP 或数据模型任务。

### FR-07 从冻结输入形成可调度计划

计划以已确认需求、冻结文档和适用的项目计划/里程碑为依据，表达任务目标、REQ/AC 关联、模块、输入输出、依赖、文件权限、共享资源、验收方式及风险。按真实模块和依赖拆分，不能只按 AC 数量机械复制前后端任务。

用户批准计划与资源预算后，SG 可在批准边界内细分任务、调整执行顺序和并发。任务细分不能扩大父任务权限、改变 AC、放松验证或越过里程碑门禁。改变需求、契约承诺或资源预算时重新申请审批，并保留计划版本与变更原因。

验收标准：

- AC-23：独立模块能够产生可并行任务，存在依赖的任务等待前置结果。
- AC-24：无效依赖、循环依赖或缺少必要输入的任务不会被派发。
- AC-25：任务可追溯到批准输入；自动调整仅限既定需求、权限与预算范围。

### FR-08 动态多 agent 执行与资源约束

调度应综合复杂度、任务依赖、里程碑、文件归属、契约稳定性、共享资源、宿主能力及执行反馈，决定串行或并行，并说明决策依据。不能简单按任务数等比例增加 agent。

默认遵守 D08。4 是执行 agent 的上限，不是必须启动数量，也不代表宿主保证提供 4 个槽位。角色数量与执行实例数量分别表达，不能让并发破坏测试设计、实现及 Review 的独立性。

并发任务需有隔离的工作区和可追溯结果；集成冲突回到具体任务处理，不能覆盖用户修改或静默丢弃分支结果。最终对统一集成提交生成验证和 Review 证据。

验收标准：

- AC-26：宿主剩余能力少于 4 时按实际可用能力调度，不伪造并发会话。
- AC-27：文件权限冲突、资源互斥或未稳定的共享接口被识别后，相关任务协调或串行执行。
- AC-28：达到获批时限或预算边界时保存进度，停止启动新任务并请求调整，不通过反复重启隐性突破预算。
- AC-29：集成结果绑定具体任务、输入版本、agent 会话与提交；最终验证不拼接不同提交的通过结果。

### FR-09 按影响范围验证与真实闭环验收

常规变更根据场景、风险、依赖和影响范围选择验证集合，解释为什么运行这些检查及哪些区域没有覆盖。关键版本或工作流内核变化执行真实完整闭环，不能用合成 fixture 冒充真实业务仓库、用户审批或角色会话。

金丝雀样例应将业务行为目标、既有回归和运行约束分开建模，减少重复准备及无效返工。业务生产灰度发布属于独立可选流程，不因本文件批准而自动执行。

验收标准：

- AC-30：常规变更不无条件附加完整业务金丝雀，但必须展示验证选择及其依据。
- AC-31：达到关键版本或内核变化触发条件时，缺少真实闭环证据不得宣称对应验收通过。
- AC-32：已经成立的工具链自检、历史保留等约束不被错误要求先变成业务失败。
- AC-33：技术验证、人工验收、归档、推送和生产部署分别报告。

### FR-10 验证证据与审批边界

沿用可信审批、版本化输入、冻结资产保护、独立 Review 及提交绑定证据的原则。未运行、跳过、取消、超时或不可用的检查不能显示为通过；缺少验证适配时明确说明缺口。

需分别表达格式检查和会写文件的格式化动作，不能把自动发现的 `format` 脚本一律当作只读检查。格式化产生新提交后，遵守当前冻结要求，在该提交完整重跑质量门；不得仅因本次引入影响分析就默默放宽旧要求。

验收标准：

- AC-34：仅存在脚本、报告模板或生成文档，不能生成执行通过结论。
- AC-35：修改后的提交不能直接复用修改前的 PASS；未覆盖或不适用均附依据。
- AC-36：写入需求文档、批准需求、批准实施计划、批准安装及批准交付分别表达，不相互代替授权。
