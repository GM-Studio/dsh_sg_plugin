## 1. 反向复述与澄清

### 1.1 对用户意图的复述

我的理解是：

1. **Codex 是执行主体**。规划、编码、测试、修复、验证、交付准备全部由 Codex 自行完成，控制面**不参与、不编排、不替代** Codex 的思考与执行。
2. **控制面是观测者与把关者**。它负责：启动 Codex、接收 Codex 上报的事件、在 Codex 主动请求人工时把请求转发给人、记录人的决策、再让 Codex 继续。
3. **「监督」的边界是「只观察 + 预算熔断」**（方案 A）。控制面只在数值型预算超限或执行异常（失败/失联）时介入；不对 Codex 的业务判断做主动干预，不自动改 prompt 重试。
4. **人工只需处理「Codex 举手」的时刻**。正常执行不打扰；只有 H1/H3 审批、信息不足、无法继续等关键节点才触达。
5. **触达方式是「消息 + 跳转链接」**，不做 IM 内的交互式卡片审批。消息负责把人叫醒，真正的裁决在 Web 管理台完成。
6. **实现方式是增量修改现有 Node 方案**，复用已验证的状态机、版本 CAS、幂等键、文档指纹与 step-up 能力。

### 1.2 必须防止的错误理解

- 「控制面监督」**不等于**控制面可以打断或改写 Codex 的工作。
- 「WebUI 实时监控」**不等于**展示模型完整思维链或全部原始输出；监控的是可解释、可审计的执行事实。
- 「异步审批」**不等于**把同步等待搬到网页上；等待期间必须释放执行资源。
- 「消息里点按钮」**不等于**完成审批；消息链接只是入口，审批仍需服务端授权与权威状态。
- 「在现有 Node 上改」**不等于**可以降低安全要求；现有四条安全保证必须继续有效。

## 3. 产品行为定义

### 3.1 职责边界（核心）

| 事项             | Codex                | 控制面                | 人工        |
| ---------------- | -------------------- | --------------------- | ----------- |
| 决定怎么做       | ✅ 全权              | ❌ 不参与             | ❌ 不参与   |
| 写代码/测试/修复 | ✅ 全权              | ❌ 不参与             | ❌ 不参与   |
| 判断是否需要人工 | ✅ **由 Codex 举手** | ❌ 不预设门禁         | ⚠️ 被通知方 |
| 记录事件         | 产出事件流           | ✅ 接收、脱敏、存储   | 只读        |
| 预算熔断         | —                    | ✅ **唯一主动干预点** | 事后可上调  |
| 审批/取消/修改   | 等待                 | ✅ 记录决策并续跑     | ✅ 决策方   |

> **红线**：控制面不得因「觉得 Codex 跑偏」而中断或改写执行；唯一允许的主动中断是预算超限，或执行已失败/失联。

### 3.2 人工触达时机

仅在以下情况触达人工，其余一律静默：

| 类型                 | 触发者 | 场景                  |
| -------------------- | ------ | --------------------- |
| `H1_APPROVAL`        | Codex  | 需求确认门禁          |
| `H3_APPROVAL`        | Codex  | 发布审批门禁          |
| `CLARIFICATION`      | Codex  | 信息不足需补充        |
| `BLOCKED`            | Codex  | 无法继续              |
| `BUDGET`             | 控制面 | 预算超限（数值判断）  |
| `FAILED` / `OFFLINE` | 控制面 | 执行失败 / 宿主机失联 |
| `COMPLETION`         | Codex  | 交付完成待确认        |

**静默规则**：常规进度、阶段性自测通过、内部重试一律不通知。

### 3.3 触达形式

采用**消息 + 跳转链接**，不做 IM 内交互式卡片审批。

- 飞书：交互卡片，按钮 = 打开管理台深链（现有 `feishu.js` 已实现）。
- 钉钉：ActionCard（`singleTitle/singleURL` 或 `btns[]{title,actionURL}`），**仅需群自定义机器人 webhook，不要求企业应用**。
- 消息内容只包含：类型、标题、摘要、风险、跳转链接；**不含源码、绝对路径、密钥**。

## 4. 需求条目

### 4.1 观测与监控（O 系列）

#### O1 事件持久化

- **行为**：Codex 运行期间产出的 JSONL 事件，经脱敏后按 Run 持久化；Run 结束后仍可回看。
- **约束**：只存解释性事实，不存完整思维链原文；单事件与单 Run 均有字节上限；入库前必须走现有 `redact`；超期清理不得影响审计所需的决策记录。
- **验收**：Run 结束后可经 API 取回事件序列；任意事件不含密钥与绝对路径；超限时按策略截断并标记。

#### O2 执行时间线视图

- **行为**：管理台为每个 WorkItem/Run 提供时间线，展示阶段、命令执行、文件变更、工具调用、举手点、决策点。
- **约束**：按业务语义呈现（图标 + 中文描述），不直接倾倒原始 JSON。
- **验收**：打开已完成的 Run 能看懂「做了什么、在哪一步停了、谁批的」。

#### O3 实时推送

- **行为**：状态与事件变化经 SSE 推送前端；断线自动重连，并回退轮询兜底。
- **约束**：推送负载同样脱敏；单连接限流。
- **验收**：状态变更 ≤1s 到达；断网重连后自动补齐；推送内容与查询接口一致。

#### O4 用量与预算可视

- **行为**：展示当前 Run 的耗时、token 用量、工具调用数、预算占比。
- **依据**：`turn.completed` 事件自带 `usage`。
- **验收**：数值与实际 `usage` 一致；接近上限时界面明确提示。

### 4.2 触达（N 系列）

#### N1 多渠道通知

- **行为**：同一注意力可投递到配置的多个渠道（飞书、钉钉，企业微信可选）。
- **约束**：任一渠道成功即视为已送达；部分失败不阻断其余；密钥不出现在任何 Web 响应。
- **验收**：单渠道故障时其余仍送达；重复 Run 不产生重复消息。

#### N2 钉钉渠道

- **行为**：经**群自定义机器人 webhook** 发 ActionCard，按钮 URL 指向管理台深链。
- **约束**：仅出站；**不要求企业内部应用、卡片模板、企业认证**。
- **验收**：配置 webhook 后能在钉钉群看到卡片；点击按钮能打开对应注意力页面。

#### N3 深链令牌

- **行为**：消息链接携带一次性/短时效凭证。
- **约束**：链接可能被留存或转发，**高风险操作不得仅凭链接完成**（见 S2）。
- **验收**：令牌过期或已消费后，链接无法再次进入授权态。

#### N4 提醒与升级

- **行为**：注意力超时未处理时按间隔提醒，临期升级渠道或通知备份人，过期发失效通知。
- **约束**：不得重复轰炸；提醒次数有上限。
- **验收**：`REMINDED` 状态被真实推进；过期后原链接明确提示失效。

### 4.3 审批与安全（S 系列）

#### S1 审批复用现有链路

- **行为**：所有裁决仍汇聚到既有 `service.decide()` 与 `attentionNeedsStepUp` 策略。
- **约束**：**不得**新增绕过指纹校验、版本 CAS、幂等键的旁路。
- **验收**：现有审批回归测试全部通过；新增渠道产生的决策与 Web 产生的决策在状态机中不可区分（除 `source` 字段）。

#### S2 分层授权红线

- **必须 Web + TOTP step-up**：H1/H3 的 `approve`、`cancel`、`accept_delivery`。
- **可仅凭会话**：`pause`、`resume`、`retry`、`request_changes`。
- **验收**：未通过 step-up 的 H1 批准被拒绝，且失败原因可审计。

#### S3 事件脱敏与最小暴露

- **约束**：事件入库与消息投递前必须脱敏；云端不存完整源码 diff 与绝对路径；不得把模型思维链原文写入任何持久化介质。
- **验收**：注入含密钥/路径的样例事件，入库与消息中均被剥离。

### 4.4 跨机执行（W 系列，可选阶段）

> 仅当控制面与执行机分离部署时启用。**首版可与执行同机，不启用本节。**

#### W1 本地执行器主动拉取

- **行为**：执行机作为 worker **主动出站**领取任务、续租、上报事件、提交结果、查询决策。
- **约束**：云端**从不主动连入**本地；本地无需公网 IP、端口映射或域名。
- **验收**：本地仅出网即可工作；关闭本地后任务排队，上线后自动领取。

#### W2 一致性与补偿

- **约束**：租约以**云端时钟**判定；事件断线本地队列重连补传并去重；同一 WorkItem 不得被两台机器同时领取。
- **验收**：断网 1 分钟后恢复，事件不丢不重；双 worker 场景不重复执行。

#### W3 worker 权限隔离

- **约束**：worker 使用**独立令牌**，不得复用用户配对令牌；只能操作绑定自身 id 与白名单项目的任务。
- **验收**：越权领取被拒绝并审计。

## 6. 验收口径

### 6.1 功能验收

| 场景                 | 期望结果                                                                   |
| -------------------- | -------------------------------------------------------------------------- |
| Codex 正常跑完无门禁 | **全程零通知**；WebUI 可见完整时间线                                       |
| Codex 举手 H1        | 飞书+钉钉各收到 1 条；点击跳到对应注意力页；**执行进程已退出、租约已释放** |

| 人工要求修改         | 决策带上修改意见；续跑提示词含该意见                                       |
| 人工取消             | 不续跑；状态终态正确                                                       |
| 预算超限             | 执行中断；产生 `BUDGET` 注意力；可选择上调续跑                             |
| 宿主机失联           | 超时后判 `OFFLINE`，产生注意力并通知                                       |
| 注意力超时未处理     | 按间隔提醒 → 临期升级 → 过期发失效通知                                     |
| 消息链接被转发给他人 | 高风险操作仍需 TOTP，无法仅凭链接批准                                      |

### 6.2 安全验收

| 项       | 期望                                                   |
| -------- | ------------------------------------------------------ |
| 指纹校验 | 文档变更后旧审批失效，返回 `APPROVAL_ARTIFACT_CHANGED` |

| 幂等     | 同一 `idempotencyKey` 重复提交只生效一次               |
| step-up  | 未过 TOTP 的 H1/H3 批准被拒                            |
| 脱敏     | 事件、消息、Web 响应中均无密钥与绝对路径               |

## 8. 风险与约束

1. **事件量**：高频事件（delta 流）会造成存储膨胀。**只存`item.started`/`item.completed`等离散事件，不存逐字 delta**。
2. **敏感信息**：事件可能含代码片段。入库前脱敏 + 上限截断，云端不存完整 diff。
3. **钉钉门槛**：群自定义机器人 ActionCard 无需企业应用；若后续需要更强能力再评估企业内部应用，**本需求不依赖**。
4. **跨机时钟**：租约一律以控制面时钟判定。
5. **交互卡片不做的代价**：用户需多跳一次网页。经评估可接受，换取免企业资质。
