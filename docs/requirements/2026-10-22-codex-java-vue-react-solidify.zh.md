## 1. 反向复述与澄清

### 1.1 对用户意图的复述

我的理解是：

1. 目标不是继续铺新技术栈，而是把 Java + Vue/React 这一条链打磨到"接单即可
   交付"的稳定程度。
2. 建项目时必须能交互选择 JDK 大版本（8/17/21）和前端框架（Vue 3 或
   React 18），选择结果要成为项目的固化事实，后续变更只能在该事实内工作。
3. 初始化不能只给"能跑起来的空壳"，而要给一个**完整的小型管理系统脚手架**：
   用户、角色、菜单、权限、审计、分页、导入导出、仪表盘等常见后台能力，
   前后端都要有，且能直接构建、测试、运行。
4. 这套脚手架同时是**风格与实现参考基线**：后续 change 的表单、列表、权限、
   i18n、异常处理、测试写法都要向它对齐，而不是每个单子各写一套。
5. 一人团队会同时接多个客户项目，控制面要能**聚合看全局**，也要能**按项目
   隔离**部署与运行。
6. 工作流不能绑死在某个 Codex 版本上：能力可用就用，不可用就明确降级或明确
   拒绝，不能"看起来在跑实际没跑"。
7. 交付可信度只在 **Windows 与 Linux 双平台都真实验证通过**时成立；Linux 必须
   在真实环境中验证，而不是只写一份步骤文档。

### 1.2 必须防止的错误理解

- "做牢一条栈"不等于把模板写死，用户仍必须能就 JDK 与前端做出选择，并且选择
  必须被下游强制。
- "完整脚手架"不等于把所有业务都塞进去；它必须领域中立，避免把某个客户的
  业务语义焊进模板。
- "风格基线"不等于限制表达；它约束可观测的一致约定（结构、命名、分层、
  i18n、错误处理、测试），不约束具体业务实现。
- "多项目"不等于同项目内并行多变更；同一项目仍维持单活动 Change 语义。
- "不依赖 Codex 版本"不等于忽略能力差异；必须探测能力并给出确定行为。
- "双平台通过"不等于只运行一次构建；必须覆盖真实构建、真实运行与真实测试。
- "交付文档"不等于可以直接开工；文档批准前不写任何源码。

## 2. 产品定位

### 2.1 一句话定位

> 把一条 Java + Vue/React 的全栈交付链做实：会选型、有标杆脚手架、有强制
> 风格基线、能聚合管多项目、能在任意可用 Codex 与双平台上稳定跑完交付闭环。

### 2.2 产品职责

SpecGate 负责：

- 在建项目时提供 JDK 与前端框架的交互选择，并把选择固化为项目事实。
- 生成领域中立的完整管理系统脚手架，作为参考实现与风格基线。
- 在 change 工作流中强制项目已选的栈与风格基线。
- 提供跨项目聚合与按项目隔离两种控制面承载方式。
- 探测宿主 Codex 能力并按能力提供确定行为，而非按版本号猜测。
- 在 Windows 与 Linux 上产出可审计的双平台验收证据。

Codex 负责：

- 理解代码与业务目标。
- 按项目已选栈与风格基线实现 change。
- 在缺失能力时按明确降级路径使用项目级 MCP 与技能。

### 2.3 产品不是

- 不是多技术栈通用脚手架平台。
- 不是 Web IDE 或远程 shell。
- 不是多租户 SaaS 或企业项目组合管理平台。
- 不是把全部业务模块预置进模板的业务框架。
- 不是绕过 H1/H3、证据门禁或交付记录要求的自动化工具。

## 3. 第一性原理与不变量

1. 选型是项目事实，必须一次确定并全程强制，不能在后续变更中静默漂移。
2. 脚手架是"可运行的参考实现"，不是"生成即完成"；它自身必须被真实验证。
3. 风格基线的价值在于一致，一致必须可检查、可阻塞，否则不成立。
4. 多项目的第一需求是"看见全局"；隔离是第二需求，两者不可互相替代。
5. 宿主能力必须被探测，不能被假设；能力缺失必须产生确定而非模糊的结果。
6. 验收证据必须来自真实环境；单平台通过不能推导出跨平台可用。
7. 现有状态机、证据链、审批与交付语义保持不变，本次只在其上加宽输入面与
   承载面。

## 4. 技术栈矩阵与选择

### 4.1 第一/二阶段矩阵

- 前端：Vue 3（现有）与 React 18（新增）。
- JDK：8、17、21。
- 后端：Spring Boot，随 JDK 档位绑定（Java 8 → Spring Boot 2.7.18；Java 17/21
  → Spring Boot 3.5.x）。
- Spring Boot 4.0 预览档在本阶段不纳入矩阵。

### 4.2 React 侧默认技术选型

- 构建：Vite。
- 语言：TypeScript。
- 路由：React Router。
- 状态：Zustand。
- UI：Ant Design。
- 国际化：react-i18next。
- 测试：Vitest + Testing Library。

### 4.3 前端一致性要求

- Vue 与 React 两套脚手架必须共用同一后端契约、同一菜单结构、同一交互流与
  同一 i18n key 集合。
- 两侧应使用等价组件库以保证视觉与交互对齐。
- 同一业务能力的页面在两个前端上应呈现等价的信息层级与操作路径。

### 4.4 选择方式

- 选择在 Codex 会话交互中完成，作为 `sg_init_preview` / `sg_init` 的入参。
- 选择结果写入 `ProjectProfile`，成为项目固化事实。
- 未提供选择时使用显式默认值，且默认值必须在结果中可见。

## 5. 初始化脚手架：完整小型管理系统

### 5.1 领域

领域中立后台系统，预置模块至少包含：

- 用户、角色、部门、菜单、权限。
- 审计日志。
- 列表分页、条件查询。
- 导入导出（至少 CSV）。
- 仪表盘/概览。

### 5.2 前后端都要完整

- 后端：分层完整（controller/service/repository/entity/dto/vo）、统一响应
  与错误处理、统一追踪、安全与本地账号、参数校验、分页封装、导入导出服务、
  单元与接口测试。
- 前端：路由、布局、菜单、权限控制、状态管理、API 层、i18n、通用列表/表单
  组件、错误与空态处理、测试。

### 5.3 生成规范（沿用现有约定）

- 包名 `com.<company>.<business>`，由 `sg_init` 参数提供；禁止生成
  `com.example.*`。
- 源码文件使用中文文件说明与业务注释。
- 展示文本通过 i18n key 提供，默认 `zh-CN`，保留 `en-US` 运行时切换。
- 生成物自身必须可构建、可测试；生成不等于验证。

### 5.4 参考基线作用

- 脚手架同时是后续 change 的参考实现：新功能的分层、命名、错误处理、分页、
  导入导出、i18n、测试写法必须向它对齐。

## 6. 风格与实现基线（强制）

- 交付两类基线：
  1. 可运行的脚手架源码。
  2. 独立的风格指南文档（结构、命名、分层、错误码、i18n、测试、提交约定）。
- Reviewer 在审查时以该基线为判据；明确偏离且无正当理由的，可报 blocking。
- 偏离必须给出显式理由并记录，不能静默放过。

## 7. 人工交互选择与门禁

- 选择发生在 `sg_init_preview` / `sg_init` 交互中。
- 选择写入 `ProjectProfile` 并纳入基线证据。
- change 工作流必须强制：React 项目只能派发 React 前端 agent 与依赖，Vue
  项目同理。
- 栈不匹配、缺依赖或版本不符必须在实现前 fail closed，而不是运行时才发现。

## 8. 多项目控制面

### 8.1 聚合模式

- 单 daemon + 项目注册表，一个控制台聚合展示所有项目。
- 首页提供跨项目注意力视图与跨项目队列。
- 提供全局并发上限。

### 8.2 隔离模式

- 每个项目可有独立 control home 与端口。
- 提供一条命令在聚合与隔离之间切换。

### 8.3 其他

- Web 会话与配对在控制面重启后仍可用（沿用 8 小时会话、15 分钟配对）。
- 项目之间不共享 MCP 配置与凭据。

## 9. Codex 版本兼容与能力探测

- 启动时探测能力：`plugin`、`exec --json`、原生 subagents、elicitation。
- 能力缺失时按明确降级路径运行（项目级 MCP + 技能），不静默失败。
- 保留版本门槛提示：低于门槛时给出明确拒绝与升级指引，但判断依据是能力而非
  版本号字符串。
- 探测结果必须可查看（例如 `doctor` 输出），并区分"已具备/缺失/未探测"。

## 10. 平台与真实环境验收

- 支持平台：Windows 与 Linux。
- Linux 验收环境：VMware Ubuntu 24.04 LTS 真机/虚拟机。
- WSL 不计入验收证据。
- 工具链优先复用本机已安装的 JDK/Maven/Node；缺失时给出明确指引，不静默
  下载。
- 每个模板组合的 golden 验收必须 Windows + Linux 双通过才算 verified。

## 11. 与现有语义的兼容

- 沿用现有状态机、事件溯源、CAS、证据链、H1/H3、DeliveryRecord、客户接受与
  增量再交付语义。
- 不新增第二套交付记录或第二套真相。
- 增量再交付的影响分析（AC 复用/失效）应接入 `sg_change` 入口，使其真正可用。
- `doctor` 增强为能力探测输出。

## 12. 功能需求

### 12.1 技术栈与脚手架

#### FR-001 交互式选型

系统 MUST 在建项目时允许用户选择 JDK 大版本与前端框架，并在结果中回显实际
生效的选择。

#### FR-002 矩阵覆盖

系统 MUST 支持 Vue3+React18 与 JDK 8/17/21 的组合生成。

#### FR-003 选择固化与强制

系统 MUST 将选择写入 `ProjectProfile`，并在后续 change 中强制栈匹配；不匹配
MUST fail closed。

#### FR-004 领域中立脚手架

系统 MUST 生成领域中立的完整后台系统脚手架，覆盖 FR-005 所列模块。

#### FR-005 前后端齐备

脚手架 MUST 同时包含完整后端与完整前端，且两者能联调运行。

#### FR-006 生成规范

系统 MUST 使用 `com.<company>.<business>` 包名、中文源码说明、默认 `zh-CN`
的 i18n，且 MUST NOT 生成 `com.example.*`。

#### FR-007 脚手架可验证

脚手架生成结果 MUST 能通过真实构建、真实测试与真实运行验证。

#### FR-008 双前端等价

Vue 与 React 两套脚手架 MUST 共用同一后端契约、菜单与 i18n key，并呈现等价
交互。

### 12.2 风格基线

#### FR-009 基线交付

系统 MUST 同时交付可运行脚手架与独立风格指南文档。

#### FR-010 强制审查

Reviewer MUST 能以风格基线为判据报告 blocking；偏离 MUST 有显式理由与记录。

### 12.3 多项目控制面

#### FR-011 项目注册表

系统 MUST 维护多项目注册表，使一个控制台可管理多个项目。

#### FR-012 聚合视图

系统 MUST 提供跨项目注意力首页与队列视图。

#### FR-013 隔离模式

系统 MUST 支持每项目独立 control home 与端口，并提供切换命令。

#### FR-014 全局并发

系统 MUST 提供可配置的跨项目全局并发上限，默认不超过既有并发语义。

#### FR-015 会话持久

Web 会话与配对 MUST 在控制面重启后仍然有效。

#### FR-016 项目隔离

不同项目 MUST NOT 共享 MCP 配置或凭据。

### 12.4 Codex 兼容

#### FR-017 能力探测

系统 MUST 探测 `plugin`、`exec --json`、原生 subagents、elicitation 能力。

#### FR-018 降级路径

能力缺失时系统 MUST 按明确路径降级（项目级 MCP + 技能），MUST NOT 静默失败。

#### FR-019 版本门槛提示

系统 MUST 在能力不足时给出明确拒绝或降级说明与升级指引。

#### FR-020 探测可见

系统 MUST 使能力探测结果可查看，并区分"已具备/缺失/未探测"。

### 12.5 平台验收

#### FR-021 双平台门

每个模板组合 MUST 在 Windows 与 Linux 均通过后才标记 verified。

#### FR-022 工具链复用

系统 MUST 优先复用本机已安装工具链，缺失时给出指引且 MUST NOT 静默下载。

#### FR-023 Linux 真实环境

Linux 验收 MUST 在真实（虚拟）系统中执行，MUST NOT 以 WSL 替代。

## 13. 非功能需求

### NFR-001 一致性

- 选择、栈强制、风格基线在三处（生成、change、Review）使用同一事实来源。
- 聚合与隔离模式对同一项目显示同一业务事实。

### NFR-002 性能与时间预算

- 初始化生成 SHOULD 在分钟级完成，不追求秒级。
- 单 WorkItem 与单验证阶段沿用既有时间预算并可配置。
- 聚合控制台首屏 SHOULD 在 2 秒内返回。

### NFR-003 并发与资源

- 全局并发上限可配置，默认与既有 `maxConcurrent` 一致。
- 磁盘与日志占用上限沿用既有约定；归档后清理工作树并保留证据。
- 任一项目耗尽预算不得影响其他项目。

### NFR-004 安全

- 新脚手架的客户交付包沿用既有脱敏规则，隐藏路径、凭据与内部内容。
- 项目间凭据与 MCP 隔离。
- 无法完成能力/授权校验时 fail closed。

### NFR-005 可维护性

- 模板与栈矩阵必须可扩展：新增前端框架或 JDK 档位不应改动工作流内核。
- 风格基线以文档 + 可检查规则表达，避免散落在代码中的隐式约定。

### NFR-006 可移植性

- 在 Windows 与 Linux 上使用同一套生成与验证契约，不引入仅单平台可用的绝对
  路径假设。
- 不新增依赖具体 Codex 版本号的代码分支。

### NFR-007 成本

- 双平台验收与全矩阵验证应有明确的执行脚本，避免人工重复操作。
- 自动修复不得无限重试，沿用既有重试上限。

### NFR-008 数据保留

- 交付记录、审批与客户接受长期保留。
- 模板验收记录（templateHash + 双平台结果）可追溯。

### NFR-009 兼容性

- 不破坏现有 tool 契约与既有测试；新增能力以增量方式提供。
- 现有项目无需重生成即可继续使用，除非其栈不在新矩阵内。

## 14. 核心验收场景

### AC-001 交互选型生效

- GIVEN 用户新建项目
- WHEN 用户选择 JDK 21 与 React
- THEN 生成的 `ProjectProfile` 记录该选择
- AND 生成物为 React 前端 + JDK 21 后端

### AC-002 栈强制

- GIVEN 一个 React 项目
- WHEN 执行 change
- THEN 只派发 React 前端 agent 与依赖
- AND 越界依赖或栈不匹配时 fail closed

### AC-003 脚手架完整可跑

- GIVEN 生成一个组合的脚手架
- WHEN 执行真实构建、测试与运行
- THEN 前端与后端均通过
- AND 预置模块（用户/角色/菜单/权限/审计/分页/导入导出/仪表盘）可用

### AC-004 风格偏离被阻塞

- GIVEN 一次 change 的实现违反风格基线
- WHEN Reviewer 审查
- THEN Reviewer 可报告 blocking
- AND 若无正当理由则该 round 不得通过

### AC-005 聚合多项目

- GIVEN 多个项目存在
- WHEN 用户打开聚合控制台
- THEN 可看到跨项目待办与队列
- AND 全局并发上限生效

### AC-006 隔离模式

- GIVEN 需要按项目隔离
- WHEN 用户使用切换命令选择隔离模式
- THEN 该项目使用独立 control home 与端口
- AND 不影响其他项目的状态

### AC-007 能力降级

- GIVEN 宿主 Codex 不支持 `plugin`
- WHEN 启动工作流
- THEN 系统按项目级 MCP + 技能路径运行
- AND 明确报告降级，不静默失败

### AC-008 版本门槛

- GIVEN 宿主能力不足
- WHEN 用户尝试启动交付
- THEN 系统给出明确拒绝或降级说明与升级指引

### AC-009 双平台验收

- GIVEN 一个模板组合
- WHEN 在 Windows 与 Linux 各完成一次真实验证
- THEN 记录同一 templateHash 的双平台结果
- AND 仅在两者均通过时标记 verified

### AC-010 全流程冒烟

- GIVEN 新生成的项目
- WHEN 执行 `sg_init` → `sg_verify` → 一次完整 change → `sg_release_archive`
- THEN 全流程通过
- AND 该流程可由脚本重复执行

### AC-011 会话跨重启

- GIVEN Web 控制台已建立会话
- WHEN 控制面重启
- THEN 会话与配对仍可用（在有效期内）

### AC-012 项目隔离

- GIVEN 两个项目分别配置
- WHEN 其中一个项目运行
- THEN 不共享 MCP 配置与凭据
- AND 不影响另一个项目的执行

## 15. 指标与发布门槛

### 15.1 指标

- 每个栈组合在双平台的端到端通过率。
- 从"选择栈"到"首个可运行脚手架"的耗时。
- 脚手架生成后首次真实构建/测试通过率。
- change 中风格偏离被 Review 捕获的比例。
- 多项目聚合下跨项目故障隔离有效性。
- 能力探测的准确率（探测结果与真实行为的偏差）。

### 15.2 发布门槛

- 每个组合在 Windows 与 Linux 均通过端到端验收。
- 全流程冒烟脚本可重复执行且稳定。
- 无能力误判导致的"看起来在跑实际没跑"。
- 现有测试、lint、format、pack 与 smoke 全绿。

### 15.3 停止扩张条件

出现以下任一情况应优先修复而非继续扩张：

- 新增组合导致既有组合回归。
- 风格基线长期无法被检查执行。
- 多项目聚合引入状态串扰。
- 能力探测与真实行为持续不一致。
