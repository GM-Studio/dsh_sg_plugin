# SpecGate v3.8 需求：`/sg-init` 三种入口与“确认前零变动”

- 文档 ID：V3.8-REQ-001
- 状态：已确认（2026-10-19）
- 基线：v3.7.0（277 项测试通过）
- 决策来源：2026-10-19 对话第 1–10 轮问答
- 验证方式：本需求先落文档，再按第 10 节切片实现；实现后跑全量 `node --test`

## 0. 一句话

把 `/sg-init` 从“表单盘问 + 问答失败静默降级”改成：

**导入 / 描述 / 对话三种入口 → 宽松但确定的校验 → Agent 逐维澄清 → 单页确认（= H0）→ 一次性落盘到 H1_PENDING**，

并且**确认前项目目录零字节变化，任何问答失败都必须中止而不是自动确认**。

## 1. 现状与问题（可核对）

| # | 问题 | 证据 |
|---|---|---|
| P1 | `/sg-init` 完全忽略参数，无法 `-req`，也无法接自由文本 | `src/v3/commands.js` 的 `sg-init` handler 不读 `inv.rawInput` |
| P2 | 只有 `userQuestions` 表单式四维盘问，不能导入已有需求文档 | `collectRequirements` |
| P3 | **问答失败会静默用示例默认值，确认失败会 `autoConfirmed` 直接落盘** | `collectRequirements` 的 `catch`；`confirmInit` 第 0 轮失败返回 `autoConfirmed: true` |
| P4 | 确认前已经写 `.specgate/config.yaml`、`state.json`、`init-result.json`、`env-report.md` | `initProject` 与命令 handler |
| P5 | 只生成 `openspec/REQ.md`（REQ-xxx），没有模板化、人类可读的 FR/NFR/AC 文档 | `renderRequirementsDoc` |
| P6 | 没有“基于模板生成真实需求文档”的入口 | 无 |

**实证**：`java_demo/.specgate/init-result.json` 为 `"autoConfirmed": true`，需求是示例占位，正是 P3 的产物。

## 2. 目标

- **G1 三种入口**：`-req <文档>`、`<自由描述>`、无参纯对话。
- **G2 可校验**：需求文档先校验，再进入初始化；不合格明确报错。
- **G3 Agent 主导澄清**：AI 在对话框逐维追问，而不是一次性表单。
- **G4 单页确认 = H0**：需求文档 + 技术栈同页确认，确认后直接进入 `H1_PENDING`。
- **G5 确认前零写 + fail-closed**：确认前不写任何项目文件；问答不可用/取消/异常一律中止。
- **G6 幂等与兼容**：已初始化项目重复执行零写入；现有 277 项测试不回归。

## 3. 术语

| 术语 | 含义 |
|---|---|
| 需求文档 | `docs/requirements/REQ.md`，模板格式（FR/NFR/AC），人类可读，**不是**工作流基线 |
| 需求基线 | `openspec/REQ.md`，`REQ-xxx` 连续编号 + `AC-xxx covers`，由需求文档派生 |
| 澄清提纲 | `sg_init` 返回给 Agent 的模板、维度问题、当前草稿、缺失项 |
| 确认页 | 唯一人工确认点：完整需求文档 + 技术栈 + 将写入文件清单 + 自动补全/告警 |
| 零写 | 项目根下不 create/modify/delete 任何文件，含 `.specgate/`、`openspec/`、`docs/`、`.gitignore`、git index |

## 4. 三种入口与统一流程

| 入口 | 调用 | 行为 |
|---|---|---|
| A 导入 | `/sg-init -req <path>` 或 `sg_init({ req })` | 读取 → 宽松解析 → 最低校验 → 缺维度由 Agent 追问 → 技术栈 → 确认 |
| B 描述 | `/sg-init 我想做……` 或 `sg_init({ description })` | 以描述为种子 → Agent 逐维追问 → 生成需求文档草稿 → 校验 → 技术栈 → 确认 |
| C 对话 | `/sg-init` 或 `sg_init()` | 无种子 → Agent 从背景/目标开始逐维追问 → 同上 |

统一状态机：

```text
未初始化
  └─ CLARIFY（零写，可多轮；Agent 主导）
       └─ VALIDATE（零写；不合格 → 返回缺失项，继续 CLARIFY）
            └─ STACK（技术栈问答，零写）
                 └─ CONFIRM（单页；= H0）
                      ├─ 确认 → COMMIT → H1_PENDING
                      ├─ 修改需求/技术栈/其他 → 回到对应步骤（仍零写）
                      └─ 取消/异常 → 中止，零写
```

## 5. 功能需求

### FR-1 三种入口与参数解析

- 命令：`/sg-init`、`/sg-init <自由文本>`、`/sg-init -req <path>`；`-req` 与自由文本互斥，同时出现报 `E_ARGS_CONFLICT`。
- 工具：`sg_init({ req?, description?, draft? })`，三者互斥；空对象等价于无参。
- 路径相对项目根解析；允许绝对路径；只读，不修改源文件。
- 命令与工具行为一致，错误码一致。

### FR-2 需求文档模板

- 模板固定为插件自带 `assets/templates/requirements/REQUIREMENTS.zh.md`（英文环境用 `REQUIREMENTS.md`）。
- 章节固定：目标与范围、术语、功能需求、非功能需求、验收标准、约束/假设/不做范围、变更记录。
- frontmatter 至少含：`document`、`version`、`status`、`updated_at`；生成时追加 `source`、`source_sha256`。
- 功能需求用 `FR-xxx`，非功能用 `NFR-xxx`，验收用 `AC-xxx`，每条 AC 带 `- covers: FR-xxx`。

### FR-3 `-req` 宽松解析与最低校验

解析规则：

- 支持 Markdown 标题、列表、`### FR-001`/`### NFR-001`/`### AC-001` 形式；按关键词识别四个维度（功能/非功能/约束/验收，含英文同义词）。
- 识别不到功能章节时，把所有顶层列表项当作“功能候选”，并在确认页标记“待归类”。
- 编号保留；重复编号按出现顺序重编，并在确认页列出“重编清单”。
- 验收标准缺失时，每条功能自动补 `实现并通过自动化测试：<标题>`，并在确认页标记“自动补全”。
- AC 的 `covers` 优先按声明关联；未声明时按顺序关联；多条 AC 指向同一功能时合并进该功能的验收描述并告警。

最低校验（不满足即失败，零写）：

| 错误码 | 条件 |
|---|---|
| `E_REQ_NOT_FOUND` | 路径不存在 |
| `E_REQ_NOT_FILE` | 不是普通文件 |
| `E_REQ_UNREADABLE` | 无读权限 / 读取失败 |
| `E_REQ_TOO_LARGE` | 超过 1 MiB |
| `E_REQ_ENCODING` | 非 UTF-8（允许 BOM） |
| `E_REQ_EMPTY` | 去空白后为空 |
| `E_REQ_NO_FUNCTIONAL` | 抽不出至少 1 条功能需求 |

非功能、约束、验收缺失**不算失败**，进入对话补齐。

### FR-4 Agent 主导澄清协议

- 有 `userQuestions` 通道时，`sg-init` 主动打开对话框逐维追问（功能→非功能→约束→验收），用户可自定义输入；没有通道时才返回 `phase: "CLARIFY"`（载荷含模板、四维问题、种子、草稿、`missing`、`nextQuestions`、`protocol`、`limits`），交给 Agent 继续。两条路径都**不写任何文件**。
- Agent 在聊天中一次问 1–2 个问题，顺序：背景/目标 → 功能 → 非功能 → 约束 → 验收；每维回答后先复述再进入下一维。
- 每维最多 6 轮，总计最多 12 轮；用户说“够了/直接生成”立即停止追问。
- 信息不足时不得用示例默认值填充；只能标记 `missing` 继续问，或由用户明确确认“该维度留空”（草稿 `confirmedEmpty`）。
- Agent 收集完成后调用 `sg_init({ draft })`；草稿结构见 §8。

### FR-5 草稿校验与自动补全

- 功能需求至少 1 条且标题非空，否则 `E_DRAFT_INCOMPLETE`。
- 非功能、约束允许为空，但必须在 `confirmedEmpty` 中声明；否则视为 `missing` 返回 `CLARIFY`。
- 验收标准可缺省；缺省时按功能顺序自动补 1 条 AC；提供但数量不匹配时，缺的自动补、多的保留为“额外 AC”，并告警。
- 技术栈必填；Java 组合沿用现有 `validateJavaSelection` 矩阵校验。
- 所有校验错误一次性返回，带 `code`、`message`、必要时 `path`/`line`。

### FR-6 技术栈采集

- 沿用现有 `collectContext` 的问题与选项（node/python/vue/react/monorepo/generic/java + Java 子项）。
- 草稿已带 `context` 时作为推荐值；用户仍可在确认页选“修改技术栈”重答。
- 问答通道不可用 → `E_QUESTIONS_UNAVAILABLE`，零写。

### FR-7 单页确认（= H0）

确认页必须包含：

1. 完整需求文档（模板格式，含自动补全与重编标记）。
2. 技术栈与 Java 组合摘要。
3. 将写入的文件清单（见 FR-8）。
4. 告警/待定项列表。

选项：`确认` / `修改需求` / `修改技术栈` / `修改其他确认点` / `取消`。

- 仅 `确认` 进入写入。
- `修改需求` 返回 `CLARIFY`（保留当前草稿，零写）。
- `修改技术栈` 回到 FR-6（零写）。
- `修改其他确认点` 重问背景/团队/实施步骤（零写）。
- `取消`、关闭、异常、超时 → `E_CONFIRM_CANCELLED` / `E_QUESTIONS_UNAVAILABLE`，零写。
- 确认时计算 H0 产物哈希（文档 + 上下文）并记录为 H0 批准（确认页即 H0）。

### FR-8 确认后落盘与基线派生

确认后按顺序写入：

1. `docs/requirements/REQ.md`：模板格式；frontmatter `status: approved`、`source`、`source_sha256`、`updated_at`；已有同名文件时**不覆盖**，改用 `REQ.v1.0.md`，并在确认页提前说明。
2. `openspec/REQ.md`：`REQ-xxx` 连续编号（功能 → 非功能 → 约束），`AC-xxx` 每条带 `- covers: REQ-xxx`；头部记录 `derived_from: docs/requirements/REQ.md` 与哈希。
3. `openspec/history/v1.0/REQ.md`：与基线逐字一致。
4. `.specgate/config.yaml`：`requirements.enabled: true`、`version: v1.0`、`doc: openspec/REQ.md`。
5. `.specgate/state.json`：`phase: H1_PENDING`、`context`、`requirements`、`requirementsSource`、`h0 { hash, approvedAt }`；**state 最后写**。
6. `.specgate/init-result.json`：审计用，已 gitignore。
7. 新项目：脚手架 + 首个 change `add-version` + `git init/commit`。

中途失败：state 不推进，重跑可从断点续写；错误信息列出已完成/未完成项。

### FR-9 一次性初始化到 H1_PENDING

- 新项目确认后：写需求资产 → 生成脚手架 → 创建 `add-version` → `H1_PENDING`。
- 既有项目确认后：只写需求资产与配置，**不生成脚手架** → `H1_PENDING`。
- 不再需要单独 `sg_approve H0`；H0 哈希与批准时间在确认页确认时写入。
- `sg_approve H0` 在已进入 H1 后调用，返回“已在初始化确认页批准”，不重复写。

### FR-10 确认前零写与 fail-closed

- 确认前禁止任何写操作（含 `.specgate/`、`openspec/`、`docs/`、`.gitignore`、git index）。
- 只读允许：项目文件、`-req` 指定的项目外文件。
- 删除 `autoConfirmed` 分支；删除“问答异常用默认值”的降级。
- 任何问答不可用、异常、超时、拒绝 → 返回错误码并中止，**绝不落盘**。
- Agent 对话中断时天然零写（草稿只在对话/tool 载荷里）。

### FR-11 幂等与已初始化项目

- 已初始化且 `phase >= H1_PENDING` 或存在 change → 直接返回当前阶段与需求来源，**零写**。
- `phase == H0_PENDING` 且尚无 `openspec/REQ.md` → 允许带 `-req`/`draft` 重跑，替换草稿；无参数则提示先用 `/sg-context --reset`。
- 并发调用沿用现有锁；第二个调用返回 `E_LOCKED`。
- `/sg-context --reset` 清空 H0 批准与上下文，回到可重新澄清状态。

### FR-12 审计、状态与兼容

- `/sg-status` 增加：需求文档路径、来源、版本、H0 批准时间、是否自动补全。
- 错误信息统一 `{code, message, fix}`；不把需求全文写日志。
- 更新 `README.md`、`CHANGELOG.zh.md`、`README.en.md`、模板与测试。
- 旧的无参 `/sg-init` 行为由“表单盘问”改为“Agent 对话引导”；命令文本与工具描述同步更新。

## 9. 错误码

| 错误码 | 含义 |
|---|---|
| `E_ARGS_CONFLICT` | `-req` 与自由文本同时出现 |
| `E_REQ_NOT_FOUND` / `E_REQ_NOT_FILE` / `E_REQ_UNREADABLE` | 文件不可用 |
| `E_REQ_TOO_LARGE` / `E_REQ_ENCODING` / `E_REQ_EMPTY` | 内容不可用 |
| `E_REQ_NO_FUNCTIONAL` | 无功能需求 |
| `E_DRAFT_INCOMPLETE` | 草稿缺功能/缺确认留空声明 |
| `E_QUESTIONS_UNAVAILABLE` | 问答通道不可用 |
| `E_CONFIRM_CANCELLED` | 用户取消 |
| `E_CONFIRM_LIMIT` | 确认轮回超过 6 轮 |
| `E_ALREADY_INITIALIZED` | 已初始化且不可重跑 |
| `E_LOCKED` | 并发锁 |
| `E_WRITE_FAILED` | 落盘失败 |

## 10. 影响面与实现切片

**影响文件**：

## 11. 决策记录

| # | 决策 | 选择 |
|---|---|---|
| 1 | `-req` 校验强度 | 宽松解析：能抽出功能/非功能即可，缺维度由对话补齐 |

| 3 | 确认前变动 | 零落盘 + 失败即中止 |

## 12. 风险与兼容

1. **H0 语义变化**：确认页即 H0 后，新项目不再需要 `sg_approve H0`；老项目与已处于 H0_PENDING 的项目需要兼容路径。
2. **既有 autoConfirmed 项目**（含当前 `java_demo`）：不静默改写；需要 `/sg-context --reset` 或手工清理后重跑。
3. **`docs/requirements/REQ.md` 已存在**：不覆盖，改用 `REQ.v1.0.md`，并在确认页提前说明。
4. **Agent 协议依赖 Agent 遵循指令**：`CLARIFY` 返回里带明确 `protocol`，并在 `sg-status` 暴露未完成澄清状态。
5. **一次性初始化写脚手架**：确认页会列出将写入的文件；用户仍可在确认前取消。

## 13. 明确不做

- 不支持 PDF/Word/URL 作为 `-req` 输入（只支持本地 Markdown/文本）。
- 不做需求文档的后续增量合并（留给 `sg-change`/delta）。
- 不自动迁移已 autoConfirmed 的历史项目。
- 不改变 H1/H2/H3 既有门控语义。
- 不引入网络依赖或新的第三方库。
