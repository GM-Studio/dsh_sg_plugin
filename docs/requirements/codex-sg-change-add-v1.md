# Codex 原生 SG 工作流 v1 需求文稿

> 文档状态：**已批准，未实施**  
> 版本：v1.0  
> 批准日期：2026-10-21  
> 适用范围：Codex 原生插件首版 `sg-init`、`sg-verify`、`sg-change --add`  
> 实施状态：**未进入实施；未修改代码、配置、测试或 Git 状态**

---

## 1. 文档目的

本文档定义将 SpecGate（SG）现有工作流能力迁移到 Codex 原生插件后的首版需求。

本文档是后续技术设计和实施计划的基线。批准本文档不等于批准实施；实施前仍需单独输出计划并取得用户确认。

---

## 2. 背景

SpecGate 当前是 DSH host plugin，已具备 Java/Vue 初始化、需求、计划、任务、测试、审查、worktree、证据和归档等基础能力。

现状与目标之间仍存在以下差距：

- `sg_change` 只接收 change 名称，没有 `--add` 语义；
- 需求阶段是固定四维问答，不是独立需求 Agent 的深度澄清；
- 没有独立的反向复述和批判 Agent；
- Plan 主要校验已有任务，不是根据冻结需求动态拆分；
- 执行角色是 `implementer / tester / reviewer`，不是前端开发、后端开发、测试、审查四个角色；
- 没有完整的“开发前冻结测试用例”流程；
- Review 只有单一模式，没有宽松、标准、严格三档；
- 根编排不能稳定完成前后端并行、测试、Review 和自动推进；
- 审批、状态并发控制、取消和恢复仍需加强；
- 当前归档不会自动推送远端。

---

## 3. 目标

实现一个 Codex 原生插件工作流，支持一人团队完成全栈项目落地：

```text
sg-init
  → 生成 Java + Vue 全栈脚手架和示例 CRUD
  → sg-verify 真实验证初始化模板

sg-change --add
  → 模糊需求输入
  → 需求澄清
  → 反向复述与批判
  → 用户 H1 审批
  → 需求冻结
  → 动态拆分任务
  → 测试用例和测试骨架冻结
  → 前端/后端 Agent 并行开发
  → 合并到 integration worktree
  → 格式化、静态检查、单元/接口/集成/冒烟测试
  → Review Agent 三档审查
  → 用户最终审批
  → 自动归档、commit、合并、推送
```

核心目标是：

1. 人只在关键节点审批、修改、取消，其余由 AI 驱动和执行；
2. 首版先跑通 `init + change-add` 端到端闭环；
3. 前后端分离、快速开发、快速反馈；
4. 所有关键结果都有真实证据，不把生成或推断当作验证通过。

## 4. 首版范围

### 4.1 首版包含

- `sg-init`
- `sg-verify`
- `sg-change --add`
- 需求澄清 Agent
- 需求批判 Agent
- 动态 Plan
- 测试用例生成与冻结
- 前端开发 Agent
- 后端开发 Agent
- Test Agent
- Review Agent
- 独立 worktree
- 结构化状态事件
- H1 需求冻结审批
- H3 最终 Review 审批
- 自动归档、commit、合并、推送
- 无 remote 时的本地归档和明确提示
- 暂停、恢复、取消

### 4.2 首版不包含

- `change-update`
- `change-delete`
- 多个 active change 并行
- DSH 与 Codex 双端同时运行
- 专用 UI 任务看板
- 自动创建 PR
- 强制浏览器 E2E
- 多仓库或 submodule 拓扑
- React、Node 全栈等其他技术栈
- 任意项目自动 adopt
- force push
- 自动下载大型 SDK 或项目本地归档

## 5. 核心原则

1. 需求冻结前不得开发。
2. 测试用例和测试骨架必须在开发前生成并冻结。
3. 前端和后端可以并行，但必须先冻结接口契约。
4. 生成成功不等于验证通过。
5. 只有真实命令和运行时结果才能作为通过证据。
6. 模型只能发起审批，不能自己批准。
7. 所有状态变更、测试结果、Review 结论和归档动作必须可审计。
8. 任何失败都不得静默跳过。
9. 不允许 Agent 直接修改主工作树或目标分支。
10. 首版优先保证 `init + change-add` 闭环，不追求一次覆盖所有变更类型。

## 6. 目标架构

### 6.1 插件形态

首版采用 Codex 原生插件：

```text
Codex Plugin
├── Skills
│   ├── 需求澄清
│   ├── 反向复述与批判
│   ├── 动态计划
│   ├── TDD 与测试设计
│   ├── 代码审查
│   ├── 验证
│   └── 归档
├── MCP Server
│   ├── 状态机
│   ├── 门控
│   ├── 审批
│   ├── 任务图
│   ├── 证据
│   ├── worktree 管理
│   └── Git/归档控制
├── Codex Subagents
│   ├── 前端开发
│   ├── 后端开发
│   ├── 测试
│   └── 审查
└── Hooks / 状态事件
    └── 主 Agent 状态同步
```

### 6.2 职责边界

- **Skills**：承载方法、检查清单和流程知识，不承载权威状态。
- **MCP Server**：承载权威状态、合法状态迁移、门控、审批、证据和操作控制。
- **Subagents**：执行具体开发、测试和审查任务。
- **Hooks / 事件**：负责上下文注入、状态通知和审计，不作为唯一安全边界。
- **Codex 用户审批通道**：提供可信的人工审批来源。
- **模型参数和普通对话文本**：不能作为自签审批凭据。

### 6.3 运行方式

- 首版使用本地 stdio MCP Server；
- 状态和证据保存在项目 `.specgate/`；
- 插件代码和项目状态分离；
- 不使用云端 MCP Server；
- 不长期驻留后台 HTTP 服务。

### 6.4 子 Agent 方式

使用 Codex 原生 subagents，由主 Agent 调度。

首版固定角色：

- 前端开发 Agent；
- 后端开发 Agent；
- Test Agent；
- Review Agent。

Plan 由主 Agent 使用 Plan Skill 完成，不新增独立 Plan 子 Agent。

## 7. 角色与职责

### 7.1 主 Agent

负责：

- 解析用户命令；
- 调用 MCP Server；
- 驱动状态机；
- 创建和调度子 Agent；
- 汇总状态；
- 在人工门暂停；
- 处理失败、阻塞、取消和恢复；
- 触发归档和推送。

主 Agent 不直接替代开发、测试和审查 Agent。

### 7.2 需求 Agent

负责：

- 接收模糊需求；
- 进行最多 3 轮澄清；
- 每轮最多提出 5 个高价值问题；
- 覆盖功能需求、非功能需求、约束、验收标准、边界条件和失败场景；
- 记录用户回答、假设和修改；
- 形成需求草案；
- 识别阻断性未决问题。

### 7.3 需求批判 Agent

负责：

- 反向复述需求；
- 检查需求是否被正确理解；
- 识别歧义、矛盾、遗漏和不合理点；
- 分析可实现性、成本、风险和替代方案；
- 检查安全、性能、并发、兼容性和可观测性；
- 输出结构化批判报告；
- 提出继续澄清的问题。

### 7.4 Plan

负责：

- 根据冻结需求动态拆分任务；
- 先产生接口契约和数据模型任务；
- 契约冻结后拆分前端和后端任务；
- 建立任务依赖图；
- 映射需求 AC、测试用例和负责角色；
- 标记可并行任务；
- 生成执行计划。

### 7.5 前端开发 Agent

负责：

- 只修改前端 worktree；
- 实现 Vue 页面、组件、状态管理和 API 客户端；
- 遵循冻结契约；
- 不修改测试资产；
- 不直接修改主工作树或目标分支；
- 完成后提交到自己的分支；
- 向主 Agent 汇报状态。

### 7.6 后端开发 Agent

负责：

- 只修改后端 worktree；
- 实现 Java API、领域逻辑、持久化和错误处理；
- 遵循冻结契约；
- 不修改测试资产；
- 不直接修改主工作树或目标分支；
- 完成后提交到自己的分支；
- 向主 Agent 汇报状态。

### 7.7 Test Agent

负责：

- 在开发前生成测试用例和可执行测试骨架；
- 冻结测试资产；
- 开发完成后执行测试；
- 维护测试配置和测试夹具；
- 只写测试相关文件，不修改生产代码；
- 生成真实测试报告和覆盖率证据；
- 发现生产缺陷时退回对应开发 Agent。

### 7.8 Review Agent

负责：

- 只读审查，不修改代码；
- 根据冻结需求审查实现；
- 按宽松、标准、严格三档输出结论；
- 生成结构化审查报告；
- 为每个 finding 提供文件、行号、严重级别、需求映射、证据和修复建议；
- 不直接提交修复。

## 8. 初始化：`sg-init`

### 8.1 命令形态

同时提供：

```text
/sg-init [--preset <preset>] [path]
```

和 MCP 工具：

```text
sg_init({
  path,
  preset
})
```

### 8.2 技术矩阵

完整迁移 SG 的四档 Java/Vue 技术矩阵：

| Preset | JDK | Spring Boot | 构建 | 前端 |
|---|---|---|---|---|
| `jdk8-boot2.7` | Java 8 | 2.7.18 | Maven | Vue 3 + TypeScript + Vite + npm |
| `jdk17-boot3.5` | Java 17 | 3.5.16 | Maven | Vue 3 + TypeScript + Vite + npm |
| `jdk21-boot3.5` | Java 21 | 3.5.16 | Maven | Vue 3 + TypeScript + Vite + npm |
| `jdk21-boot4.0` | Java 21 | 4.0.0 preview | Maven | Vue 3 + TypeScript + Vite + npm |

规则：

- 默认 preset 为 `jdk8-boot2.7`；
- `jdk8-boot2.7` 必须提示 legacy 维护风险；
- `jdk21-boot4.0` 必须提示 preview 风险；
- 不引入多版本前端栈；
- 版本矩阵和模板 hash 必须可查询。

### 8.3 初始化产物

至少生成：

- Java/Spring Boot 后端脚手架；
- Vue 3/TypeScript/Vite 前端脚手架；
- 示例 Task CRUD；
- 常见接口代码和错误处理；
- H2 文件持久化；
- OpenAPI 文档；
- 前后端基础页面；
- 测试配置和示例测试；
- 格式化、lint、typecheck 配置；
- `README`、安全说明和 API 文档；
- 初始需求基线 `REQ v1.0`；
- `.specgate/config.yaml`；
- `.specgate/monorepo.json`；
- `.specgate/init-report.json`；
- 模板风格和模板 hash；
- Git 基线 commit 和 `init-baseline` tag。

### 8.4 非空目录处理

默认目标是空目录。若目标非空：

1. 先扫描目标目录；
2. 输出：
   - 已存在文件；
   - 将新增文件；
   - 冲突文件；
   - 将被覆盖文件；
   - 将被保留文件；
   - 当前 Git 状态；
3. 用户必须通过可信审批确认覆盖策略；
4. 用户不确认时：
   - 不执行初始化；
   - 不修改任何文件；
   - 明确提示“目录非空，初始化未执行”。

覆盖规则：

- 默认只补齐缺失文件，不覆盖已有业务文件；
- 冲突文件必须逐项确认；
- 已有 `.specgate/` 默认拒绝重新初始化；
- 不静默删除或覆盖用户代码。

### 8.5 生成与验证分离

`sg-init` 的默认行为保持与 SG 一致：

- 只生成；
- 建立 Git 基线；
- 状态为 `GENERATED_ONLY`；
- `initializationComplete = false`；
- 不安装依赖；
- 不编译；
- 不启动服务；
- 不声称验证通过。

### 8.6 `sg-verify`

提供独立的：

```text
/sg-verify
```

和 MCP 工具 `sg_verify`。

验证内容至少包括：

- 工具链发现；
- 后端依赖安装；
- 后端编译；
- 后端单元测试；
- 后端静态检查；
- 后端格式检查；
- 前端依赖安装；
- 前端构建；
- 前端单元测试；
- 前端 lint；
- 前端格式检查；
- 启动后端；
- 启动前端；
- 健康检查；
- 基础冒烟测试；
- 覆盖率对账。

只有真实命令成功并产生证据，才能标记验证通过。

### 8.7 首版验证验收范围

- 四个版本档都必须在 Windows 完成真实验证；
- Linux 记录为未验证，不作为首版阻断项；
- 不得把 Linux 未验证写成矩阵完整通过；
- 如果本机缺少工具链，明确标记未验证，不自动下载大型 SDK。

## 9. `sg-change --add`

### 9.1 命令形态

同时提供：

```text
/sg-change --add [change-name] "需求描述"
```

和 MCP 工具：

```text
sg_change_add({
  name,
  request
})
```

规则：

- `name` 可选；
- 未提供时由 AI 生成稳定 slug；
- 已存在 active change 时直接拒绝；
- 不自动排队；
- 用户必须显式取消或完成当前 change 后，才能创建下一个；
- 首版不支持 update/delete 类型。

### 9.2 前置条件

`sg-change --add` 必须满足：

1. 项目已由 `sg-init` 初始化；
2. 已执行 `sg-verify` 并存在真实验证证据；
3. Git 工作树 clean；
4. 未跟踪文件也视为不 clean，除非被 `.gitignore` 排除；
5. 不存在其他 active change。

不满足时必须拒绝，并说明具体原因。

## 10. 状态机

### 10.1 主流程

```text
REQ_INTAKE
  → REQ_CLARIFYING
  → REQ_CRITIQUE
  → H1_PENDING
  → REQ_FROZEN
  → PLANNING
  → TEST_DESIGN
  → TEST_CASES_FROZEN
  → DEVELOPING
  → INTEGRATING
  → TESTING
  → REVIEWING
  → H3_PENDING
  → ARCHIVING
  → ARCHIVED
```

### 10.2 旁路状态

```text
BLOCKED
PAUSED
CANCELLED
PUSH_FAILED
ARCHIVED_NOT_PUSHED
ROLLBACKING
```

### 10.3 人工门

首版只保留两个业务人工门：

- **H1：需求冻结审批**
- **H3：最终 Review 报告审批**

不设置 H2 计划审批门。

规则：

- Plan 和测试用例自动生成，但必须完整展示；
- H1 未通过，不得进入 Plan；
- H3 未通过，不得归档；
- 用户可以在 H1 和 H3 选择批准、修改或取消；
- 需求或 Review 内容变化后，旧审批自动失效。

### 10.4 自动推进

主 Agent 自动推进到下一个门或阻塞点：

- 需求澄清和批判完成后自动进入 H1；
- H1 通过后自动进入 Plan；
- 测试用例冻结后自动进入开发；
- 前后端开发完成后自动进入集成；
- 集成完成后自动进入测试；
- 测试通过后自动进入 Review；
- Review 完成后进入 H3；
- H3 通过后自动归档。

## 11. 需求阶段

### 11.1 澄清

需求 Agent 最多进行 3 轮访谈，每轮最多 5 个问题，覆盖：

- 功能需求；
- 非功能需求；
- 业务约束；
- 技术约束；
- 验收标准；
- 边界条件；
- 失败场景；
- 安全、性能、并发和兼容性。

### 11.2 未决问题

- 非阻断问题可以带“显式假设 + 风险 + 待确认项”进入 H1；
- 阻断性问题必须解决，不能冻结；
- 不允许 AI 静默补全关键需求；
- 所有问答、假设和修改写入需求修订历史。

### 11.3 批判报告

必须结构化输出：

- 需求反向复述；
- 歧义点；
- 矛盾点；
- 不可实现或高成本点；
- 遗漏的非功能需求；
- 安全、性能、并发风险；
- 测试盲区；
- 建议澄清问题；
- 每条结论对应的需求引用。

### 11.4 需求冻结

H1 通过后：

- 生成不可变需求快照；
- 记录需求 hash；
- 记录审批人、时间、意见和审批 hash；
- 开发开始前发现问题，可以创建新需求修订版；
- 开发开始后需求变化，默认新建关联 change；
- 不覆盖旧版本；
- 旧审批自动失效。

---

## 12. Plan 与任务拆分

Plan 根据冻结需求动态生成，不预设固定任务数量。

必须包含：

- 接口契约任务；
- 数据模型任务；
- 后端任务；
- 前端任务；
- 测试任务；
- 集成任务；
- Review 前置检查；
- 文档更新任务。

规则：

- 先冻结接口契约和数据模型；
- 契约冻结后，前端和后端任务并行；
- 最大并行开发任务数为 2；
- 每个任务必须映射到：
  - 需求 AC；
  - 测试用例；
  - 负责角色；
  - 依赖任务；
  - 验收条件；
- 任务图、计划 hash 和执行计划写入 `.specgate/`；
- Plan 不单独设置人工审批门，但必须完整展示给用户；
- 实施计划先在对话中展示，用户确认后再落盘到 `docs/plans/`。

## 13. 测试用例冻结

Test Agent 在开发前生成：

- 人类可读测试用例；
- 可执行测试骨架；
- 测试数据或夹具；
- AC 与测试用例映射；
- 覆盖率目标。

规则：

- 测试用例和测试代码在开发前冻结；
- 记录测试资产 hash；
- 前端和后端开发 Agent 不允许修改测试资产；
- 测试资产有缺陷时，只能由 Test Agent 发起受控解冻；
- 解冻必须记录原因、变更内容和影响范围；
- 解冻后必须重新冻结并记录新 hash；
- 开发完成后，Test Agent 按冻结用例执行。

首版采用严格 TDD：

```text
冻结测试
  → 测试先失败
  → 开发实现
  → 测试通过
  → 不允许先写实现再补测试
```

## 14. Worktree 与分支

### 14.1 仓库拓扑

首版采用单仓库：

```text
repo/
├── backend/
└── frontend/
```

不使用多仓库或 submodule。

### 14.2 Worktree

至少包含：

- 主工作树；
- 前端开发 worktree；
- 后端开发 worktree；
- integration worktree；
- test worktree；
- review worktree。

规则：

- 每个角色只操作自己的 worktree；
- 任何 Agent 不得直接修改主工作树或目标分支；
- 前后端从同一个契约冻结 commit 创建分支；
- 前后端分支先合并到 integration 分支；
- Test Agent 在 test worktree 中检出 integration 分支执行测试；
- Review Agent 在 review worktree 中检出待审 commit 执行审查；
- 冲突退回对应开发 Agent 修复；
- 主 Agent 负责合并和状态推进；
- 取消后保留 worktree、分支、证据和日志，不自动删除。

## 15. 开发阶段

前端和后端并行开发：

```text
契约冻结
  → 前端 Agent 在 frontend worktree 开发
  → 后端 Agent 在 backend worktree 开发
  → 各自格式化
  → 各自运行局部检查
  → 合并到 integration
```

开发 Agent 必须：

- 遵守冻结契约；
- 不修改测试资产；
- 不修改其他角色 worktree；
- 提交自己的分支；
- 汇报任务开始、完成、失败和阻塞；
- 对失败任务最多自动重试 2 次。

## 17. Review 阶段

### 17.1 三档模式

**宽松**

- 只阻断 P0/P1；
- 重点检查需求覆盖、明显功能错误、安全和数据破坏风险。

**标准**

- 阻断 P0/P1/P2；
- 检查需求覆盖、接口契约、错误处理、测试充分性和可维护性。

**严格**

- 阻断 P0/P1/P2/P3；
- 额外检查安全、性能、并发、可观测性、边界条件和测试盲区。

### 17.2 档位选择

- 默认根据结构化风险信号自动选择；
- 用户可以在 Review 前覆盖档位；
- 任一高风险信号触发严格审查。

风险信号包括：

- 认证或授权；
- 数据删除或迁移；
- 外部网络；
- 文件上传；
- 支付或敏感数据；
- 公共契约变更；
- 新增依赖；
- 跨模块变更；
- 变更规模；
- 测试覆盖不足。

### 17.3 审查报告

必须包含：

- verdict；
- findings；
- 严重级别；
- 文件和行号；
- 需求映射；
- 证据；
- 修复建议；
- 测试结果引用；
- 是否存在阻断项。

Review Agent 只读审查，不修改代码。

### 17.4 Review 失败循环

- 普通代码缺陷：在原 change 内修复、重测、复审；
- 需求级问题或高风险设计问题：新建关联 change；
- 每次循环保留失败报告和修复证据；
- 开发、测试、Review 统一最多自动重试 2 次；
- 超过上限进入 `BLOCKED`。

## 18. 审批安全

### 18.1 审批来源

H1 和 H3 必须通过 Codex 原生可信用户审批/交互能力完成。

模型只能发起审批请求，不能：

- 自己生成审批；
- 通过工具参数伪造审批；
- 通过普通文本冒充用户批准；
- 重复使用旧审批。

### 18.2 审批记录

必须包含：

- 审批人；
- 审批时间；
- 过期时间；
- nonce；
- 被审批对象的 hash；
- 是否已消费；
- 审批意见；
- 审批结果。

### 18.3 审批失效

以下情况旧审批自动失效：

- 需求内容变化；
- Review 报告变化；
- 归档预览变化；
- hash 不匹配；
- 审批过期；
- 审批已消费；
- 审批被重复使用。

所有审批动作写入审计日志。

## 19. 状态、事件与恢复

### 19.1 状态持久化

- 权威状态保存在项目 `.specgate/`；
- 状态写入必须带版本号或 CAS；
- 所有状态变更写入 append-only 事件日志；
- 合法状态迁移由统一迁移表控制；
- 不允许任意跳转状态。

### 19.2 状态事件

主 Agent 至少接收以下结构化事件：

- 任务开始；
- 任务完成；
- 任务失败；
- 测试开始；
- 测试完成；
- Review 开始；
- Review 完成；
- 进入人工门；
- 阻塞；
- 取消；
- 归档完成；
- 推送失败。

首版以文本和结构化事件为主，不做专用 UI 看板。

### 19.3 暂停、恢复和取消

- 用户可以在需求门、执行中、测试中、Review 前暂停或取消；
- 暂停保留状态、worktree、分支和证据；
- 恢复从最后一个稳定检查点继续；
- 取消后保留 worktree、分支、证据和日志；
- 不允许无限循环或静默跳过失败步骤。

### 19.4 重试

- 开发、测试、Review 使用统一重试策略；
- 每个失败任务最多自动重试 2 次；
- 超过后进入 `BLOCKED`；
- 用户可以修复、恢复、取消或新建关联 change。

## 20. 归档与 Git

### 20.1 归档前预览

最终 H3 审批前必须展示：

- 目标分支；
- remote；
- commit；
- 变更摘要；
- 测试结果；
- Review 结果；
- 是否包含未推送提交；
- 是否存在未跟踪文件；
- 是否将覆盖或合并已有提交。

### 20.2 归档动作

H3 通过后自动执行：

1. commit；
2. 合并到目标分支；
3. 推送目标分支；
4. 移动 change 到归档目录；
5. 更新文档归档；
6. 更新任务归档；
7. 写入归档证据。

### 20.3 安全规则

- 永不执行 force push；
- 不自动创建 PR；
- 没有 remote 时：
  - 完成本地归档；
  - 状态标记 `ARCHIVED_NOT_PUSHED`；
  - 明确提示“未推送”；
- 推送失败时：
  - 不自动重试；
  - 不自动执行回滚或继续归档；
  - 状态标记 `PUSH_FAILED`；
  - 保留 worktree、日志、测试证据、失败原因和归档上下文；
  - 由用户明确决定后续动作，例如重试、保留本地归档、回滚或取消；
  - 在用户决定前保持阻塞，不静默改变 Git 状态。

## 21. 非功能需求

### 21.1 平台

- 首要支持 Windows 10/11 + PowerShell；
- macOS/Linux 做兼容性设计，但不作为首版阻断验收项；
- 工具链发现必须有边界、跨平台、优先复用已有安装。

### 21.2 安全

- 不自动下载大型 SDK；
- 不在日志和证据中记录密钥、token、密码；
- 网络访问只发生在依赖安装、推送等明确步骤；
- 审批不能被模型自签；
- 不允许 Agent 直接修改主工作树或目标分支。

### 21.3 可恢复性

- 长任务必须可暂停、恢复和取消；
- 每个阶段必须有稳定检查点；
- 失败必须保留证据；
- 不允许因为进程退出而丢失状态。

### 21.4 可审计性

- 需求、计划、测试、Review、审批和归档都保留版本和 hash；
- 关键命令和运行时结果必须落盘；
- 未执行项必须明确标记，不得写成已通过。

## 22. 验收标准

首版满足以下条件才算完成：

1. 四个 Java/Vue preset 都能生成脚手架和示例 CRUD。

5. `sg-init` 只生成，不把生成状态标记为验证通过。
6. `sg-verify` 能产生真实构建、测试、lint、格式和冒烟证据。
7. `sg-change --add` 支持模糊需求输入和可选 change 名称。
8. 同一仓库同一时间只允许一个 active change。
9. 需求 Agent 最多 3 轮、每轮最多 5 个问题。
10. 需求批判输出结构化报告。
11. H1 通过后生成不可变需求快照和 hash。
12. Plan 能根据冻结需求动态拆分任务。
13. 接口契约任务先于前后端并行任务。
14. 测试用例和测试骨架在开发前冻结。
15. 前端和后端在独立 worktree 并行开发。
16. Test Agent 不修改生产代码。
17. Review Agent 只读审查。
18. Review 支持宽松、标准、严格三档和自动风险选择。
19. 测试达到行覆盖率 80%、分支覆盖率 70%、变更代码覆盖率 90%。
20. P0/P1 缺陷为 0。
21. 静态、单元、接口、集成、冒烟测试全部通过。
22. H3 通过前不得归档。
23. H3 通过后自动 commit、合并、推送。
24. 没有 remote 时完成本地归档并明确提示“未推送”。
25. 永不 force push。
26. 推送失败时不自动重试，保留证据并由用户决定后续动作。
27. 状态写入具备版本控制或 CAS。
28. 所有关键动作有 append-only 事件日志。
29. 暂停、恢复、取消可用。
30. 未执行或失败的检查不得标记为通过。

## 24. 残余风险与约束

7. 推送失败后的回滚、保留或重试由用户决定，系统不得自行选择。
8. 首版不覆盖多 change 并行、PR、E2E 和 UI 看板。
