## 1. 反向复述与产品意图

### 1.1 对用户意图的复述

本产品要解决的不是“如何让 AI 多写代码”，而是：

> 如何让一个人可以放心地把一整条全栈交付链路交给 AI 执行，同时只在关键风险节点做决策。

目标闭环是：

1. 人给出意图、范围和验收标准；
2. Codex 规划、实现、测试、修复和准备交付；
3. 控制面记录执行事实、预算、版本和证据；
4. 只有在需求歧义、风险接受、发布、验收、取消或不可恢复阻塞时，才请求人工介入；
5. 飞书、钉钉负责把人叫醒；
6. 人通过安全的 Web 控制台完成决策；
7. 原 Codex 会话恢复，继续执行或终止；
8. 修复后重新验证，并生成可追溯的交付记录；
9. 全过程可审计、可回放、可再交付。

### 1.2 必须防止的错误理解

- 控制面不是第二个技术负责人，不替 Codex 决定怎么实现。
- WebUI 不是模型思维链查看器，只展示可解释的执行事实和证据。
- 异步审批不是把阻塞进程搬到网页上，等待期间必须释放执行资源。
- 消息按钮不是审批凭据，消息链接不能直接建立管理会话。
- 云端可访问不等于云端可持有源码、凭证或任意执行权限。
- “AI 自动修复”不等于“AI 可以自己修改验收标准并宣布通过”。
- 多 Worker 预留不等于第一版就要做复杂调度平台。

## 2. 产品定位与目标用户

### 2.1 一句话定位

> **一人团队的 AI 交付控制面。**

### 2.2 目标用户

- 一人全栈开发者；
- 独立顾问和小型交付团队负责人；
- 需要 AI 长时间执行，但必须保留关键决策权的人；
- 同时维护多个项目、多个仓库或多个交付任务的人。

### 2.3 核心价值

- 快速开发：减少等待和重复沟通；
- 快速验证：执行结果带真实验证证据；
- 快速反馈：只在需要人时发出有上下文的请求；
- 快速修复：失败后有边界地自动修复；
- 快速再交付：修复、重验和交付形成闭环；
- 跨项目控制：用一个例外收件箱管理多个项目；
- 安全远程决策：消息可达，但授权不依赖消息链接；
- 可回放信任：人能看到 AI 做了什么、验证了什么、自己批准了什么。

### 2.4 第一版不追求

- 多租户 SaaS；
- 计费和订阅；
- 客户自助注册；
- 复杂组织权限；
- 全云端 Codex 执行；
- 多 Agent 编排平台；
- IM 内交互式审批；
- 生产发布自动放行；
- 大规模集群调度。

## 4. 职责边界

| 事项                 | Codex        | 控制面               | 人工     |
| -------------------- | ------------ | -------------------- | -------- |
| 决定如何实现         | 全权         | 不参与               | 不参与   |
| 写代码、测试、修复   | 全权         | 不代替执行           | 不参与   |
| 判断是否需要业务举手 | 主动举手     | 接收并结构化         | 被通知   |
| 不可逆安全动作       | 不得自行放行 | 确定性拦截           | 明确授权 |
| 记录执行事实         | 上报离散事件 | 持久化、脱敏、审计   | 查看     |
| 创建 Attention       | 提出请求     | 校验、冻结版本、通知 | 处理     |
| 做 Decision          | 不代替人     | 记录、校验、应用     | 决策     |
| 恢复执行             | 恢复原会话   | 校验决策后下发       | 不参与   |
| 最终验收             | 提供证据     | 校验证据完整性       | 签字     |

### 4.1 人应该介入

- 初始意图、范围和验收标准；
- H1 需求/范围歧义；
- H3 发布、生产、客户验收；
- 预算、成本或外部依赖升级；
- 不可逆操作和高风险取消/回滚；
- 最终交付接受；
- AI 无法在授权边界内解决的阻塞。

### 4.2 人不应该介入

- 普通编码进度；
- 常规测试失败；
- 预算内的有界自动修复；
- 格式化、风格和普通实现选择；
- 没有实质变化的运行状态；
- AI 已经能够依据既定验收标准解决的问题。

## 5. 端到端工作流

```text
意图 / 范围 / 验收标准 / 预算
              |
              v
      Codex 规划与风险识别
              |
              v
       实现 -> 测试 -> 修复
              |
              v
       真实验证与证据采集
              |
              v
        是否需要人工？
          |          |
         否          是
          |          |
          v          v
     生成交付包   Attention 冻结版本
                     |
                     v
             飞书 / 钉钉通知
                     |
                     v
              安全 Web 决策
                     |
          +----------+----------+
          |          |          |
        批准        修改        取消
          |          |          |
          v          v          v
      恢复原会话  带意见恢复   终止
          |
          v
     重新验证 -> 再交付 -> 闭环通知
```

### 5.1 关键原则

- 每个等待状态释放执行资源；
- 每个 Attention 绑定精确版本和 artifact hash；
- 每个 Decision 幂等；
- 每个失败都有重试、取消或请求变更路径；
- 每个通知有投递记录；
- 每个 Attention 有提醒、升级和过期；
- 每个重要状态可回放；
- 每个交付都能追溯到验证证据。

## 6. 领域对象与状态

### 6.1 核心对象

| 对象                   | 职责                                     |
| ---------------------- | ---------------------------------------- |
| `User`                 | 账号、角色和认证主体                     |
| `Device`               | 已注册设备、撤销状态和最近认证           |
| `Session`              | 绑定用户与设备的会话                     |
| `Project`              | 项目、仓库元数据、Worker 绑定、通知策略  |
| `Worker`               | 本地执行端、令牌、项目白名单、心跳       |
| `WorkItem`             | 目标、范围、验收标准、预算和生命周期     |
| `Run`                  | 一次执行尝试、Codex session、状态和用量  |
| `Attention`            | 为什么需要人、选项、风险、证据和截止时间 |
| `Decision`             | 人做了什么决定、基于哪个版本和 artifact  |
| `EvidenceEvent`        | 脱敏、追加式执行事实                     |
| `NotificationDelivery` | 渠道、接收方、投递状态和重试             |
| `Delivery`             | 交付包、验证证据、回滚说明和验收状态     |

### 6.2 WorkItem 生命周期

至少支持：

```text
QUEUED
RUNNING
WAITING_FOR_USER
PAUSED
BLOCKED
FAILED
DECIDED_PENDING_APPLY
RESUMING
DELIVERING
COMPLETED
CANCELLED
```

要求：

- 状态转换必须记录操作者、时间、来源、版本、原因和关联对象；
- `DECIDED_PENDING_APPLY` 不等于已生效；
- Worker 应用失败必须进入 `BLOCKED` 或重新生成 Attention；
- 取消是终态，不得被后台任务静默恢复；
- 旧版本决策不得应用到新版本 WorkItem。

### 6.3 Attention 生命周期

```text
OPEN
  -> DELIVERED
  -> REMINDED
  -> ESCALATED
  -> RESOLVED
  -> EXPIRED
  -> CANCELLED
```

Attention 生命周期必须独立于通知渠道。即使飞书和钉钉都不可用，Attention 仍然会提醒、升级和过期。

### 6.4 Decision 状态

至少区分：

```text
RECORDED
PENDING_APPLY
APPLYING
APPLIED
STALE
REJECTED
```

规则：

- `RECORDED` 只表示决策已被权威记录；
- `PENDING_APPLY` 表示等待 Worker 拉取；
- `APPLIED` 才表示本地执行端已经接受；
- `STALE` 表示 artifact 或版本已变化；
- `REJECTED` 表示权限、签名、版本或策略校验失败。

## 7. 功能需求

### F01 云端控制面

- 提供 WebUI、管理 API、认证、Attention、Decision、Audit 和 Notification Outbox；
- 默认不直接执行 Codex；
- 云端不保存完整源码、原始日志、Codex 凭证、SSH key 或数据库密码；
- 云端必须能独立重启和恢复；
- 云端配置变更必须审计；
- 云端对本地 Worker 只下发类型化命令，不下发任意 shell。

### F02 本地执行 Worker

- 主动出站连接云端；
- 云端不得主动连入本地；
- Worker 使用独立令牌，不得复用用户会话令牌；
- Worker 只能领取绑定自身和项目白名单内的任务；
- 本地保留 Codex 凭证、仓库、完整日志、沙箱和原始构建产物；
- Worker 断线时不得继续执行需要新审批的动作；
- Worker 恢复后补传事件、拉取决策并校验后应用。

### F03 项目与 Worker 管理

- 支持多项目；
- 每个项目可配置默认 Worker、通知渠道、风险策略和保留期；
- Worker 可注册、启用、停用和撤销；
- Worker 有独立身份、心跳、租约和能力声明；
- 同一 WorkItem 不得被两个 Worker 同时领取；
- 第一版只启用一个 Worker，但第二个 Worker 不能越权领取任务。

### F04 WorkItem 与 Run

- WorkItem 保存目标、范围、验收标准、预算和风险策略；
- Run 保存 Codex sessionId、开始/结束时间、用量和结果；
- 支持暂停、恢复、重试、请求变更、取消和验收；
- 每次状态变更必须有版本和幂等键；
- 恢复必须优先使用原 sessionId；
- 不能恢复时必须明确说明原因，不得伪装成原会话继续。

### F05 Attention 协议

每个 Attention 至少包含：

- `attentionId`；
- 为什么需要人；
- 当前问题；
- 可选项；
- 风险等级；
- 证据摘要；
- 影响范围；
- `workItemVersion`；
- `artifactHash`；
- 有效期；
- 决策后的预期行为；
- 允许的动作列表。

要求：

- Attention 创建时冻结版本和 artifact；
- 提醒、升级和过期不依赖通知渠道；
- 过期不得自动批准或默认继续执行；
- 过期后原链接必须显示失效；
- 无实质变化不得重复创建 Attention；
- 相同事件重复上报不得重复通知。

### F06 Decision 与授权

- 所有决策走统一服务端入口；
- 绑定 `workItemVersion` 和 `artifactHash`；
- 支持版本 CAS；
- 支持幂等键；
- 记录 actor、device、session、authLevel、认证时间、来源和原因；
- 重复提交只产生一个有效决策；
- 制品变化后旧决策失效；
- 决策先记录，Worker 应用后才算生效；
- 应用失败必须产生新的 Attention 或阻塞状态；
- 客户端不能通过不提交 `stepUpCode` 绕过服务端风险策略。

### F07 认证与设备

- 账号密码登录；
- 强制 TOTP；
- 设备注册和撤销；
- 会话绑定 `userId + deviceId + sessionId`；
- 新设备需要额外确认；
- 高风险操作需要重新 TOTP；
- 消息链接不能建立管理会话；
- 登录、TOTP 和设备注册必须限流；
- 认证失败必须审计。

### F08 统一授权与 step-up

服务端维护统一风险策略，至少满足：

| 操作                           | 最低授权                           |
| ------------------------------ | ---------------------------------- |
| 查看状态和时间线               | 已认证设备会话                     |
| pause                          | 已认证设备会话                     |
| resume                         | 近期 TOTP                          |
| retry                          | 近期 TOTP                          |
| request_changes                | 近期 TOTP                          |
| H1/H3 approve                  | 当前操作 TOTP                      |
| cancel                         | 当前操作 TOTP                      |
| accept_delivery                | 当前操作 TOTP                      |
| 发布、生产写入、删除、密钥访问 | 当前操作 TOTP + 精确 artifact 绑定 |

要求：

- 策略在服务端集中定义；
- 所有状态变更必须有可信会话；
- 失败原因进入审计；
- 不能把“本地回环”当作远程模式的安全替代；
- 远程模式必须强制 HTTPS 和安全 Cookie。

### F09 通知与渠道适配

- 飞书、钉钉均支持；
- 均为出站 Webhook 或出站长连接，不要求公网 IP、域名或反向代理；
- 每个渠道有独立适配器；
- 每个 Attention 对每个渠道有独立投递记录；
- 一个渠道失败不影响其他渠道；
- 支持重试、退避和最大尝试次数；
- 支持投递回执；
- 支持决策、恢复、失败、过期和交付结果通知；
- 消息只负责唤醒和跳转，不负责审批。

### F10 通知内容与脱敏

默认允许：

- 项目名；
- WorkItem 标题；
- 风险等级；
- 证据摘要；
- artifact hash；
- 截止时间；
- 短时效 Attention 入口。

默认禁止：

- 客户名称；
- 绝对路径；
- 原始日志；
- 源码片段；
- 密钥；
- Codex 凭证；
- 模型思维链；
- 完整 diff。

要求：

- 入库前脱敏；
- 发送前再次脱敏；
- Web 响应按权限裁剪；
- 日志中不得出现 Webhook 密钥和会话令牌；
- 脱敏失败时 fail closed，不发送原始内容。

### F11 执行时间线与证据

持久化脱敏后的离散事件，至少包括：

```text
run.started
plan.created
tool.called
test.started
test.failed
test.passed
verification.skipped
gate.requested
decision.recorded
decision.applied
run.resumed
delivery.packaged
notification.sent
notification.failed
```

每个事件至少包含：

- `eventId`；
- `workItemId`；
- `runId`；
- `sessionId`；
- 类型；
- 时间；
- 摘要；
- `artifactHash`；
- `correlationId`。

禁止持久化：

- 模型思维链；
- 逐 token 输出；
- 完整源码 diff；
- 原始日志；
- 未脱敏绝对路径；
- 密钥和凭证。

### F12 实时更新

- 第一版使用 SSE；
- SSE 只推送版本变化或有界脱敏事件；
- 不通过 SSE 推送完整状态快照和敏感内容；
- 断线后回退到轮询；
- 轮询和 SSE 都必须受认证和限流保护；
- 前端不得依赖 4 秒轮询作为唯一实时机制。

### F13 快速修复与再交付

- 测试失败可以触发有界自动修复；
- 修复轮次可配置；
- 超过轮次进入 Attention；
- 修复后必须重新验证；
- 不允许通过修改冻结验收测试让结果变绿；
- 交付包必须绑定 artifact hash；
- 交付记录包含验证结果、未执行检查和回滚说明；
- AI 可以提供交付证据，但不能给自己的最终交付签字；
- 再交付必须引用原交付和受影响的验收标准。

### F14 多项目例外收件箱

- 首页优先展示需要人处理的事项；
- 按风险、临期和阻塞时间排序；
- 展示等待时长、通知投递失败和过期状态；
- 支持按项目、风险、状态筛选；
- 不把“AI 正在运行”作为首页主视图；
- 第一版只启用 owner，其他角色保留数据模型。

### F15 审计与保留

- 执行事件默认保留 7 天；
- 通知投递记录默认保留 30 天；
- Decision 默认保留 1 年；
- Audit 默认保留 1 年；
- 保留期按项目可配置；
- 删除操作必须审计；
- 关键决策不得静默过期、覆盖或丢失；
- 审计记录追加式保存，禁止静默篡改。

## 8. 安全与信任边界

### 8.1 云端数据边界

云端可以保存：

- 项目名称和 WorkItem 元数据；
- Attention；
- Decision；
- 审计事件；
- artifact hash；
- 脱敏执行摘要；
- 通知投递记录；
- 租约和心跳；
- 用户、设备和会话元数据。

云端不得保存：

- 完整源码；
- 原始 diff；
- 完整测试日志；
- Codex 凭证；
- SSH key；
- 数据库密码；
- 未脱敏绝对路径；
- 模型思维链；
- 逐 token 输出。

### 8.2 消息链接边界

- 链接只定位 Attention；
- 链接携带短时效 nonce；
- 链接不能直接建立管理会话；
- 链接被转发后不能获得管理权限；
- 未授权访问只能看到登录或失效提示；
- 高风险操作必须重新 TOTP；
- 决策必须绑定 artifact hash 和版本。

### 8.3 Worker 信任边界

- Worker 令牌独立；
- Worker 只能操作白名单项目；
- 云端不主动连入本地；
- 云端不能下发任意 shell；
- Worker 执行前重新校验决策；
- Worker 拒绝过期、越权或 artifact 不匹配的决策；
- Worker 失联不得被视为任务完成；
- 多 Worker 预留时必须防止重复领取。

### 8.4 远程部署边界

- 云端必须 HTTPS；
- 反向代理只信任明确配置的代理；
- 严格校验 Host 和 Origin；
- Cookie 使用 Secure、HttpOnly、SameSite；
- 登录和设备注册限流；
- 管理端口不得无保护暴露公网；
- 远程模式必须显式启用，不满足安全条件时拒绝启动。

## 9. 数据与持久化

### 9.1 MySQL 使用范围

第一版允许使用 MySQL 持久化：

- 用户、设备和会话；
- 项目、Worker 和租约；
- WorkItem、Run；
- Attention、Decision；
- EvidenceEvent；
- NotificationDelivery；
- Delivery；
- AuditLog；
- 项目配置和保留策略。

### 9.2 数据要求

- 关键表使用版本字段或等价 CAS；
- 决策使用幂等键唯一约束；
- 事件使用事件 ID 去重；
- 通知使用 `attentionId + channel + recipient + kind + version` 去重；
- 审计追加式写入；
- 备份加密；
- 备份和恢复流程可验证；
- 删除策略可配置且可审计。

### 9.3 不建议第一版引入

- Redis；
- 消息队列；
- Kubernetes；
- 多区域数据库；
- 复杂事件溯源平台；
- 独立微服务拆分。

## 10. 非功能需求

### N01 安全

- 全链路 HTTPS；
- 密码使用强哈希；
- TOTP 防重放；
- 会话可撤销；
- CSRF 防护；
- 登录、TOTP、设备注册和 Worker 注册限流；
- Webhook 密钥不进入日志；
- Worker 令牌可撤销；
- 服务端统一授权；
- 敏感数据脱敏；
- 审计不可静默篡改。

### N02 隐私与数据最小化

- 云端只保存完成任务所需的最小数据；
- 通知内容默认最小化；
- 源码、原始日志和凭证不进入云端；
- 数据导出和删除有明确策略；
- 日志、备份和消息均执行脱敏；
- 脱敏失败时 fail closed。

### N03 可靠性

- 通知失败可重试；
- Worker 断线可恢复；
- 决策幂等；
- 事件去重；
- 租约防重复执行；
- 云端重启后 reconcile；
- MySQL 备份和恢复可验证；
- 决策应用失败不能静默丢弃。

### N04 性能目标

以下为第一版建议验收目标，审批时可调整：

- 常规 API p95 小于 500ms；
- Attention 创建到通知入队小于 2 秒；
- SSE 事件到达小于 2 秒；
- 支持至少 50 个项目；
- 支持至少 200 个活跃 WorkItem；
- 支持至少 4 个已注册 Worker，第一版启用 1 个；
- 单次通知重试不阻塞主执行流程。

### N05 可用性与恢复

- 单台云服务器部署；
- 目标月可用性 99%；
- MySQL 定期全量备份和 binlog；
- RPO 不超过 15 分钟；
- RTO 不超过 2 小时；
- 重启后自动 reconcile；
- 失联 Worker 进入 `SUSPECT` 或 `OFFLINE`；
- 离线期间决策进入 `PENDING_APPLY`。

### N06 可运维性

- 单实例锁；
- 开机自启；
- 健康检查；
- 结构化日志；
- 指标：Attention 数量、等待时长、通知失败、Worker 在线、决策延迟、过期数量；
- 配置变更可审计；
- 升级和回滚有文档；
- 不依赖人工登录桌面才能启动。

### N07 可测试性

- 冻结验收测试；
- 独立验证；
- 未执行检查显式记录；
- 不允许把跳过、取消或超时写成通过；
- 安全用例覆盖链接转发、重放、旧 artifact、渠道故障和 Worker 断线；
- 关键状态转换必须有自动化测试；
- 通知脱敏和权限裁剪必须有负向测试。

### N08 兼容性

- 保持现有 Codex 执行适配器行为；
- 保持 `approval_policy="never"`；
- 保持 `SPECGATE_WAITING_FOR_USER` 举手协议；
- 保持原 session 恢复能力；
- 保持版本 CAS、幂等键、artifact hash 和 TOTP；
- 不引入版本命名的兼容目录或双运行时。

### N09 用户体验

- 首页以“需要我处理”为中心；
- 每个 Attention 一屏内说明原因、风险、选项和证据；
- 明确显示“决策已记录”和“决策已应用”的区别；
- 通知失败、过期和 Worker 离线可见；
- 不展示思维链和逐 token 输出；
- 决策后显示恢复和再验证进度。

### N10 成本

- 第一版单台云服务器可控；
- 不因通知重试或事件写入产生不可控成本；
- 事件保留期可配置；
- 支持按项目关闭非必要通知；
- 不把大模型调用放进控制面主路径。

## 11. 验收标准

### AC01 远程通知闭环

Codex 举手后：

- 飞书和钉钉各收到一条通知；
- 执行进程已退出；
- 租约已释放；
- 消息链接只能打开对应 Attention。

### AC02 链接转发安全

消息链接被转发给未授权用户：

- 不能建立管理会话；
- 不能查看敏感信息；
- 不能批准；
- 只能看到登录或失效提示。

### AC03 高风险 step-up

未完成当前操作 TOTP：

- H1/H3 批准被拒绝；
- cancel 被拒绝；
- accept_delivery 被拒绝；
- 失败原因进入审计。

### AC04 旧制品失效

artifact 变化后：

- 旧决策不能应用；
- Worker 返回 `STALE`；
- 产生新的 Attention；
- 人必须重新决策。

### AC05 决策幂等

同一决策重复提交：

- 只产生一个 Decision；
- 不重复恢复 Worker；
- 不重复发送结果通知。

### AC06 Worker 断线

Worker 离线时：

- 云端可以记录决策；
- 决策状态为 `PENDING_APPLY`；
- Worker 恢复后拉取；
- 校验通过后恢复；
- 校验失败则拒绝并告警。

### AC07 渠道故障隔离

飞书不可用、钉钉可用时：

- 钉钉正常送达；
- Attention 生命周期不受影响；
- 飞书进入重试；
- 超过上限后记录失败；
- 不产生重复轰炸。

### AC08 Attention 过期

无人处理：

- 按配置提醒；
- 临期升级；
- 到期标记 `EXPIRED`；
- 原链接显示失效；
- 不自动批准；
- 不自动继续执行。

### AC09 决策到再交付闭环

人批准后：

- 产生 Decision；
- Worker 应用；
- 原会话恢复；
- 重新验证；
- 交付结果通知；
- 全过程可在时间线回放。

### AC10 数据边界

注入源码、密钥、绝对路径和客户名：

- 云端持久化中不出现禁止字段；
- 通知中不出现禁止字段；
- 时间线只显示脱敏摘要；
- 脱敏失败时不发送。

### AC11 多项目隔离

多个项目同时存在时：

- 首页按待处理风险排序；
- 每个项目有独立通知策略；
- 决策不会串项目；
- Worker 只能操作授权项目。

### AC12 多 Worker 预留

第一版只启用一个 Worker，但：

- Worker 注册表存在；
- Worker 令牌独立；
- 项目白名单生效；
- 租约和心跳生效；
- 第二个 Worker 不能越权领取任务。

### AC13 未验证如实记录

- 未执行测试不得显示为通过；
- 跳过、取消和超时必须显式记录；
- 验收测试冻结；
- AI 不能通过修改冻结测试自证通过；
- 交付记录包含未执行检查。

### AC14 保留期与审计

- 执行事件默认 7 天；
- Decision 和 Audit 默认 1 年；
- 保留期可配置；
- 删除操作有审计；
- 关键决策不会被静默覆盖。

### AC15 部署安全

远程模式：

- 强制 HTTPS；
- 安全 Cookie；
- Host/Origin 校验；
- 反向代理可信配置；
- 管理端口不无保护暴露；
- 未满足条件时拒绝启动。

### AC16 快速再交付

修复后：

- 重新验证；
- 新交付绑定新 artifact hash；
- 原决策失效；
- 历史交付保留；
- 新交付引用原交付和受影响验收标准。

## 12. 边界与失败场景

| 场景                | 期望行为                              |
| ------------------- | ------------------------------------- |
| 通知渠道全部不可用  | Attention 仍存在、提醒、升级和过期    |
| 消息链接被转发      | 不能建立会话，不能审批                |
| 同一决策重复点击    | 只生效一次                            |
| 决策后制品变化      | 旧决策 `STALE`，重新请求人            |
| Worker 断线         | 决策 `PENDING_APPLY`，恢复后校验      |
| Worker 令牌泄露     | 可撤销，不能访问其他项目              |
| 云端数据库损坏      | 明确失败，不伪造审计                  |
| 审计链损坏          | 拒绝继续写入或显式告警                |
| 通知模板脱敏失败    | fail closed，不发送                   |
| TOTP 重放           | 拒绝并审计                            |
| 旧 session 无法恢复 | 明确阻塞，不伪装续跑                  |
| 验收测试被修改      | 旧验证失效，重新审批                  |
| 预算超限            | 产生 BUDGET Attention，不自动续跑     |
| 项目被删除          | 历史 Decision 和 Audit 按保留策略处理 |
| 多 Worker 同时领取  | 只有一个获得租约                      |

## 15. 显式假设

1. 第一版是自用产品，不做多租户和计费。
2. 第一版只启用 owner，其他角色只保留数据模型。
3. 云端不保存源码、原始日志、Codex 凭证、SSH key 或数据库密码。
4. 本地 Worker 主动出站，云端不主动连入。
5. 第一版只启用一个 Worker，多 Worker 只预留能力。
6. 使用 MySQL 作为持久化数据库。
7. 使用一台云服务器，不引入 Redis、Kubernetes。
8. 飞书、钉钉只做出站通知。
9. IM 内不做审批。
10. 消息链接只定位 Attention，不建立会话。
11. 账号密码 + 强制 TOTP + 设备绑定。
12. 执行事件默认 7 天，Decision/Audit 默认 1 年。
13. 旧决策随 artifact 变化失效。
14. AI 可以修复，但不能给自己的最终交付签字。
15. 差异化优先做“快速修复再交付”和“跨项目统一控制”。
