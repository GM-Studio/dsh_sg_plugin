## 1. 产品目标

### 1.1 要解决的问题

Codex 等代码 Agent 能够越来越自主地理解项目、修改代码、运行测试和完成
单次任务。一人接单开发者仍然缺少一套稳定机制来回答以下问题：

- 上次交付给客户的是哪个版本。
- 当时承诺了什么，客户接受了什么。
- 本轮客户反馈相对于上次交付改变了哪些范围。
- 哪些历史测试仍然有效，哪些必须随需求变化。
- 这次修改是否引入新失败或未验证风险。
- 出现问题时应该回退、恢复还是前滚修复。
- 如何把工程结果转换为客户可理解、可验收的交付物。

SpecGate 不重复实现 Codex 已有的代码生成、代码编辑、工具调用和多 Agent
能力。SpecGate 位于代码执行之上，负责项目基线、变更契约、真实证据、商业
交付记录和增量再交付。

SpecGate 不是更聪明的编码器，不是完整 SDLC 平台，也不是高级 CI 包装器。
它的核心职责是补齐 AI 生成结果与商业可交付结果之间的责任缺口：

```text
客户意图
  ↔ 已确认 AC
  ↔ 实际行为
  ↔ 可复核证据
  ↔ 客户验收
```

### 1.2 双入口

产品必须同时支持两种项目起点：

```text
新建 Java/Vue 项目 ─┐
                    ├─> ProjectProfile + Baseline
存量 Java/Vue 项目 ─┘
                            ↓
                      统一交付内核
```

两种入口只在“项目如何建立可信基线”上不同。进入项目基线之后，Change、
Verification、Delivery 和 Incremental Delivery 必须使用同一套模型、状态和
证据规则，不维护两套工作流。

### 1.3 用户价值

1. 新项目能够从可靠模板和真实验证形成可交付起点。
2. 存量项目能够安全接入，不要求被 SpecGate 重新创建或覆盖。
3. 每次客户变更能够快速形成范围、AC、风险和执行计划。
4. Codex 执行结果由真实命令、报告和运行观察证明。
5. 每次验收形成可追溯的交付记录，并成为下一次增量交付的基线。
6. 失败工作能够定向恢复，不因无关失败推倒整个交付。
7. 客户可读交付包与内部工程证据包分离。
8. 默认不操作生产环境，但能够提供经过验证的回退或前滚说明。

### 1.4 成功定义

产品成功不等于实现完整状态机或增加 Agent 数量。首版成功必须同时满足：

- 存量 Java/Vue 项目无需 `sg_init` 即可接入并建立 adopted baseline。
- 新项目和存量项目能够进入同一套交付流程。
- 每次验收能够形成不可变 Delivery 记录。
- 下一次客户反馈能够引用上一次 Delivery 并只分析受影响范围。
- 失败恢复不会重跑已完成且无依赖变化的工作项。
- 所有交付结论绑定当前 commit 和真实执行证据。
- 一人团队每次变更的主要人工决策不超过两次。
- 与裸用 Codex 相比，试点项目能够明显降低返工、验收争议或交付风险。

### 1.5 产品原则

1. 宿主负责执行，SpecGate 负责交付保证，不重复实现通用 Agent Runtime。
2. 使用风险匹配的最小治理，不以阶段数量、Agent 数量或提示词数量作为价值。
3. 证据用于降低审查成本，不能取消高风险变更的代码审查责任。
4. 自动化只减少重复工作，不能替代客户对业务范围和最终结果的接受。
5. 所有用户交互以保护注意力为目标，内部复杂状态默认对用户隐藏。
6. 交付记录必须积累为可复用资产，而不是一次性执行日志。
7. 无法证明的成本、收益和行业数据不能成为产品需求的唯一依据。

## 2. 目标用户与核心任务

### 2.1 目标用户

- 一人完成需求、前端、后端、测试和交付的独立开发者。
- 承接 Java/Vue 商业项目、二次开发、内部系统和 MVP 的一人团队。
- 需要持续回应客户反馈、进行多轮修改和再交付的承接方。

首版不承诺支持任意技术栈的存量项目。识别到非 Java/Vue 项目时必须明确
返回不支持，不得以模糊的“尽力而为”方式继续执行。

### 2.2 核心任务

1. 新建项目并建立可信初始基线。
2. 接管已有项目并记录当前可观察行为。
3. 将客户变更转换为明确的范围、非目标、AC 和风险。
4. 由 Codex 执行实现和修复。
5. 通过真实命令和运行证据验证结果。
6. 验收并形成商业交付记录。
7. 基于上一交付处理客户反馈和增量再交付。
8. 在失败时恢复、回退或前滚，同时保留证据。

## 3. 产品边界与差异化

### 3.1 宿主与 SpecGate 的职责

Codex 负责：

- 理解代码和项目上下文。
- 修改文件。
- 调用工具和运行命令。
- 生成必要测试、修复缺陷和解释结果。
- 在宿主能力允许时创建子 Agent。

SpecGate 负责：

- 判断项目是否已经建立有效基线和配置。
- 保存客户承诺、Change Contract 和验收标准。
- 限制高风险路径和不可接受的执行方式。
- 绑定真实执行证据与 commit。
- 保存 Delivery、验收回执和增量血缘。
- 判断交付是否满足准入条件。
- 生成内部证据包和客户交付包。

宿主已有的 Git、worktree、子 Agent 和命令执行能力不得在 SpecGate 内重复
实现。SpecGate 只保存和校验交付所需的不可替代状态。

### 3.2 核心差异化

1. **双入口统一基线**
   - 新项目和存量项目进入同一个交付内核。
   - 存量项目不要求重新初始化。

2. **验收驱动的证据**
   - AC、代码、命令、运行观察和用户验收形成可追溯链。
   - Agent 自述不能作为通过证据。

3. **基于上一交付的增量再交付**
   - 新反馈必须引用上一交付。
   - 历史 AC 和测试按影响关系复用、版本化或失效。

4. **风险自适应门禁**
   - 小型修复使用压缩门禁。
   - API、数据、安全、支付和不可逆操作使用严格门禁。

5. **客户可用的商业交付物**
   - 内部工程证据和客户摘要分离。
   - 交付物明确范围、验证方式、已知问题和回退方式。

6. **注意力保护**
   - 用户只处理业务范围、风险和最终验收。
   - 失败恢复、证据整理和下一步动作由系统提供明确建议。

SpecGate 的差异化是“验收账本 + 增量再交付 + 风险自适应证据”，不是通用
代码生成、完整 CI 能力或流程阶段数量。

### 3.3 首版非目标

- 与宿主竞争的代码生成、代码补全或通用 Agent 运行时。
- 任意技术栈的自动初始化、测试和交付。
- 通用应用生成器。
- 生产部署。
- 自动执行生产数据库回滚。
- 多客户 SaaS 管理门户。
- 多仓库微服务统一编排。
- 企业级项目组合、成本和合规平台。
- 第一版的多工作项并行 DAG、文件锁调度器和复杂安全并行。
- 以 Agent 数量、提示词数量或工作流阶段数量作为产品价值。
- 自研通用 Harness、沙箱、会话管理或代码代理运行时。

## 4. 核心模型

### 4.1 ProjectProfile

ProjectProfile 是项目的受控配置，不包含临时执行状态。

```json
{
  "schemaVersion": 2,
  "projectId": "project-...",
  "mode": "new",
  "stack": "java-vue",
  "root": "<project-root>",
  "targetBranch": "main",
  "remoteUrl": null,
  "pushApproved": false,
  "commands": {
    "install": [],
    "build": [],
    "test": [],
    "lint": [],
    "format": [],
    "runtime": []
  },
  "protectedPaths": [],
  "createdAt": "...",
  "updatedAt": "..."
}
```

约束：

- `mode` 只能是 `new` 或 `adopted`。
- `pushApproved` 默认 `false`。
- `remoteUrl` 不得包含用户名、密码、token 或其他明文凭据。
- 未识别或未确认的命令不能被标记为有效。
- 用户提供的命令覆盖必须记录来源。

### 4.2 ProjectBaseline

ProjectBaseline 表示本轮 Change 开始前项目的可验证状态。

```json
{
  "baselineId": "baseline-...",
  "projectId": "project-...",
  "commit": "<sha>",
  "status": "green",
  "knownFailures": [],
  "unverifiedAreas": [],
  "commands": [],
  "evidence": [],
  "createdAt": "..."
}
```

`status` 允许：

- `green`：必要基线命令全部真实通过。
- `known-failures`：存在已记录、可复核的历史失败。
- `partial`：项目可识别且可执行部分基线，但存在明确未验证范围。
- `unknown`：尚未完成基线验证，只能用于只读接入，不得开始正式 Change。

约束：

- 新项目原则上必须达到 `green` 才能形成正式基线。
- 存量项目允许 `known-failures` 或 `partial`，但必须明确风险。
- `commit` 必须是基线时的固定 Git commit。
- 基线证据必须与 commit 和命令绑定。
- 未执行、跳过、超时和失败不得记录为通过。

### 4.3 ChangeContract

ChangeContract 是一次业务变更的确认契约。

```json
{
  "changeId": "change-...",
  "parentDeliveryId": null,
  "type": "feature",
  "request": "客户原始需求",
  "scope": ["..."],
  "nonGoals": ["..."],
  "acceptance": ["AC-001"],
  "compatibility": ["..."],
  "assumptions": ["..."],
  "risks": ["..."],
  "baselineId": "baseline-...",
  "status": "H1_PENDING"
}
```

约束：

- `type` 首版只能为 `feature`、`modify` 或 `fix`。
- 每个 AC 必须描述可观察行为，包括必要的失败和边界行为。
- 新 Change 的 `parentDeliveryId` 可空；增量 Change 必须指向上一次交付。
- H1 通过后，类型、范围、AC、非目标和风险不能静默改变。
- 修改契约后，旧 H1、受影响计划和证据必须失效或进入新版本。

### 4.4 DeliveryRecord

每次 H3 通过后生成不可变 DeliveryRecord。

```json
{
  "deliveryId": "delivery-...",
  "projectId": "project-...",
  "changeId": "change-...",
  "parentDeliveryId": null,
  "baselineCommit": "<sha>",
  "deliveryCommit": "<sha>",
  "tag": "specgate-delivery-...",
  "state": "accepted",
  "environmentFingerprint": "env-...",
  "reviewMode": "evidence",
  "acceptedAt": "...",
  "acceptance": ["AC-001"],
  "evidence": [],
  "knownIssues": [],
  "rollback": {
    "code": "...",
    "data": "...",
    "forwardFix": "..."
  },
  "push": {
    "requested": false,
    "remoteUrl": null,
    "status": "not-requested"
  }
}
```

约束：

- DeliveryRecord 是后续增量交付的唯一可信父基线。
- 必须包含固定 `deliveryCommit`。
- 默认创建本地 tag，不自动推送。
- 交付记录生成后不得覆盖；修订必须形成新 Delivery。
- 工程证据包和客户交付包必须引用同一个 DeliveryRecord。
- `state` 不得将技术验证、客户验收、推送和生产部署混为一谈。

### 4.5 Evidence

每项证据至少包含：

- 证据 ID。
- 类型。
- 对应 AC。
- 执行者。
- 命令或操作。
- 工作目录和固定 commit。
- 开始时间、结束时间和耗时。
- 状态：`passed`、`failed`、`skipped`、`not-run`、`timeout`、`cancelled`。
- 退出码。
- 原始日志或产物的路径和内容哈希。
- 脱敏后的摘要。

证据类型至少支持：

- `automated-test`
- `command`
- `http-observation`
- `browser-observation`
- `manual-demo`
- `database-migration-check`
- `user-acceptance`

不是每个 AC 都必须有自动测试。没有自动测试时，必须使用明确的人工演示、
运行观察或其他可复核证据，不能将 AC 直接标记为自动通过。

### 4.6 EnvironmentFingerprint

环境指纹用于判断已有证据在新的执行环境中是否仍然有效。

```json
{
  "fingerprintId": "env-...",
  "os": "Windows",
  "runtimes": {
    "java": "21",
    "node": "20.19.0"
  },
  "packageManager": "npm",
  "database": "postgresql-16",
  "browser": "chromium-...",
  "environmentVariableNames": [],
  "externalServices": [],
  "configurationHash": "<sha>",
  "createdAt": "..."
}
```

约束：

- 不保存敏感环境变量值。
- 必须记录足以复现验证结果的关键版本和配置差异。
- 使用 mock、本地服务或替代数据库时必须显式记录。
- 环境指纹变化后，受影响证据必须重新评估，不能直接沿用旧结论。

### 4.7 VerificationAssessment

每个 Change 在 H3 前必须形成验证充分性结论。

```json
{
  "verificationId": "verify-...",
  "risk": "yellow",
  "independenceLevel": "fresh-context",
  "acCoverage": [],
  "evidence": [],
  "reviewMode": "evidence-and-diff",
  "environmentFingerprint": "env-...",
  "openRisks": [],
  "decision": "requires-h3"
}
```

`decision` 允许：

- `blocked`
- `requires-risk-confirmation`
- `requires-h3`
- `verified-awaiting-acceptance`

验证评估必须说明证据是否足以支持 AC，而不是只统计测试通过数量。

## 5. 双入口项目接入

### 5.1 新建项目

新建项目流程：

```text
选择 Java/Vue 模板
  -> 生成项目结构
  -> 安装依赖
  -> 运行 build/test/lint/runtime 基线
  -> 创建初始化提交
  -> 写入 ProjectProfile
  -> 生成 ProjectBaseline
```

要求：

- 新项目创建只负责形成可靠起点，不直接生成完整业务产品。
- 生成不等于验证。
- 依赖安装、构建、测试和运行证据必须真实执行。
- 基线验证失败时不得伪装成可交付新项目。
- 可以复用现有 Java/Vue 模板和工具链发现能力，不重复构建通用生成器。

### 5.2 存量项目接入

存量项目使用独立接入流程 `sg_adopt`。

第一阶段必须只读扫描：

- Git 根目录、分支、HEAD 和远程配置。
- 工作区是否干净。
- Java/Vue 技术栈及模块结构。
- 构建、测试、lint、格式化和运行命令。
- 测试框架、测试目录和已有报告。
- API 契约、数据库迁移和部署配置。
- 受保护路径、敏感文件和可能包含凭据的位置。
- 当前基线可验证程度。

扫描只生成接入预览，不修改业务代码、不创建基线、不写入正式配置。

用户确认后：

1. 写入 ProjectProfile。
2. 创建 adopted ProjectBaseline。
3. 记录已知失败、未验证范围和剩余风险。
4. 进入与新项目相同的 Change 流程。

接入要求：

- 不要求存量项目执行 `sg_init`。
- 不覆盖已有项目文件。
- 不强制迁移到 SpecGate 模板。
- 不把当前 adopted baseline 伪装成历史客户验收。
- 新的验收历史从本次接入之后开始。
- 非 Java/Vue 项目明确返回不支持。

### 5.3 脏工作区处理

存量项目存在未提交修改时采用 B 方案：

1. 允许执行只读扫描并展示脏文件清单。
2. 不直接建立正式 Baseline。
3. 向用户展示拟提交文件、文件状态和拟提交说明。
4. 用户明确批准后，由 Codex 创建基线提交。
5. 只能提交用户确认的文件集合，禁止默认使用 `git add -A`。
6. 提交完成后重新扫描，确认工作区干净。
7. 然后建立 ProjectBaseline。

约束：

- 未获得明确批准时不得提交任何文件。
- 提交前必须检查敏感信息和不应进入版本库的产物。
- 用户可以选择取消并自行提交或 stash。
- 基线提交属于项目基线，不等同于业务交付。
- 提交失败时不得继续建立正式基线。

## 6. 统一变交流程

### 6.1 完整闭环

```text
ProjectProfile + ProjectBaseline
  -> 客户变更请求
  -> Change 分析与契约草案
  -> H1 用户确认
  -> Codex 串行实现
  -> 独立验证
  -> 风险复核
  -> H3 用户验收
  -> DeliveryRecord
  -> 本地 tag
  -> 可选远程 push
  -> 客户反馈
  -> 增量 Change
```

### 6.1.1 用户可见生命周期

内部状态机可以有更多实现状态，但用户只看到四个产品级状态：

```text
项目就绪
  -> 变更已确认
  -> 证据已就绪
  -> 交付已接受
```

每个状态必须能够回答：

- 当前目标是什么。
- 哪些事项已经确定。
- 还缺什么证据或决定。
- 下一步由用户还是系统执行。
- 失败或中断后从哪里恢复。

### 6.2 首版执行模式

第一版采用可靠串行闭环：

1. 一个实现执行单元完成获准范围。
2. 一个独立验证视角检查 AC、测试和运行行为。
3. 高风险变更增加独立 Reviewer。
4. 格式化、lint、测试执行和构建优先使用项目已有命令。
5. 多工作项并行、复杂 DAG 和文件锁调度延后。

实现和验证可以由 Codex 主 Agent 或宿主可用的子 Agent 完成，但验证结果必须
由 SpecGate 根据真实命令和产物校验，不能以“子 Agent 说通过了”作为证据。

同一模型的不同 Agent 不自动构成独立验证。独立性至少要求：

- 验证依据来自已确认 AC，而不是实现者的完成声明。
- 验证命令来自 ProjectProfile、已确认计划或服务端校验，而不是实现者临时自证。
- 验证上下文不继承实现者的自评和未经验证的假设。
- 高风险变更接受独立 diff、安全和数据边界审查。
- 用户对最终业务结果进行验收。

### 6.3 变更类型

#### Feature

必须描述：

- 新增能力。
- 目标用户和业务价值。
- 可观察 AC。
- 非目标和兼容性。

#### Modify

必须描述：

- 要修改的现有行为。
- 目标变化。
- 明确保持不变的行为。
- 兼容性和数据/API 影响。

#### Fix

必须描述：

- Bug 现象。
- 期望行为。
- 实际行为。
- 可选复现步骤、日志、环境和严重级别。

Fix 必须优先产生针对该问题的失败回归证据，再修复并证明由红转绿。无法稳定
复现时，必须保留失败原因和未解决风险，不能把修复标记为已验证通过。

### 6.4 快速反馈

每个阶段向用户展示最小决策信息：

- 当前目标和意图。
- 实际完成的改动。
- 修改文件或制品。
- AC 和证据状态。
- 新风险、已知失败和未执行检查。
- 需要用户决定的事项。

同一问题不得反复询问。用户已经确认的范围、非目标和假设必须被复用。

### 6.5 中途反馈和退回

允许用户：

- 暂停。
- 继续。
- 取消。
- 返回 Change Contract。
- 返回实现。
- 只重跑失败部分。
- 进入增量 Change。

任何退回必须记录原因，并明确哪些 AC、计划、测试和证据失效。

### 6.6 验证独立性矩阵

| 风险   | 最低验证独立性                                          | 必需审查                     |
| ------ | ------------------------------------------------------- | ---------------------------- |
| Green  | 实现者执行项目命令，独立验证视角复核证据和当前 commit   | 证据；必要时抽查关键 diff    |
| Yellow | 由已确认 AC 驱动验证，使用干净上下文，服务端校验结果    | 证据 + 关键 diff             |
| Red    | 独立 Reviewer 复核固定 diff，检查契约、安全、数据和迁移 | 完整代码审查 + 迁移/回退说明 |

规则：

- 低风险可以主要审查证据，但不能跳过真实执行。
- 自动测试不能单独证明高风险业务和安全正确性。
- 证据不足时，验证状态必须是 `blocked` 或 `requires-h3`，不能自动通过。
- 验证独立性等级必须写入 VerificationAssessment。

## 7. Baseline 与风险策略

### 7.1 基线差异原则

新项目和存量项目必须使用同一比较原则：

```text
当前结果与 ProjectBaseline 比较
```

规则：

1. 基线已通过的项目不得出现新失败。
2. 基线已知失败必须有稳定签名、证据和影响范围。
3. 本次变更不能扩大已知失败范围。
4. 已修复的历史失败必须从 knownFailures 中移除并保留证据。
5. 无法确定的失败不得静默忽略。
6. 高风险变更不能因为基线是 `known-failures` 或 `partial` 而降低门禁。

### 7.2 缺少测试

存量项目缺少测试时：

- 围绕本次变更生成必要的行为保护和回归测试。
- 不承诺一次性补齐整个项目。
- 对无法自动覆盖的 AC 使用人工演示或运行观察。
- 明确记录未覆盖范围和剩余风险。
- 高风险变更可以要求补充 characterization test 或迁移演练。

### 7.3 风险等级

#### Green

适用：

- 单端修改。
- 不改变 API、数据、安全或权限语义。
- 可通过定向回归或人工演示验证。

要求：

- 压缩版 H1。
- 真实验证证据。
- H3 验收。

#### Yellow

适用：

- 常规 feature 或 modify。
- 前后端协作或业务规则变化。
- 兼容性需要明确说明。

要求：

- 完整 Change Contract。
- 必要测试和兼容性检查。
- 独立验证。
- H3 验收。

#### Red

适用：

- 破坏性 API。
- 数据语义、迁移或一致性风险。
- 鉴权、权限、安全、支付或关键账务。
- 不可逆外部副作用。

要求：

- H1 和 H3 明确展示风险。
- 数据备份、迁移和前滚/回退说明。
- 更严格的 Review。
- 未满足必要条件时阻断交付。

风险先由计划和实际 diff 共同判断。实际 diff 只能将风险升级；降级必须由
明确策略和用户确认支持。

### 7.4 测试抖动和隔离策略

- 同一失败可以按有限策略重试，但每次尝试必须保留证据。
- 重试后通过不能自动抹除第一次失败，必须标记为不稳定结果。
- 因本次变更出现的新失败不得通过重试、跳过或加入已知失败清单洗成通过。
- 临时隔离已知 flaky test 必须记录原因、影响范围、负责人和复查条件。
- 高风险变更不得依赖不稳定测试作为唯一通过证据。
- 任何 `skip`、`only`、隔离或重试策略都必须显式出现在 VerificationAssessment。

## 8. 人工门禁

### 8.1 H1

H1 确认：

- 业务目标和范围。
- 非目标。
- AC。
- 假设和开放问题。
- 兼容性。
- 风险。
- 计划采用的验证方式。

低风险 Fix 可以使用压缩版 H1，但不能跳过契约和用户确认。

### 8.2 风险例外

以下情况必须单独确认：

- 破坏性 API。
- 数据或迁移语义变化。
- 鉴权、权限、安全、支付或关键账务。
- 超出已确认范围的新增要求。
- 无法安全自动处理的冲突。

### 8.3 H3

H3 展示：

- AC 与证据映射。
- 验证独立性等级和证据充分性结论。
- 测试和运行结果。
- 环境指纹和证据有效期。
- 变更文件和 commit。
- 已知问题。
- 未验证范围和剩余风险。
- 客户交付包。
- 回退或前滚说明。

### 8.4 风险自适应审查

- 低风险变更可以主要依据证据摘要进行验收。
- 普通变更必须同时提供证据和关键 diff。
- 高风险变更必须进行固定 commit 的独立代码审查。
- 测试通过不能替代安全、权限、并发、事务、迁移和支付语义审查。
- 审查者只审查当前固定 commit；commit 变化后必须重新审查受影响部分。

### 8.5 审批安全

- 审批必须来自可信原生用户交互。
- Agent、工具参数、环境变量、日志或报告不能伪造审批。
- 审批必须绑定当前的契约、证据和交付预览哈希。
- 审批后内容变化时，旧审批失效。

## 9. 证据与正确性

### 9.1 证据真实性

- 只接受实际执行的命令和运行观察。
- 不存在的命令、跳过项、超时和取消项不能计为通过。
- 测试报告必须来自当前 commit。
- 日志和制品必须保留路径、哈希和脱敏摘要。
- 证据变化后，依赖该证据的 H3 或交付必须失效。
- Agent 的总结只能作为摘要，不能替代机器证据。

### 9.2 证据与验收

系统必须支持将证据绑定到 AC：

```text
AC-001
  -> automated-test: passed
  -> http-observation: passed
  -> user-acceptance: passed
```

对于视觉、交互或业务判断类 AC，可以要求人工演示或用户验收。人工验收必须
记录验收对象、时间和 Delivery 版本，不能伪造客户身份。

### 9.3 未验证内容

无法执行的检查必须显示为 `not-run`，并说明：

- 原因。
- 影响范围。
- 替代证据。
- 剩余风险。
- 是否阻止 H3。

### 9.4 证据充分性

每个 AC 必须声明所需证据类型和通过条件：

- 自动测试。
- 命令退出状态。
- HTTP 响应观察。
- 浏览器行为观察。
- 数据库迁移检查。
- 人工演示。
- 用户验收。

证据充分性评估必须回答：

- 证据是否来自当前固定 commit。
- 证据是否在有效环境内执行。
- 是否覆盖成功、失败和边界行为。
- 是否存在被 mock、跳过或替代验证的部分。
- 是否足以支持该风险的 H3 决策。

### 9.5 证据与代码审查

- 证据用于降低审查成本，不用于取消高风险代码审查。
- 测试只能证明被测试的行为，不自动证明测试本身就是正确需求。
- 高风险变更必须同时审查证据、关键代码、契约、迁移和回退路径。
- Reviewer 的结论必须引用固定 diff 或具体证据。

## 10. 交付

### 10.1 内部工程证据包

包含：

- 原始命令和退出码。
- 测试、构建、lint 和运行报告。
- commit 和文件变更。
- 未执行项、失败项和剩余风险。
- 工件哈希。
- 回退执行细节。

工程包包含技术路径和内部信息，不默认直接交付客户。

### 10.2 客户交付包

包含：

- 本次交付范围。
- 已完成的 AC。
- 客户可执行的验证步骤。
- 已知问题和限制。
- 部署或升级说明。
- 数据影响和备份说明。
- 回退或前滚说明。
- 变更说明。

客户交付包不得包含：

- 明文凭据。
- 不应暴露的内部路径。
- 未经脱敏的日志和客户数据。
- 与交付无关的内部 Agent 对话。

### 10.3 远程推送

远程推送规则：

- 默认 `push=false`。
- 仅配置 `remoteUrl` 不触发 push。
- 只有在 H3 已通过、DeliveryRecord 已生成、`remoteUrl` 有效且
  `push=true` 时才允许推送。
- 默认推送 ProjectProfile 指定的目标分支。
- 使用系统 Git 凭据，不保存明文密码或 token。
- 禁止 force push。
- 推送失败保留本地交付和完整错误证据。
- push 失败不自动无限重试。
- 交付记录必须记录推送请求、远程地址状态和最终结果。

### 10.4 交付状态

以下状态必须分开记录：

```text
CHANGE_VERIFIED
  -> DELIVERY_ACCEPTED
  -> PUSHED
  -> DEPLOYED_UNKNOWN
  -> DEPLOYED_VERIFIED
```

约束：

- `CHANGE_VERIFIED` 只表示技术和证据验证完成，不表示客户接受。
- `DELIVERY_ACCEPTED` 表示 H3 验收完成并生成 DeliveryRecord。
- `PUSHED` 只表示远程推送成功，不表示已部署。
- `DEPLOYED_UNKNOWN` 表示不知道生产状态，不得推断为已部署。
- `DEPLOYED_VERIFIED` 必须有独立的生产或目标环境观察证据。
- SpecGate 不自动执行生产部署；部署状态只能由真实证据或用户明确确认。

## 11. 增量再交付

### 11.1 输入

客户反馈形成新的 Change，并必须：

- 引用上一 DeliveryRecord。
- 使用上一 `deliveryCommit` 作为父交付基线。
- 记录客户反馈原文和脱敏后的结构化需求。
- 判断是 feature、modify 还是 fix。

### 11.2 影响分析

必须分析：

- 受影响的 AC。
- 受影响的代码和契约。
- 受影响的测试。
- API、数据库、配置和部署影响。
- 历史已知失败和未验证区域。

影响分析由 Codex 提供建议，SpecGate 负责绑定 Artifact 并进行证据校验。

### 11.3 复用和失效

- 仍然有效的历史 AC 和测试继续复用。
- 受新需求影响的历史测试必须版本化或显式失效。
- 不允许静默删除历史测试。
- 不允许用新测试覆盖旧测试而不保留原因和旧版本。
- 高风险或契约变化必须重新审批。

### 11.4 验证

- 先执行与本次变更直接相关的定向回归。
- 最终执行必要的受影响历史回归。
- 高风险变更执行更完整的回归。
- 新交付不能丢失上一交付的验收证据。
- 完成 H3 后生成新的 DeliveryRecord，不覆盖上一版本。

## 12. 恢复与回退

### 12.1 未交付变更恢复

- 失败工作保留 commit、日志和报告。
- 用户可只重跑失败部分。
- 已完成且无依赖变化的部分不得重复执行。
- 失败产物不得自动销毁。

### 12.2 代码回退

支持：

- 回退未合并分支。
- 回退未交付 commit。
- 对已交付代码生成反向 patch 或 revert 方案。
- 记录回退后的 commit 和重新验证证据。

### 12.3 数据和外部副作用

- 不自动执行生产数据库回滚。
- Red 风险必须提供备份、迁移和恢复方案。
- 对不可逆外部副作用必须明确记录。
- 当回退不安全时，优先评估前滚修复。

## 13. 持久化

建议的数据职责：

| 数据            | 位置                                     | 约束               |
| --------------- | ---------------------------------------- | ------------------ |
| ProjectProfile  | `.specgate/codex/project.json`           | 受控配置，模式固定 |
| ProjectBaseline | `.specgate/codex/baselines/`             | 绑定 commit 和证据 |
| Change Contract | `.specgate/codex/changes/<id>/contract/` | 版本化，绑定来源   |
| 执行证据        | `.specgate/codex/changes/<id>/evidence/` | 可追溯，禁止伪造   |
| DeliveryRecord  | `.specgate/codex/deliveries/<id>/`       | 不可覆盖           |
| 客户交付包      | Delivery 目录或显式导出目录              | 必须脱敏           |
| 归档            | `.specgate/codex/archive/`               | 失败证据不自动删除 |

约束：

- 运行时状态写入必须使用版本 CAS。
- 配置迁移必须可预览，不得静默覆盖用户配置。
- 路径必须经过项目边界检查。
- 不允许通过符号链接逃逸项目目录。
- 大日志和临时工作区应有保留策略，但不得在失败后自动销毁关键证据。

## 14. 功能需求

### FR-001 新项目基线

系统 MUST 支持 Java/Vue 新项目创建、真实初始验证和正式 Baseline。

### FR-002 存量项目接入

系统 MUST 提供只读 `sg_adopt` 预览，并允许用户确认后建立 adopted
ProjectProfile 和 Baseline。

### FR-003 双入口统一

新项目和存量项目 MUST 在 Baseline 之后进入同一 Change、Evidence、
Delivery 和 Incremental Delivery 流程。

### FR-004 脏工作区

存量项目存在脏工作区时，系统 MUST 展示拟提交文件，获得明确批准后创建
基线提交，并在提交后重新扫描。

### FR-005 基线失败

系统 MUST 支持 `green`、`known-failures`、`partial` 和 `unknown` 基线
状态，并区分历史失败与本次新增失败。

### FR-006 Change 类型

系统 MUST 支持 `feature`、`modify` 和 `fix`，并按类型收集必要输入。

### FR-007 Fix 红转绿

Fix MUST 在可行时先生成真实失败回归证据，再修复并证明通过。

### FR-008 H1 和 H3

系统 MUST 要求可信用户完成 H1 和 H3。低风险 Fix 可使用压缩版 H1。

### FR-009 串行交付

首版 MUST 支持实现者、独立验证者和高风险 Reviewer 组成的可靠串行闭环。

### FR-010 证据绑定

系统 MUST 将每个 AC 的真实证据绑定到固定 commit，并区分通过、失败、跳过、
未执行、超时和取消。

### FR-011 DeliveryRecord

H3 通过后，系统 MUST 生成不可变 DeliveryRecord 和本地 tag。

### FR-012 双交付包

系统 MUST 生成内部工程证据包和客户交付包，并确保二者引用同一个 Delivery。

### FR-013 增量再交付

系统 MUST 支持新 Change 引用上一 Delivery，分析影响范围，复用或失效历史
AC 与测试，并生成新 DeliveryRecord。

### FR-014 恢复

系统 MUST 支持失败恢复，并避免重跑已完成且不受影响的工作。

### FR-015 回退说明

系统 MUST 提供代码回退方案；Red 风险 MUST 要求数据备份、迁移和恢复说明。

### FR-016 远程推送

系统 MUST 仅在 H3 通过、DeliveryRecord 存在、远程地址有效且 `push=true`
时推送目标分支，且 MUST NOT force push。

### FR-017 兼容旧入口

在可行时保留现有 `sg_change_add`，作为 `feature` 的兼容入口。

### FR-018 项目模式隔离

`sg_init` MUST 只用于新项目创建；`sg_adopt` MUST 只用于存量项目接入。

### FR-019 验证独立性

系统 MUST 按风险等级记录验证独立性，并 MUST NOT 将同一实现上下文的
自我总结视为独立验证。

### FR-020 证据充分性

系统 MUST 为每个 AC 记录所需证据类型、覆盖范围、执行环境和充分性结论。

### FR-021 环境指纹

系统 MUST 记录验证环境的可复现标识，并在环境变化后使受影响证据进入重新
评估状态。

### FR-022 测试稳定性

系统 MUST 区分稳定失败、本次新增失败、flaky test 和被隔离测试，并保留所有
重试和跳过证据。

### FR-023 交付状态

系统 MUST 分开记录技术验证、客户验收、远程推送和部署状态。

### FR-024 注意力预算

系统 MUST 提供四个用户可见生命周期状态，并记录用户决策次数、恢复所需操作和
手工阶段数量作为产品指标。

### FR-025 交付记录可迁移性

项目基线和交付记录 MUST 使用可独立读取的结构化格式，使产品未来能够更换
执行宿主而不丢失交付历史。

## 15. 非功能需求

### NFR-001 安全

- 用户输入、日志和反馈必须脱敏。
- 不保存明文凭据。
- 项目、baseline、交付和归档路径必须进行边界检查。
- Agent 不能伪造审批、冻结哈希、用户身份或测试结果。
- 远程推送使用系统 Git 凭据。

### NFR-002 可审计

- 项目接入、基线、Change、执行、交付、推送、恢复和回退必须可追溯。
- 关键状态转换必须记录事件。
- 未执行、跳过、超时、取消和失败必须显式记录。

### NFR-003 可恢复

- 失败工作不得阻塞无依赖工作的证据保存。
- 恢复后必须重新验证受影响部分。
- 不自动清理失败日志、代码和报告。

### NFR-004 一致性

- ProjectProfile、Baseline、Change、Evidence、Delivery 和 parent Delivery
  必须引用相同项目 ID。
- 状态写入必须使用版本 CAS。
- 交付记录不得被静默覆盖。

### NFR-005 性能与成本

- 存量项目接入目标不超过 10 分钟，不含依赖安装时间。
- 正常变更从发起到开始执行目标不超过 2 分钟。
- 每次变更主要人工决策不超过 2 次。
- 记录阶段耗时、执行轮次、失败次数和可获得的成本指标。
- 已完成且无依赖变化的工作不得因无关失败重复执行。

### NFR-006 一人团队体验

- 默认给出建议决策。
- 用户不承担内部 Agent 编排。
- 内部工具隐藏在少量命令和自然语言操作后。
- 同一问题不重复询问。
- 首次接入和首次变更必须有清晰恢复路径。
- 用户可见状态不超过四个：项目就绪、变更已确认、证据已就绪、交付已接受。
- 系统必须记录人工决策次数、恢复操作次数和手工阶段数量。
- 长日志和工程证据必须转换为可决策摘要，不要求用户逐行阅读原始输出。

### NFR-007 平台

- Windows 作为首要真实验证平台。
- 实现保持跨平台，不引入仅适用于单一操作系统的新依赖。
- 工具链发现必须有限、可复用已有安装并支持用户配置覆盖。

### NFR-008 数据与包

- 工程证据包和客户交付包必须分离。
- 客户交付包必须可独立阅读。
- 交付包必须绑定 DeliveryRecord 和固定 commit。

### NFR-009 验证完整性

- 证据必须可追溯到固定 commit 和已确认 AC。
- 关键命令结果必须包含退出码、耗时和状态。
- Agent 自述、摘要和计划不能替代实际执行证据。
- 证据或环境变化后，相关 H3 和交付状态必须失效或重新评估。

### NFR-010 确定性

- 同一基线、同一命令和同一环境必须产生可比较的结果。
- 不得存在无上限重试、静默跳过或自动掩盖失败。
- flaky test、隔离测试和 mock 替代必须显式记录。
- 恢复操作必须可重复执行，且不能产生重复提交、重复推送或重复交付。

## 16. 验收场景

### AC-001 新建项目

- GIVEN 用户选择 Java/Vue 新项目
- WHEN 创建、安装和基线验证完成
- THEN 生成 ProjectProfile、有效 Baseline 和初始化提交
- AND 业务需求从统一 Change 流程开始

### AC-002 存量项目接入

- GIVEN 用户提供一个已有 Java/Vue 项目
- WHEN 执行 `sg_adopt` 只读预览并确认
- THEN 无需 `sg_init` 即可建立 ProjectProfile 和 adopted Baseline
- AND 不覆盖现有项目文件

### AC-003 脏工作区

- GIVEN 存量项目存在未提交修改
- WHEN 用户请求接入
- THEN 系统展示脏文件且不自动提交
- WHEN 用户明确批准拟提交清单
- THEN Codex 创建基线提交并重新扫描
- AND 只有工作区干净后才建立正式 Baseline

### AC-004 已知失败基线

- GIVEN 存量项目已有稳定失败
- WHEN 建立 adopted Baseline
- THEN 失败被记录为 knownFailures
- AND 本次变更没有产生新失败时不被历史失败错误阻断
- AND 任何新失败都会阻断

### AC-005 缺少测试

- GIVEN 存量项目没有覆盖本次 AC 的测试
- WHEN 执行 Change
- THEN 生成必要的定向回归或明确使用人工/运行证据
- AND 未覆盖区域被记录为剩余风险

### AC-006 Fix 红转绿

- GIVEN 用户提交可复现 Bug
- WHEN 回归证据在修复前执行
- THEN 证据显示失败
- WHEN 修复完成
- THEN 同一回归证据真实通过

### AC-007 H1 和 H3

- GIVEN Change 契约或交付预览发生变化
- WHEN 尝试复用旧审批
- THEN SpecGate 拒绝旧审批并要求新审批

### AC-008 串行闭环

- GIVEN 一个常规 Change
- WHEN 实现和独立验证完成
- THEN 验证证据绑定当前 commit
- AND 未执行检查不会被计为通过

### AC-009 交付记录

- GIVEN H3 已通过
- WHEN 生成交付
- THEN 创建不可变 DeliveryRecord 和本地 tag
- AND 内部包与客户包引用同一 Delivery

### AC-010 远程推送

- GIVEN 配置了有效 remoteUrl
- WHEN `push=false` 或 H3 尚未通过
- THEN 不推送
- WHEN H3 已通过且 `push=true`
- THEN 推送目标分支
- AND 禁止 force push

### AC-011 增量再交付

- GIVEN 上一 Delivery 已验收
- WHEN 客户提出新反馈
- THEN 新 Change 引用该 Delivery
- AND 记录受影响 AC 和历史回归
- AND 生成新 DeliveryRecord，不覆盖旧记录

### AC-012 失败恢复

- GIVEN 一个工作部分失败，另一个无依赖工作已完成
- WHEN 用户重试
- THEN 只重跑失败和受影响部分
- AND 已完成证据仍然有效

### AC-013 回退说明

- GIVEN 已交付版本需要回退
- WHEN 生成交付材料
- THEN 代码回退步骤明确
- AND Red 风险包含数据、迁移和恢复说明
- AND 不自动操作生产数据库

### AC-014 凭据安全

- GIVEN 用户输入或日志包含类凭据内容
- WHEN 写入项目状态、证据或交付包
- THEN 内容被拒绝或脱敏
- AND 明文凭据不进入版本库

### AC-015 环境变化

- GIVEN 证据来自 Java 21 和 Node 20.19 环境
- WHEN 使用不同主版本运行时复用该证据
- THEN 系统将证据标记为需要重新评估
- AND 不自动沿用旧的 H3 或交付结论

### AC-016 Flaky Test

- GIVEN 同一测试首次失败、有限重试后通过
- WHEN 生成验证评估
- THEN 结果标记为不稳定
- AND 所有失败和重试证据被保留
- AND 高风险变更不能只依赖该测试通过

### AC-017 证据不能替代高风险审查

- GIVEN Red 风险变更的自动测试全部通过
- WHEN 未完成固定 commit 的独立代码、迁移和安全审查
- THEN 验证评估不得进入 `requires-h3`

### AC-018 证据充分性不足

- GIVEN 某个 AC 是非自动化的视觉或业务判断
- WHEN 只有无关的单元测试通过
- THEN 系统判定证据不足
- AND 要求人工演示、观察或用户验收

### AC-019 注意力预算

- GIVEN 用户完成一次普通 Change
- WHEN 进入 H1、验证和 H3
- THEN 用户只需要处理业务范围和最终验收等主要决策
- AND 不需要手工串联内部 Agent 或执行阶段
- AND 恢复操作和当前缺口有明确提示

### AC-020 交付状态

- GIVEN 本地测试通过但未进行 H3
- WHEN 查询交付状态
- THEN 系统只显示 `CHANGE_VERIFIED`
- AND 不显示 `DELIVERY_ACCEPTED`、`PUSHED` 或 `DEPLOYED_VERIFIED`

## 17. 试点与产品成功判定

### 17.1 试点范围

正式扩张前必须使用真实项目验证：

- 至少 3 个真实 Java/Vue 项目。
- 至少 3 个新建项目场景。
- 至少 6 个存量项目变更场景。
- 覆盖 `feature`、`modify` 和 `fix`。
- 至少一次客户反馈后的增量再交付。
- 至少一次失败恢复。

### 17.2 对照组

必须与以下实际基线比较：

```text
裸用 Codex + 开发者手工测试和 Git 操作
```

不能只与完全手工开发比较。

### 17.3 指标

- 到首次可演示版本的时间。
- 到最终验收的时间。
- 人工介入次数和耗时。
- 用户决策次数和恢复所需操作次数。
- 用户手工串联的阶段数量。
- 交付摘要阅读和判断时间。
- 返工轮次。
- 遗漏回归数量。
- 失败恢复时间。
- 增量再交付时间。
- token 和工具执行成本。
- 客户对交付包的采用情况。

### 17.4 通过条件

- 存量项目确实无需 `sg_init` 即可接入。
- 第二次及后续交付能够引用上一 Delivery。
- 增量 Change 能复用有效 AC 和测试。
- 失败恢复不会大面积重跑。
- 交付包内容与实际 commit、证据一致。
- 用户能够感知返工、验收成本或交付风险下降。

首轮试点使用以下临时阈值，后续根据真实项目校准：

- 存量项目接入不超过 10 分钟，不含依赖安装时间。
- 每次变更主要人工决策不超过 2 次。
- 常规变更相对裸用 Codex 的额外耗时不超过 30%。
- 返工轮次、遗漏回归或验收争议中至少一项降低 30%。
- 用户不需要手工串联内部阶段。
- 所有交付结论均绑定当前 commit 和真实验证环境。
- 不存在无证据通过、静默跳过或未确认的脏工作区提交。

若仅增加时间而没有降低返工、验收成本或交付风险，应停止扩张，优先删除
流程步骤和内部 Agent，而不是继续增加功能。

若试点失败，优先裁剪功能和降低流程复杂度，不通过增加 Agent 数量补偿。

## 18. 交付切片顺序

本节只定义产品价值闭环的纵向切片，不定义文件级实施方案。具体模块、工具、
测试和发布步骤由后续 design 和 tasks 文档负责。

### S1：项目就绪

- 存量 Java/Vue 项目只读接入。
- 脏工作区确认提交。
- ProjectProfile、ProjectBaseline、环境指纹和已知失败记录。
- 对应价值：不需要重新初始化即可开始真实客户项目。

### S2：变更已确认并可验证

- feature、modify、fix。
- H1、压缩版低风险流程和已确认 AC。
- H1、实现和 H3 的用户可见路径。
- 对应价值：降低需求漂移和 Agent 自证风险。

### S3：证据已就绪

- 项目命令、独立验证、VerificationAssessment 和证据充分性。
- Flaky test、未执行和未验证风险。
- 对应价值：没有证据的完成状态无法进入交付。

### S4：交付已接受并可增量

- DeliveryRecord、本地 tag、交付状态和双交付包。
- 显式远程推送。
- 上一 Delivery 引用、影响分析和增量再交付。
- 回退和前滚说明。
- 对应价值：客户反馈不必从零开始，历史验收成为可复用资产。

### S5：新项目复用统一内核

- Java/Vue 新项目创建和初始验证。
- 复用 ProjectProfile、Baseline、Change、Evidence 和 Delivery。
- 对应价值：新项目不是另一套产品，而是同一交付内核的另一种入口。

切片的优先级根据真实使用频率和风险调整，但每个切片必须形成端到端可验证
价值，不能只完成内部基础模块而没有用户可见结果。

## 19. 已确认决策

1. 首版只支持 Java/Vue 新项目和存量项目。
2. 新项目创建负责模板、安装、初始验证和可靠起点，不直接生成完整业务。
3. 存量项目通过 `sg_adopt` 只读预览，确认后建立 adopted baseline。
4. 脏工作区采用 B 方案：用户明确批准文件后，由 Codex 创建基线提交。
5. 存量基线允许 `known-failures` 和 `partial`；新失败必须阻断。
6. 测试不足时只补本次变更需要的保护和回归，并记录剩余风险。
7. 每次 H3 生成不可变 DeliveryRecord 和本地 tag。
8. 仅 `remoteUrl` 不触发推送；必须同时 `push=true` 且 H3 已通过。
9. 新反馈引用上一 Delivery，按影响分析复用或失效历史 AC 和测试。
10. 第一版只保证代码回退和回退说明，不自动执行生产部署或数据回滚。
11. 所有 Change 保留 H1 和 H3；低风险 Fix 使用压缩版 H1。
12. 第一版采用可靠串行闭环，不实现复杂并行 DAG 和文件锁调度。
13. 用户通过少量命令和自然语言操作，不手工编排内部工具。
14. 工程证据包和客户交付包分离。
15. 使用真实项目试点，与裸用 Codex 比较，不通过则裁剪范围。
16. 产品定位为交付保证与验收账本，不是完整 SDLC 平台或高级 CI 包装器。
17. 验证独立性按风险分级，同模型不同 Agent 不自动构成独立验证。
18. 证据用于降低审查成本，不取消高风险代码、迁移和安全审查。
19. 技术验证、客户验收、远程推送和生产部署必须分别记录。
20. 记录环境指纹，并在环境变化后重新评估受影响证据。
21. Flaky test、重试、跳过和隔离必须显式记录，不能自动洗成通过。
22. 用户可见生命周期收敛为四个状态，并持续记录注意力预算指标。
23. 需求文档只定义产品应达到的结果，文件级实施步骤进入 design 和 tasks。
24. 首轮试点使用可量化阈值；只增加时间而没有降低返工或风险时停止扩张。

## 20. 最终完成定义

1. 新项目能够建立可靠 Baseline 并进入统一 Change 流程。
2. 存量 Java/Vue 项目无需 `sg_init` 即可接入。
3. 脏工作区不会在未确认时被提交。
4. 存量项目历史失败和新失败能够被正确区分。
5. feature、modify、fix 均使用统一契约和证据模型。
6. Fix 在可行时具备真实红转绿证据。
7. 实现、独立验证和高风险 Review 形成可靠串行闭环。
8. 每次验收生成不可变 DeliveryRecord 和本地 tag。
9. 工程证据包和客户交付包分离并绑定同一交付。
10. 客户反馈能够引用上一 Delivery 完成增量再交付。
11. 失败恢复不会重跑无关工作。
12. 远程 push 只在明确授权且 H3 通过后发生，且不会 force push。
13. 回退和 Red 风险数据说明可追溯，不自动操作生产环境。
14. 试点指标能够证明产品降低返工、验收成本或交付风险。
15. 所有声称通过的检查均有真实命令或运行证据。
16. 验证独立性等级和证据充分性能够支撑 H3 决策。
17. 环境指纹变化后不会错误复用失效证据。
18. Flaky test、重试和隔离不会掩盖本次新增失败。
19. 高风险变更同时具备证据和固定 commit 的独立代码审查。
20. 技术验证、客户验收、推送和部署状态不会混淆。
21. 用户只需处理少量产品级状态和决策，不承担内部编排。
22. 项目基线和 DeliveryRecord 可在更换执行宿主后继续读取。
