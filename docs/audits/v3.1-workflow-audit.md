# SpecGate v3.1 工作流审计（2026-10-19）

范围：add / modify / fix / remove 四条路径，代码为 `feat/v3-mvp` 当前 HEAD，结合 Node、Vue、Python 三个真实仓库的运行记录。

结论：主流程成立，AI 承担实现/测试/审查/集成，人只在 H1/H2/H3 决策；但存在 5 个需要正视的缺口，其中 2 个会直接影响审计可信度。

## 合规矩阵

## 缺口

### 1. H1/H2/H3 对话框缺少变更内容（高，已修复）

`askApproval` 原先只显示 change 名与产物指纹，人无法在门禁处审阅需求、文件与 diff。已改为 Markdown 审阅摘要：H1 需求概览、H2 任务/文件/套件、H3 验收/diff/脱敏，限额 20 文件、40 行、6000 字符。

### 2. guard 与 H1 顺序自相矛盾（高，未修复）

`guards.js` 在 `H1_PENDING` 时禁止写 `specs/`、`design.md`、`tests/`，但 `checkM1` 又要求 specs delta 已存在。结果是**主 Agent 必须用 shell 绕过 guard** 才能先把 specs 写好；guard 只约束子 Agent 的 write/edit 工具。这不是安全的强制边界。

建议：允许 H1 前写 proposal + specs；design/tests 仍在 H1 后冻结；或把 H1 定义为“proposal 批准”，M1 移到 H1 之后。

### 3. AC 编号跨 change 冲突（中，部分修复）

AC 编号是 change 局部编号，但归档后的测试文件继续留在仓库。新 change 复用 `AC-001` 时，历史测试也会带同名 AC。已把任务级校验限制为“本次 diff 内的用例”，但集成/验收仍可能选中归档测试的文件，导致验收表指向旧文件。

建议：AC 改为 change 前缀（如 `AC-add-health-001`），或归档时重写测试标签。

### 4. touched 清单对 docs 不强制（中，未修复）

Python T-002 的 `touched.modify` 只有 `api/app.py`，实现者改了 `docs/swagger.yaml` 仍被允许合并。`diffCheck` 对 docs 放行，导致“预期文件清单”与实际 diff 不完全一致。

建议：touched 显式区分 code/docs/tests；docs 变更要么进清单，要么在 H2 声明 `allowDocs`。

### 5. 证据链是本机文件，不是可验证签名（中，设计取舍）

`.specgate/evidence/*.json` 用哈希链记录，但没有签名或外部时间戳；本机可被重写。当前定位是“机器证据 + 人审”，不是防篡改审计。

建议：至少在归档时把证据哈希写入 git commit 或 tag annotation，形成仓库内锚点。

## 其他观察

- fix 路径确实要求复现用例在 base 上失败、修复后通过；但“测试不被弱化”仍靠 reviewer 判断。
- remove 路径允许历史测试不在 diff 内（`requireChangedFiles=false`），因此删除能力后残留测试不会被强制清理；需靠 reviewer 与 specs 校验。
- reviewer 是 LLM，不是独立人类审查；人在 H3 只看到验收摘要，不逐行看 diff（本轮已补 diff 缩略图）。
- Agent 池按仓库+角色复用，reviewer 每次新建；子 Agent cwd 固定，复用跨 worktree 依赖提示词要求其 `working_directory` 切换，属于软约束。

## 建议优先级

1. 修 guard/H1 顺序（否则 specs 只能绕过 guard 写）。
2. AC 命名空间（否则多 change 后验收表会串）。
3. touched 对 docs 的约束。
4. 证据锚定到 git tag。
5. 对话框内容（本轮已完成）。
