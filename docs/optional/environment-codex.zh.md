# 在 Codex 中使用 SpecGate

进入业务项目的 Codex 会话后使用以下入口。所有环境操作都在会话内进行，不需要另一套外部安装脚本。

| 入口                | 适用请求                                     |
| ------------------- | -------------------------------------------- |
| `$sg-codex`         | 不确定入口、需要帮助；按意图导航             |
| `$sg-codex-env`     | 环境预检、复用、按需安装和故障诊断           |
| `$sg-codex-project` | 新项目初始化、接入已有项目、建立基线         |
| `$sg-codex-change`  | 新增、修改、修复、继续/暂停/取消及验收交付   |
| `$sg-codex-status`  | 只读查看业务项目、技术栈、环境、任务与待审批 |

旧 `$sg-codex-setup` 仍可使用，按请求转到环境或项目准备，不再维护独立流程。

## 环境准备

可以直接要求：`使用 $sg-codex-env 只预检当前项目环境，先不要安装。`

准备流程为：识别平台和项目技术栈 → 只读预检 → 复用已有工具 → 展示缺项安装计划 → 可信安装确认 → 按需安装 → 真实版本探测。缺失项、权限拒绝、取消、下载/校验失败均保持环境门禁阻塞，不能继续源码生成、实现或交付。

新项目先让用户选择 JDK 8/17/21 和 Vue/React。Java 17 + Vue 项目只补齐需要的 JDK 17、Maven 3.9、Node/npm、Git，不预装 JDK 8、21 或其他非必需工具。存量项目优先读取实际配置；输入与已记录技术栈冲突会拒绝，不能顺便更换项目技术栈。

后台 `sg_env_check` 是只读预检；`sg_env_prepare` 请求安装确认、执行安装并复测。它们不接受 `approved=true`。没有可信表单时返回待确认，Codex 可根据用户明确的安装请求，在正常宿主权限审批下协调原生命令并重新预检。Git 等需要系统包管理器的组件返回明确的宿主操作提示，不伪称已安装。

工具链安装到当前用户的 `.specgate/toolchains`，后续项目共享并按技术栈选择。不会修改全局 JAVA_HOME、PATH、npm 或 Maven 配置。损坏的已有目标不会被自动覆盖；检查冲突目录、选择安全修复方法后重试。

## 国内镜像与临时数据

默认 Node 使用 npmmirror，JDK 使用南京大学 Adoptium 镜像，Maven 归档与依赖使用阿里云公共仓库。归档版本与官方 checksum 固定在内部目录中，实际下载后必须校验。下载失败不静默切换到官方源。

明确选择 `source=official` 可使用对应官方归档源；`source=custom` 需要管理员配置 `SPECGATE_BINARY_MIRROR`，目录布局为 `<镜像根>/<组件 id>/<归档文件名>`，仍使用内置官方 checksum。自定义 npm/Maven 可通过当前会话进程的 `SG_NPM_REGISTRY`、`SG_MAVEN_MIRROR` 设置，URL 仅允许不含凭据的 HTTPS 地址。

构建验证使用临时 npm 配置和 Maven settings，不改用户的 `.npmrc` 或 `.m2/settings.xml`。前端锁文件中的归档来源仍是其锁定值，切换构建源前应核对锁文件，不能宣称只改 registry 就改写了所有下载来源。

代理和企业证书沿用宿主已配置的网络能力；本次不自动配置代理凭据，也不保证 Node 下载器会读取任意 `HTTPS_PROXY` 设置。代理不可用时明确报告下载失败或超时，不能关闭 TLS 校验；可显式改用可访问的可信镜像。不要把含认证信息的代理 URL 写入项目或验收报告。

临时归档与解压目录在成功或失败后清理，受控取消走同样清理路径；下次安装只恢复有所有者标记且所属进程已退出的缓存暂存目录。工具链本身是可复用安装，不作为临时垃圾删除。

## 就绪状态与恢复

工具真实版本探测、Codex 能力/认证、MCP 连接、项目绿色基线和业务测试是不同结果。安装完成不代表项目已验证；环境完成后，项目入口继续真实验证并建立基线，然后等待业务需求。状态入口展示上次检查时间，历史结果不表示本次重新验证。

若 Node 不可用导致 MCP 未启动，已加载的环境 Skill 可指导 Codex 在当前会话内补齐运行时并重连。若 Skill 未加载、权限不允许或宿主无法重连，明确停在阻塞，不冒充准备成功。Codex 登录由用户完成，不保存或复制登录凭据。

项目入口保护现有文件，已生成未验证时继续验证，不重复新建。`sg_project_setup` 只配置 Agent、Skill 和 MCP，不能替代环境准备。需求入口沿用 H1/H3 与任务检查点；状态入口只读，绝不会因为用户问进度就自动安装或恢复任务。

## 验证范围

实现目标是 Windows/Linux x64。Linux 本次验收按用户指定使用 VMware Workstation 的 Ubuntu 26.04.1 LTS；Ubuntu 22.04/24.04、Debian 12 和其他 Windows 版本必须分别记录实际执行情况。

本仓库此次验收采用用户确认的“Windows 宿主 Codex 保持登录和会话，调度 Ubuntu 执行 Linux 命令”模式，沿用 VMware Guest Tools，不迁移认证信息。它不等于 Ubuntu 的 Codex CLI 已登录，也不等于已配置 Desktop SSH 远程项目或 app-server 远程连接；虚拟机原生会话验收仍单独记录为未验证。

真实命令结果保存在验收记录中。MCP stdio smoke、聚焦回归与工具链下载测试各自只证明对应范围；不能用它们代替宿主内 Skill 调用、可信人工审批、原生子代理或完整交付验收。
